# Environment files (.infraenv)

A project that uses Infrawrench commits `.infraenv` instead of `.env`. It lists every environment variable and says where its value comes from, so it is reviewed and versioned like code, and it never holds a secret value. `infraenv pull` (the `@infrawrench/infraenv` npm package) or `infrawrench env pull` (the desktop app's CLI) resolves it into a normal `.env` that starts with `# Auto-generated by Infrawrench. Do not edit.` The user-facing guide is https://infrawrench.com/docs/features/env-files. Read `references/format.md` before writing anything beyond a simple variable, and `references/migrate.md` when converting an existing `.env`.

## Rules

- **Never write a secret value into `.infraenv`**, and never copy one out of `.env` into it, a commit message or chat. A secret becomes a `secret("NAME")` reference (an organization secret the user creates in Infrawrench) or a `resource(...)` reference to where it already lives.
- **Never edit the generated `.env`.** Change `.infraenv` and pull again. A `.env` without the generated header is hand-written: do not overwrite it unless the user says so (`--force`).
- **Prefer references by name** (`resource("<plugin>/<type>", "<display name>", "<output>")`). They resolve in whichever organization pulls the file. Pin by id (`resource("<id>", "<output>")`) only when the user wants one exact resource or a name is ambiguous.
- **Do not add `[infrawrench] org`** unless the user asks to pin the file to one organization.
- Keep `.env` (the output) in `.gitignore`.

## Process

1. **Find the file.** `.infraenv` at the repository root (or the one the user names). If there is none, create it with `infraenv check` passing afterwards (see `references/migrate.md` when a `.env` exists).
2. **Find the values' sources.** With the Infrawrench MCP server connected, `list_env_sources` searches the organization's resources and lists each one's outputs with a suggested variable name; `describe_env_file` checks a draft. Without it, ask the user which resource or secret each variable should come from; do not guess ids.
3. **Write the variables.** Shared values go in `[env]`; what differs per environment goes in `[env.<name>]`, or better, in a substitution: `[vars]` / `[vars.<name>]` plus `${name}` inside the reference, so one line serves every environment. Put a `# <Plugin>: <resource name> (<output>)` comment above each reference.
4. **Check.** Run `infraenv check` (or `infrawrench env check`, or the `describe_env_file` tool). It reports syntax errors with line numbers, references that match nothing or several resources, outputs a type does not have, secrets that do not exist or have no value, and substitutions with no value. Fix every problem; report any that need the user (a secret to create, an account to connect).
5. **For Infrawrench CI**, a job loads the file with `env-file:`; `check_ci_env_file` (MCP) says what each variable would give a job on a given branch and what to grant first. In CI, `secret()` reads the repository's CI secrets, not the organization's.
6. **Pull only if asked.** `infraenv pull [--env <name>]` writes `.env` with the real values. Do not print the values; the commands never do in text mode.

## Commands

| npm package (`npx infraenv` or `node_modules/.bin/infraenv`) | Desktop CLI                        | What it does                                                       |
| ------------------------------------------------------------ | ---------------------------------- | ------------------------------------------------------------------ |
| `infraenv check [--var k=v]`                                 | `infrawrench env check`            | What each reference points at, and every problem. Exit 1 on any.   |
| `infraenv pull [--env <name>] [--var k=v] [--stdout]`        | `infrawrench env pull`             | Resolve and write `.env` (mode 0600). Exit 1 if a variable failed. |
| `infraenv install` / `uninstall` / `status`                  | `infrawrench env hooks install`    | Git hooks that pull again when a commit changes `.infraenv`.       |
|                                                              | `infrawrench env init --from .env` | A new `.infraenv` with one `secret("KEY")` line per `.env` key.    |

The npm package reads `INFRAWRENCH_API_KEY` (an `iwk_` key) when it is set, else the key `infraenv login` stored; the desktop CLI uses the desktop app's sign-in. In a third-party CI, set `INFRAWRENCH_API_KEY` and run `npx @infrawrench/infraenv pull --env <name>`; in Infrawrench CI, a job's `env-file:` key loads the file without a key.

## Example

```ini
[vars]
stage = dev

[env]
NODE_ENV = development
# Neon: storefront / dev (Connection string)
DATABASE_URL = resource("neon/neon-branch", "storefront / ${stage}", "connectionString")
STRIPE_SECRET_KEY = secret("STRIPE_SECRET_KEY_${stage}")

[vars.production]
stage = main

[env.production]
NODE_ENV = production
```
