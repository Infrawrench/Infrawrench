# @infrawrench/git-web

The UI of git.infrawrench.com: Vite, React 19, TanStack Router (file routes), TanStack Query, Tailwind 4 on the app's theme tokens. It talks to the worker's JSON API through a client derived from `@infrawrench/git-contract`, and runs without the worker against an in-browser mock.

```sh
pnpm --filter @infrawrench/git-web dev:mock    # VITE_GIT_MOCK=1 vite, http://localhost:5174
pnpm --filter @infrawrench/git-web typecheck
pnpm --filter @infrawrench/git-web test
pnpm --filter @infrawrench/git-web build
```

## Layout

| Path                   | What                                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `src/api/`             | The typed client (`client.ts`), its React Query form (`queries.ts`), the types derived from the contract.               |
| `src/lib/`             | Pure helpers: `paths.ts` (every URL), `refs.ts`, `lines.ts`, `diff-rows.ts`, `format.ts`, `highlight.ts`, `session.ts`. |
| `src/components/`      | Shared primitives. Nothing in here knows a feature.                                                                     |
| `src/layout/`          | `SidebarShell` (the one frame, "The shell" below), `RepoLayout`, `TopBar`, the account menu and `workspace.ts`.         |
| `src/features/<name>/` | Pages and their private components, one folder per feature.                                                             |
| `src/routes/`          | Route files only: read the params, render a page from `features/`.                                                      |
| `src/mock/`            | The dev mock: `db.ts` (state), `git.ts` (fixtures and Git operations), `handlers/*.ts` (the endpoints).                 |
| `scripts/`             | `build-fixtures.mjs` and the scripted histories it turns into fixtures.                                                 |

Feature ownership: `explore`, `new-repository`, `onboarding`, `namespace`, `workspace` and `code` are the shell and code pages. Issues, branch pages (`branch-page` and `review`), CI, Infrastructure, repository settings and personal settings each have their own folder under `features/` and their own files under `routes/` and `mock/handlers/`; none of them needs to edit a file listed above except `routeTree.gen.ts`, which the router plugin rewrites.

## Rules

- **No blurbs.** A page has a name and its controls. No slogans, no "what this does" paragraphs, no helper text that explains a feature. An empty state is one short neutral line plus the next action (`EmptyState`). A `Field` hint states a constraint, never a pitch.
- **No em dashes** in code, comments or copy.
- **Icons are inline SVG** from `components/icons.tsx` (Lucide paths on the app's 24x24 grid). Add a glyph there. Never an emoji, never an icon font.
- **The app's look**: the tokens of `app/packages/ui/src/theme.css` (`bg-surface`, `bg-surface-raised`, `bg-surface-inset`, `border-border`, `text-on-surface*`, `text-danger|warning|success`, `bg-accent text-on-accent`), `text-xs` body with `text-sm`/`text-base` headings, `rounded` and `rounded-md` corners, 1px borders, no shadows on cards. Never a Tailwind palette colour (`text-red-500`): it is right in one colour scheme only. Dark and light both come from `prefers-color-scheme`; look at both.
- **Accessible**: real `<table>`s with a caption (`Table`), every control labelled (`Field`, or `aria-label`), menus and pickers keyboard-navigable (`Menu`, `Popover`, `moveFocus`), state changes announced (`role="status"`, `role="alert"`).

## Adding a page

1. **The URL** goes in `src/lib/paths.ts`. Every link is `<AppLink href={paths.x(...)}>` (or `ButtonLink`), and navigation from code is `useGo()`. Do not use TanStack's `<Link to>`: refs and file paths contain slashes, and `paths.ts` is where they are encoded once. `paths.issues`, `paths.issue`, `paths.newIssue`, `paths.branches`, `paths.branchPage`, `paths.startWork`, `paths.ci`, `paths.infrastructure`, `paths.repoSettings` and `paths.settings` already exist and the tab bar and the code pages link to them. The Infrastructure tab is `/infrastructure`, not `/terraform`, which belongs to the state backend.
2. **The route file** goes in `src/routes/`, flat names with dots: `src/routes/$owner/$repo/issues.index.tsx` is `/:owner/:repo/issues`, `issues.$number.tsx` is `/:owner/:repo/issues/:number`, `branches.$.tsx` is `/:owner/:repo/branches/<anything>` (a splat). Everything under `$owner/$repo/` renders inside `RepoLayout` (`$owner/$repo/route.tsx`). A route file holds no logic:

   ```tsx
   import { createFileRoute } from "@tanstack/react-router";
   import { IssuesPage } from "../../../features/issues/IssuesPage";

   export const Route = createFileRoute("/$owner/$repo/issues/")({ component: IssuesPage });
   ```

   Search parameters need `validateSearch` on the route; read them with `Route.useSearch()` in a small wrapper component in the route file and pass them to the page as props. The dev server (or `vite build`) regenerates `routeTree.gen.ts`; commit it. If two branches both changed it, regenerate rather than merge by hand.

3. **The page** goes in `src/features/<feature>/`. Inside a repository, `useRepository()` is the `Repository` (already loaded by the layout: its `viewer` block decides which buttons show) and `useRepoRef()` is `{ owner, repo }` for `paths` and for request `params`. A new first path segment that belongs to the Code tab is added to `CODE_SECTIONS` in `RepoLayout.tsx`; the other tabs match their own segment already.
4. **Personal settings** live under `/settings` (`src/routes/settings*.tsx`); the account menu links to `paths.settings()`.

## Talking to the API

```tsx
import { useMutation, useQuery } from "@tanstack/react-query";
import { api } from "../../api/client";
import { invalidate, queries, usePages } from "../../api/queries";

const issue = useQuery(queries.issues.get({ params: { ...repo, number } }));

const close = useMutation({
  mutationFn: () =>
    api.issues.update({ params: { ...repo, number }, payload: { state: "closed" } }),
  onSuccess: () => invalidate("issues"),
});

const list = usePages(["issues", "list", request], (cursor) =>
  api.issues.list({ ...request, query: { ...request.query, cursor } }),
);
// <LoadMore pages={list} /> under the list; list.pages[0]?.counts for the tabs.
```

- `api.<group>.<endpoint>({ params, query, payload })` resolves with the endpoint's JSON, typed from the contract. Groups and endpoint names are the contract's (`src/api/routes.gen.ts` lists them all).
- `queries` mirrors `api` and answers `{ queryKey, queryFn }`. Keys are `[group, endpoint, request]`: `invalidate("issues")` refetches the group, `invalidate("issues", "get")` one endpoint.
- A failure is an `ApiError` with `status`, the server's sentence as `message`, and `code` (one of the contract's `ERROR_CODES`) to branch on. `QueryView` renders loading, error and data; `InlineError` goes beside a form's button.
- Request numbers are numbers (`limit: 50`), flags are the contract's `"true"`/`"false"` strings.
- After changing the contract's routes: `pnpm --filter @infrawrench/git-web generate:routes` (a test fails until `routes.gen.ts` matches). The client carries no Effect at runtime; import values from the contract only when they are plain functions or constants (`names.ts`, `urls.ts`), and everything else as `import type`.
- If the contract lacks something, do not edit it from here. Note it and work around it.

## The dev mock

`VITE_GIT_MOCK=1` replaces the client's transport with handlers in the browser. Nothing of it is in a production build.

- **Adding endpoints**: create `src/mock/handlers/<feature>.ts`. Every file in that folder is picked up; do not edit another feature's file. Two files answering the same endpoint throw at startup.

  ```ts
  import { defineMockHandlers, notFound, paginate } from "../define";
  import { findRepository, requireUser } from "../db";

  export default defineMockHandlers({
    issues: {
      list: ({ params, query }) => {
        const repo = findRepository(params.owner, params.repo); // 404s as the API does
        return { ...paginate(issuesOf(repo.id), query), counts: { open: 3, closed: 9 } };
      },
    },
  });
  ```

  Handlers are typed by the contract: `params`, `query` and `payload` in, the endpoint's JSON out. Throw `notFound()`, `badRequest()`, `conflict()`, `unprocessable()`, `unauthorized()` or `mockError(status, sentence, code)` for errors. Every file in `handlers/` is read as a handler file, so a feature's state (its issues, its runs) goes one level up, in `src/mock/<feature>-data.ts`.

- **Shared state** is `src/mock/db.ts`: `currentUser()`, `requireUser()`, `users`, `findRepository(owner, repo)` (a `RepositoryRecord`, whose `openIssueCount` and `openBranchCount` the bar's tabs show; the seeds' `issues` and `pages` are those counts until the threads are first read), `toRepository`, `toSummary`, `findNamespace`, `isMember`.
- **Git** is `src/mock/git.ts` over real repositories: `gitOf(repo)` then `resolveRef`, `summarize` (a `CommitSummary`), `log`, `mergeBase`, `aheadBehind`, `diffCommits` (a `DiffFile[]` with hunks), `statsOf`, `blobAt`, `listTree`. A branch page's mock points at real branches: `acme/infra` has `feature/vpc-peering` (3 commits ahead of `main`, 3 behind, page #12), `fix/database-backups` (1 ahead, #14), `feature/flow-logs` (merged as #7 by the scripted fixture's merge commit) and `feature/budgets/staging-alarm`, a branch with two slashes written by `seedBranches()` in `db.ts` with two pages: #17 closed (`feature/budgets/staging-alarm~1`) and #18 open (the bare key, and `~2`). `jonas/edge-router` has `fix/lowercase-hosts`, proposed to `acme/edge-router` as #6 (`jonas/edge-router:fix/lowercase-hosts`), and `mara/infra` has `docs/peering-notes`, proposed nowhere, for trying "Propose to acme/infra". `threads-data.ts` `pageKeyOf` and `findPage` are the key rules; `refsOf` reads a fork's head from the fork and copies its objects into the base (`copyObjects`).
- **Fixtures**: `acme/infra` (private, Terraform, CI) and `acme/edge-router` (public, TypeScript) are generated from the scripted histories in `scripts/fixtures/` by `pnpm --filter @infrawrench/git-web fixtures`, which writes them with real `git` and reads them back into `src/mock/fixtures/*.generated.json`. The other repositories share one of the two histories. `acme/new-service` is empty.
- **Plans**: every namespace of the mock has a plan (`acme` paid, `tidewater` free and already holding the three private repositories the free plan includes, people the personal allowance), and a private repository past the limit is refused with the sentence `privateRepositoryRefusal` of the contract words, the one the API sends. `tidewater` defaults to public.
- **Who is signed in**: `?mock=signed-in` (default: `mara`, a member of the `acme` and `tidewater` organisations with every `git:*` permission), `?mock=signed-out`, `?mock=new-user` (signed in, no username yet). Kept in `sessionStorage`. `jonas` and `priya` are the other people.
- `VITE_GIT_MOCK_DELAY` is the latency per call in ms (default 40).

### The shell (`layout/`, `features/workspace/`)

There is one UI. `routes/__root.tsx` draws `SidebarShell` for everyone once the session is known (nothing before, so a page never shows one sidebar and then the other): a sidebar the height of the window, and the page beside it with a bar of its own. Below `md` the sidebar is a drawer behind the bar's menu button. The content column is `bg-surface-raised` and the sidebar `bg-surface`.

- **A member's sidebar** (signed in with a username): the workspace switcher, Home, a folding "Your work" group (Changes, Reviews, Mentions), the selected workspace's repositories as one flat list under its name (a heading, not a fold; no other namespace is listed), a mark on each repository an agent is working in (`useAgentRepositories`: the open branches in `agent_working`, asked again every half minute), and the account menu at the foot. Its `nav` is named "Workspace".
- **A visitor's sidebar** (signed out, or signed in and still choosing a username): the forge's name, Explore, and when the page is a repository's, a group for its namespace holding the namespace and the repository (read from the cache `RepoLayout` fills). At the foot, Sign in, or the account menu for someone without a username yet. Its `nav` is named "Site". The pages beside it are the same pages a member sees. `/` sends a visitor to Explore (`HomePage` in `AgentHome.tsx`).
- **A workspace is a namespace** (`layout/workspace.ts` `useWorkspaces`): the session's organisations, the reader's own, and any other namespace `repositoryLists.listMine` has a repository of. The current one is kept in `localStorage` (`git-workspace`) and is what Home and Changes ask the API for. The sidebar follows the page: on a repository of another of the reader's workspaces (`workspaceOwning`, by the owner's slug) it shows that workspace at once and an effect stores it as the choice, so the switcher, Home and Changes agree. On a repository the reader has no tie to, the choice stays and the repository is one row under "Viewing" above the list, read from the cache `RepoLayout` fills, as the visitor's sidebar does. A workspace with nothing in it says "No repositories" over a New repository link. The "Your work" group and the recent lists under the repository shown still fold, kept in `localStorage`.
- **A page's bar is `TopBar`** (`layout/TopBar.tsx`): `<TopBar title="Changes" actions={...} />` anywhere in a page, drawn through a portal in the shell's bar. A page that renders no `TopBar` gets the shell's own: the page's name, or `owner / repo` while a repository loads. `BarPortal` is the same slot for a bar that is not a title and actions.
- **A repository has no header** (`RepoBarFrame` in `RepoLayout.tsx`). The bar is the breadcrumb (namespace / repository, a lock for a private one, then the page), the sections as `QuietTabs` (`components/controls.tsx`: plain words, the current one on a tile, icons alone below `xl`), then star and fork as a glyph and a count. A page under it adds to the bar with `<RepoBarCrumb>` (its name, after the repository's) and `<RepoBarActions>` (its controls). A fork's pages start with "Forked from", a link to compare with the parent, and "Propose to <parent>" for its default branch.
- **`lib/shell.ts` `pageColumn`** is the column `Page`, `SettingsFrame` and `Loading shape="page"` sit in. Three widths, all with the bar's gutters (`px-4`, `md:px-10`) and `py-6`: `wide` (the window; lists, tables, code and diffs), `reading` (a conversation and its sidebar, 84rem) and `narrow` (a centred form). A page that pads itself (Home, the lists) uses the same gutters.
- **How it sizes itself.** The scale is `text-xs` body, `text-sm` in the sidebar and the bar, `text-base` for a page's heading, and one large headline on Home. Rows are one line: 44px in a work list, 28 to 32px in a file table. What reads as prose has a measure whatever the window: rendered Markdown stops at 60rem (a table or a code block may use the room), a settings page at `max-w-3xl` (`SettingsFrame`), a conversation at `reading`. What reads by the row uses the window. Home's two cards sit side by side from `2xl`, since below that the sidebar leaves each too little for a title and its line.
- **The bar below `sm`** is a grid of two rows (`SidebarShell`'s header): the menu, where the page is, and star and fork; then the repository's sections (`QuietTabs`) or a page's `TopBar` actions on a row of their own that scrolls sideways. `.review-page` knows the taller bar (`--review-sticky-top`). Anything new in the bar says where it goes below `sm` (`max-sm:col-span-full max-sm:row-start-2`) or it lands in the fourth column.
- **Scrollbars and tables** (`globals.css`, `components/Panel.tsx`): the window keeps a stable gutter so the bar's controls stay put between pages; everything that scrolls inside the page has a thin bar; a strip that scrolls sideways (tabs, versions) takes `no-scrollbar`. `Table` scrolls inside its panel, so a panel never clips a column. `RelativeTime` never wraps.
- **Two departures from the app's theme, both in `globals.css`**: the dark scheme's `--color-border` and `--color-border-strong` are a step lighter here, because these pages are mostly hairlines and the app's dark border is nearly the surface's colour; and a `select` has no platform chrome (one chevron, drawn for both schemes).
- **The account menu** (`layout/account-menu.tsx`) is the reader's repositories and stars, Settings, the app and Sign out. `Menu` has `checked` (a `menuitemradio` with a tick), `heading` (a label above an item) and `side="top"` for a menu at the foot of the window.
- **`features/workspace/`**: `AgentHome` (the home page), `ListPages.tsx` (`/changes`, `/reviews`, `/mentions`), `rows.tsx` (`WorkRow`, the one-line row every list is made of, and `ChangeRow`, `SuggestedRow`, `WorkCard`) and `sentences.ts`, the pure part: the headline, the "pushed changes to" sentence, a reason's words, an activity's verb, the review estimate. Every sentence is computed from the response; none is written by a model. Reviews reads the existing `review.inbox`; the rest read `workspace.*`.
- **`/changes`, `/reviews` and `/mentions` are reserved namespaces** (client-core `git-names.ts`), since they sit where a namespace's page would.
- **`/claude` and `/cursor` are bot accounts' pages** (`features/namespace/BotPage.tsx`). `NamespacePage` asks the contract's `botByUsername` before it asks the API, so the page is drawn from the list with no request: the picture, the name, a Bot badge and one sentence, and no repositories, stars or settings. A bot is a `UserRef` with `kind: "bot"` wherever a commit names one, and `UserLink` and `CommitAuthors` call it by its display name ("Claude") rather than its username. Its picture is a file of the UI's own under `public/assets/bots/` (so under `/assets/*`, which the asset layer serves without the Worker and `_headers` caches for a year: a changed picture gets a new file name). They are the vendors' files, unchanged; `THIRD-PARTY-NOTICES.md` says where each came from. Never hotlink one and never draw one.
- **Someone in no organisation is offered a workspace** (`features/onboarding/workspace-offer.tsx`): on the username page in place of "Run CI and review agents in" (a name field, the price, "Continue to payment ($20 a month)" and "Not now", which goes on with none), and in Settings > Organisations in place of the empty state. `useWorkspaceCheckout` sends the name and follows the URL it gets; the typed name is kept in `sessionStorage` so a cancelled payment comes back to it. Back on the username page with `?workspace=return&username=`, the page claims that username into the one organisation the person now has without asking again, unless it is a username that is paid for. The mock has two scenarios for it, `?mock=new-solo` and `?mock=solo`, and no payment page: its `startWorkspaceCheckout` creates the organisation and answers the page to come back to. `onboarding/__tests__/workspace-offer.test.tsx` holds both pages.
- **Commit emails are part of Settings > Organisations** (`features/settings/CommitEmails.tsx`): under each organisation that has a name, "Commit emails in <organisation>" lists the reader's addresses there as Verified or Pending, a pending one with its code field, Verify and Send again, and a field to add another. One `account.listCommitEmails` query feeds every organisation's list, and it is asked again every five seconds while an address is still waiting for its code to be mailed (`codeSentAt` null), since the app sends it a few seconds after the forge asks. The mock "mails" at once and takes one code, `MOCK_COMMIT_EMAIL_CODE`. **Settings > Profile shows the same component** for the reader's own repositories (`organization={null}`, the rows whose `organizationId` is null, added with a null `organizationId`), under a "Commit emails" section; `useCommitEmails` is the one query with its refetch rule, and each page keeps the rows of the place it shows. `__tests__/profile-commit-emails.test.tsx` holds that neither page shows the other's.
- **The mock** (`mock/workspace-data.ts`, `mock/handlers/workspace.ts`): Acme is a team of five with fifteen open branches in three repositories. `acme/infra` `feature/vpc-peering` and `fix/database-backups` and `acme/edge-router` `feature/health-checks` are pages the rest of the mock holds; the other rows exist only in that file, so opening one is a 404 in the mock.

### Branches and their pages (`features/branch-page/`)

Every branch but the default one has a page, named by its key (`BranchKey`, client-core `git-branch-key.ts`, re-exported by the contract): `feature/a`, `bob/infra:feature/a` for a fork's branch proposed here, either with `~2` for an earlier page of a name used again. A page's number is its conversation's (`api.issues.*` take it, `#12` in a comment names it) and is never shown or put in an address.

- **Routes.** `/:owner/:repo/branches` is the Branches tab: the pages (`ThreadList kind="branches"`, open, merged and closed, a "from fork" chip on a page whose branch is in a fork) and, at `?view=all`, every Git branch (`AllBranches`: ahead and behind, its page, compare, create and delete). `/:owner/:repo/branches/<key>` is the page: the key is the route's splat with its slashes as the path's own (`paths.branchPage`, the contract's `branchPagePath`), and in an API path one encoded segment (`feature%2Fa%2Fb`, `fillPath`). Commits and Checks are `?tab=commits|checks`, since a splat has no room for a suffix, beside `?v=&diff=`. `/:owner/:repo/start` is Start work. An address with another key for the same page (`feature/a~2` for the one the bare name finds) is replaced by the page's own key, query and anchor kept.
- **Old addresses** (`redirects.tsx`, routes `pulls.*`): `/pulls` goes to `/branches` with its `?q=`, `/pulls/new` to `/branches`, `/pulls/start` to `/start`, and `/pulls/:n`, `/pulls/:n/{files,commits,checks}` through `branches.locate` to the page (the tab kept, the anchor kept), or to `/issues/:n` when the number is an issue's. `/issues/:n` for a page's number goes through `locate` too.
- **Forks.** A fork's branches get no page on push. `ProposeButton` ("Propose to <owner>/<name>", on each row of a fork's All branches and in its "Forked from" line) calls `branches.propose` on the parent with `{ head, headRepository: "<fork owner>/<fork name>" }` and goes to the returned key's page in the parent. A 409 `branch_page_exists` goes to the page that bare key names. The fork's own Branches tab says so when it has no pages and links to All branches.
- **`useBranchPage()`** is the page under `BranchLayout`; `refreshBranchPage()` refetches what a change can show up in. Queries for a page take `params: { owner, repo, branch: page.key }`; traces take `branch: page.headRef`; CI and Terraform runs take `page: key`.
- **The compare page** reads a comparison and, when `comparison.page` is set, links to the head branch's page. It opens nothing.

### Agent work review (`features/review/`)

`BranchPage` is the Review tab of a branch's page (`BranchPageView` picks the tab). `StartWorkPage` is `/start`, linked from the Branches tab.

- **The page's state is in the address**: `?v=3&diff=whole|step|since` (`paths.branchPage`, `parseBranchSearch`). Without them it opens on the newest version, against the one last reviewed when there is something newer (`defaultSelection`).
- **`review/branch.ts` is the pure part** and is tested: the "needs now" line, `diffNotice` (what an inexact or rebased interdiff says), and `placeOnDiff`, which decides whether a trace entry or a finding sits on its line, above its file, or in the list above the diff. Lines are numbered in the version they were recorded on, so on a later version they are only placed on lines that diff adds.
- **The page is a document, the width of the window** (`ReviewFrame` in `BranchLayout`). From the top: the title as a headline, under one line of meta (`BranchMeta` in `BranchLayout`: a quiet state pill, `head → base` with a fork's head as `owner/name:branch`, the author and the agent, the age; `ThreadHeader large` draws the caller's line and no badge of its own), what the branch needs under it, Review / Commits / Checks as `QuietTabs`, the ask as text (`Ask.tsx`), the versions as one slim strip (`VersionRail`: a card is its number, badges, age and size, the rest its tooltip; the strip scrolls inside the page, opens at its newest end and fades at a side that has more), the notes on the picked version (`Notes.tsx`), then the changed files, closed, with a tree of them beside and the diff's totals under the tree. What closes the page comes after: findings, the merge box and the conversation in one column, the agent, instructions, reviewers and labels beside those. Nothing sits beside the diff but its files, so a split diff has the room.
- **The diff and the file tree are `@pierre/diffs` and `@pierre/trees`** (Apache-2.0, pinned, `THIRD-PARTY-NOTICES.md`), on the branch page only. `review/diff/ReviewDiff.tsx` and `review/diff/FileTreePane.tsx` are the only modules that import them, and `VersionDiff` loads both with `lazy`, so neither is in the first download. Every other diff on the site (commits, compare) keeps `DiffView`.
  - **The renderer reads a patch.** `review/diff/patch.ts` (pure, tested) writes a `DiffFile`'s hunks as patch text (`patchOf`), with bidirectional controls written out as `showBidi` does everywhere else, since the renderer draws lines itself. Hidden lines come from one request for the new file: the old file follows from it and the hunks (`oldLinesOf`), handed to the renderer's `loadDiffFiles`.
  - **What hangs on a line is an annotation**, and an annotation is this app's own component: the renderer keeps its lines in a shadow root and takes annotations as ordinary children, so `TraceBlock`, `FindingCard`, `ReviewThreadView` and the comment box render there on the page's styles. It only draws an annotation under a line. A trace entry belongs above the lines it explains, so it hangs under the row before (`rowAbove`, which differs between unified and split); line `0` is above the file, where a file's own trace entries and findings go. `VersionDiff` builds one annotation per line with everything on it.
  - **A comment starts from the gutter's button** (`onGutterUtilityClick`); dragging it over lines makes a range, which is what shift-click did.
  - **It highlights with Shiki's JavaScript engine on the main thread** (`disableWorkerPool`, the library's default `shiki-js`): no worker, no WebAssembly, nothing for the page's policy to allow. Do not switch `preferredHighlighter` to `shiki-wasm` or `highlights`: both compile WebAssembly, which `script-src 'self'` refuses. Its grammars and themes are Shiki's whole bundle as lazy chunks, which is why a build has about a thousand asset files.
  - **Its colours are its themes'** (`pierre-light`, `pierre-dark`), placed on the page by `unsafeCSS`: black behind code in the dark scheme and the page's monospace stack. The tree takes the page's tokens through its `--trees-*-override` properties.
  - **The file's header is ours**, above the renderer's element (`disableFileHeader`), so it can hold controls and stick under the shell's bar: `--review-sticky-top` on `.review-page` (`globals.css`) is how far down a sticky row stops, 3rem for today's bar.
  - **Tests**: jsdom has no `ResizeObserver` or `IntersectionObserver`, which both libraries use; `pages.test.tsx` stubs them. Lines are in a shadow root, so a test reads annotations (ordinary children) and never a line's text.
- **The change is told before its code** (`Notes.tsx`, `ReviewNotes`). Above the files, as cards: doubts then decisions (marked down the side, `.diff-note[data-kind]`), the findings seen on the version, the review threads on lines of the diff, then the rest of the trace in the order it was recorded. A card names each file it is about as `path:101` or `path:97-103` (`whereLabel`), and that label opens the file at those lines (`jump` in `VersionDiff`: it reveals the lines, then scrolls to the note where it hangs in the diff, `diffNoteId`, or to the line's row inside the renderer's shadow root). A file the diff does not have is linked to its blob instead. The Findings panel under the diff is unchanged and lists every finding of the branch, so a finding seen on the version shows in both.
- **Every note hangs in its file; `needsCode` only decides its card.** A trace entry or a finding with a file hangs on its lines in the file's diff (or at the file's top without lines), whatever the flag. With `needsCode` its card above also shows the lines it is about under its text (`excerptOf`, drawn by `DiffExcerpt` from the same lazy chunk as the diff, at most `EXCERPT_ROWS`); without it the card is text. The server decides the default when it is written. Review threads always hang on their lines.
- **Every file starts closed**, and what is open is the page's (`DiffViewState` in `BranchPage`, so a change of version, comparison or layout keeps it; it is not stored). `review/diff/focus.ts` is the pure part and is tested:
  - **Order** (`orderFiles`): open must-fix findings, then the trace's files in the order it first names them, then other files with a finding or a thread, then the rest by path. It sorts the files loaded so far (the diff still pages in 30 at a time). A file the reader starts a comment on keeps its place (`held`), so their own comment landing does not move it from under them.
  - **Focus** (`focusFile`): an open file with notes draws only the rows they are about and `FOCUS_CONTEXT` rows around each. Rows are cut as a side-by-side view pairs them (the nth removed line of a change with its nth added one), so a window never separates a line from what replaced it, and each window is a hunk of its own with its own start numbers, which `patchOf` writes as any hunk. Left-out rows with a change among them are a gap (`FocusGap`: "40 more changed lines", a button that adds the gap's lines to the file's `reveals`); left-out rows with none are just not drawn. When nothing changed would be left out, `focusFile` answers null and the file is drawn whole.
  - **Parts are separate renderers.** Each run of hunks between two gaps is its own `FileDiff` (`Lines`), with `hunkSeparators: "simple"` and no `loadDiffFiles`: the library's "N unmodified lines" and its expansion assume everything between two hunks is unchanged, which is not so around a gap. The whole diff ("Show full diff", or a file with no notes) is one `FileDiff` with both, as before. The library's custom separator is a deprecated DOM callback that its React component ignores, which is why the gap is ours and sits between renderers. What belongs above the file's first line (line `0`) is drawn by the section itself when the file is in parts.
  - **Commenting keeps what is open.** The comment box and the thread it becomes are marks, and every mark is in focus, so a window only grows. A file with no notes is shown whole; starting a comment on it sets `full`, or the box opening would cut the file down to itself.
  - `#diff-<path>` in the address opens that file once; the tree's pick opens and scrolls. The tree marks a file with notes with a dot (`marked`), red for a must-fix.
- **`DiffView` has `renderBeforeLine`** from the branch page's first version; nothing uses it now. `ReviewThreadView` names a thread's version and what answered it and offers "Send to agent"; `MergeBox` draws `mergeability.findings` with the administrator's override.
- **What a server may not serve yet is left out, not an error.** Queries for traces, findings, instructions and T3 Code go through `optional()` (`review/optional.ts`); a 503 `not_implemented` hides that section (`isUnavailable`).
- **It asks again every four seconds only while something is at work** (`isLive`: an agent working, an instruction out, a review run queued or running). `versions.branchState` is the one polled; when what it says changes, the versions, trace, findings, instructions and the page are refetched once.
- **Other pages**: `repo-settings/ReviewSettingsPage.tsx` (`/settings/review`: review agents and reviewers; there is no switch for pages, every branch has one). `McpSetup` (`Agent.tsx`, `MCP_CLIENTS`) is how each client installs the forge's MCP server: Claude Code's command, Codex's two and Cursor's `mcp.json`, each with a copy button. Settings > T3 Code (`paths.settings("t3")`) is linked from Start work and is another page's to build.
- **Start work offers T3 Code and Another agent** (`StartWorkPage`), the agent first. T3 Code is the default and shows what the forge needs to start the thread: the environment, the ask, the base and the branch name. Another agent hides all of that, the submit button included, and shows `McpSetup` and one line: that agent makes the branch and its page itself with `start_work`. A server without T3 Code (`isUnavailable`) leaves that one choice. The app's own agent sessions are not offered: a session provisions a new VM and nothing else, and the page did nothing for it but link out. `agents.startWork` still takes `kind: "infrawrench"`, a page such a session writes still names it with "Open in Infrawrench", and the app still starts one from `/agents?git=&branch=`.
- **Findings are listed whenever there are any** (`showsFindings`). `reviewAgentsEnabled` says whether the forge's own agents run, not whether anything was found: a reviewer outside the forge reports all the same. The setting only takes away "Review again", which asks for the forge's run. Each finding in the list has an address (`#finding-<id>`), which is what the code pages link to; the list opens that one and scrolls to it.
- **A pruned version stays in the strip** (`prunedAt`): marked, with its counts and its trace. `versions.diff` answering 422 `version_pruned` is not an error on the page: the diff's place says the commits are no longer kept (`prunedNotice`), links the commit the branch was merged as, and lists what was recorded for that version. A diff that came back with `source: "merge"` is the whole change read from the merge, and says so above the files.
- **The record on the code pages** (`features/code/ReviewHistory.tsx`, `review-history.ts`). `CommitPage` asks `contents.commitReview` after the commit and shows a Review section when the commit is what a branch page was merged as. `BlobPage` and `BlamePage` ask `contents.pathReview` once for the file and show a closed "Review history" disclosure; the blame also marks lines (`CodeView`'s `marker` column: a dot on the first line a finding was about, a rule down the rest, severity and how it was settled as the tooltip). `placeOnBlame` is pure and tested, and never guesses: what it cannot match to a blame range is counted on the file's header, and that count opens the disclosure. All three go through `optional()`, so a server without the endpoints shows the pages as they were.
- **The mock** (`mock/review-data.ts`, `mock/handlers/review.ts`): `acme/infra` `feature/flow-logs` was merged six weeks ago with a merge commit and has two pruned versions, a trace and a finding in every state a merge leaves one, reported by `claude-review`; `acme/edge-router` `feature/health-checks` has that reviewer's findings in a repository whose review agents are off. `acme/infra` `feature/vpc-peering` has three versions (the second forced, v1 to v3 answered as not exact), a trace, findings of every severity and state, and answered instructions; its last version adds more to `modules/network/main.tf` than its notes are about, so that file opens in parts with a gap, and one of its doubts is recorded with `needsCode: false`; `fix/database-backups` has a T3 Code agent at work. An instruction sent to a branch with an agent is delivered after 3 seconds and answered by a new version after 11, and starting work with an agent pushes v1 the same way. `features/review/__tests__/pages.test.tsx` drives the pages through the real router against these handlers.

`lib/` gained `ansi.ts` (SGR sequences to spans), `amounts.ts` (`formatDuration`, `durationBetween`, `formatMoney`, `formatMoneyDelta`) and `cursor.ts` (`cursorQuery(cursor)`: spread it into a page request's `query`, since a query's keys are optional rather than possibly undefined).

## Decisions

- **A document is asked for as text.** `api.terraform.downloadStateVersion` resolves with the state file exactly as the server sent it: `client.ts` lists the endpoints whose success is a document (`TEXT_ENDPOINTS`) and the transport skips `JSON.parse` for them, since parsing and printing a state again changes it. A mock handler for one answers a string.
- **Forms ask before they submit.** `lib/name-availability.ts` (`useNewNameAvailability`, `useRenameAvailability`, the pure `deriveNameAvailability`) is the one place a repository name is checked while typed: the name rules locally, then the API's answer for the settled name. A check that fails leaves the decision to the submit. `lib/owners.ts` (`ownersOf`, `visibilityFor`) reads from the session where the person can create and what each namespace takes: its default visibility, and the quota's own sentence when one more private repository does not fit, which the form shows on the choice it rules out.
- **A head in a fork is `owner/name:ref`** in the compare URL (`lib/refs.ts`: `parseHead`, `formatHead`, `headQuery`), as it is in a branch key. A ref name has no colon, so nothing else needs escaping, and a head in the base repository stays bare. `HeadRepoPicker` offers the base repository and its forks; a fork's "Forked from" line links to the parent's compare page with the fork's default branch as the head (`paths.compareHead`, which leaves the base to the parent's default branch).
- **Approving follows the API, not the viewer's access.** The Approve button shows on `run.viewerCanApprove`, which also covers `ci:approve` in the organisation; `canRunPlan` (a plan by hand) is `write` on an organisation's repository, since a personal namespace answers `terraform_unavailable`.

- **Refs in URLs keep their slashes** (`/tree/feature/x/src/a.ts`), resolved against the repository's refs the way the worker resolves raw paths: a full commit id first, then the longest prefix that names a branch or tag, then the first segment (`lib/refs.ts`, tested). Compare URLs are `/compare/base...head`; a ref name cannot contain `..`, so the first `...` splits them.
- **The client has no Effect in it.** `routes.gen.ts` is the contract's method and path per endpoint, generated and held in step by a test, and the types come from the contract as `import type`. The contract package is `sideEffects: false`, so importing `names.ts` and `urls.ts` functions pulls in nothing else.
- **`AppLink` over typed routes.** Links take an `href` from `paths.ts`. Typed `to` props would need the splat routes' refs and paths encoded at every call site.
- **Diff context expands in the browser**: the view fetches the new side's blob once and fills the gaps between hunks itself, rather than asking for the diff again with more context.
- **Syntax highlighting is Shiki's core with the JavaScript regex engine**, no WebAssembly, one chunk per grammar. Tokens carry both themes' colours and CSS picks by colour scheme.

## What comes from a repository is text (after the security review)

Everything a user can write reaches the page as React text; there is no HTML sink in `src/` and raw HTML in Markdown is never rendered. The rules that keep it so:

- **Every URL from data goes through `lib/safe-url.ts`.** Links may be same-origin or `http(s)` (`mailto:` in Markdown); images same-origin or `http(s)`, and `imageSrc` sends an image from another site through the Worker's image proxy (`/-/image?url=`). Every `<img>` with a `src` from data uses `imageSrc`: the page's policy is `img-src 'self'`, so one that does not shows nothing. `AppLink` applies it to every `href`, and an address that fails renders without a link.
- **Markdown has limits** (`lib/markdown-limits.ts`): over 500 000 characters, or nested deeper than 48 levels, shows as plain text; a table that would pad to over 20 000 cells shows as its source; a render that throws falls back to plain text. One comment of 20 000 `>` used to end the page for everyone who opened it.
- **Images from other sites are fetched by the Worker** (`worker/src/images/proxy.ts`), so their host sees Cloudflare and never the reader. Relative images in a README resolve to raw files on this site. In mock mode (`VITE_GIT_MOCK=1`) there is no Worker, so `imageSrc` leaves the address as it is.
- **Bidirectional overrides and isolates are written out** (`lib/bidi.ts`, `<U+202E>`) in code, diffs, file names, breadcrumbs and commit summaries; ordinary right-to-left text is untouched.
- **ANSI logs** keep colours from the fixed map and drop every OSC, DCS, APC, PM and SOS string (terminated or not), the one-byte C1 forms and other control characters.
- **A new token's secret is not kept in the query cache** (`gcTime: 0`); it lives in the panel that shows it once.
- The mock is a build-time constant (`VITE_GIT_MOCK`); nothing at run time turns it on.
