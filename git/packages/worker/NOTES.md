# @infrawrench/git-worker

Notes per area. Settled decisions move up into `git/README.md` and KNOWLEDGE.md.

## Bindings and configuration (`src/env.ts`, `wrangler.jsonc`)

- **A cron trigger** (`triggers.crons`, hourly) runs `scheduled` in `src/index.ts`: pruning versions (`review/prune.ts`), and sending again or failing review runs nothing finished (`review/queue.ts` `sweepReviewRuns`).
- **Two queues, one `queue` handler.** `EVENTS` (`infrawrench-git-events`) is pushes; `REVIEWS` (`infrawrench-git-reviews`, optional in `Env`) is review runs, one a batch. `src/index.ts` tells them apart by `batch.queue`. The review agents' model is reached with `CLOUDFLARE_ACCOUNT_ID`, `AI_GATEWAY_ID` and `AI_GATEWAY_TOKEN` (optional secrets, the app's own values; server-core's `anthropic-client.ts` reads them from `process.env`).
- `Env` is the one type for bindings and secrets: `HYPERDRIVE`, `OBJECTS` (R2), `REPO` and `TERRAFORM_STATE` (Durable Object namespaces), `EVENTS` (queue producer, typed `Queue<GitEvent>`), and the secrets `WORKOS_API_KEY`, `WORKOS_CLIENT_ID`, `WORKOS_COOKIE_PASSWORD`, `SSH_HOST_KEY`, `GIT_JOB_TOKEN_KEY`, `ENCRYPTION_MASTER_KEY`. Variables: `SITE_ORIGIN`, `APP_ORIGIN`, `WORKOS_API_HOSTNAME`.
- **Both Durable Objects are bound**: `REPO` (`RepoDO`, migration `v1`) and `TERRAFORM_STATE` (`TerraformStateDO`, migration `v2`), both SQLite classes exported from `src/index.ts`. A class is created by the migration tag that first names it: a deployed tag is never edited, a new class gets a new tag. The queue consumer is on: `src/index.ts` has the `queue` handler.
- **`ASSETS`** is the built UI (`../web/dist`), with `run_worker_first` so every request reaches the Worker and `not_found_handling: "single-page-application"` so a path with no file is the SPA's shell.

- **There is a `define` and no `alias` map.** `__INFRAWRENCH_EDGE_PLUGINS__` says the bundle has no plugin code. The Worker calls the app's CI (`server-core/src/ci/`), whose dispatcher could reach the plugin loader and the socket drivers through the code that lends connections; with the constant defined that code is dropped at build time (`ci/runs.ts` `lendingCode`) and a run that lends something is left to the app's gateway. So nothing that cannot run in a Worker is reached, and there is no copy of the app's alias map here to drift from `server-core/edge/gateway-only-modules.json`. `src/__tests__/import-graph.test.ts` bundles the Worker and fails when that stops being true. `wrangler deploy --dry-run` bundles 3.4 MB, 0.7 MB gzipped (November 2026; 9.0 MB and 1.8 MB with the loader). `README.md` has the bindings, variables and secrets.
- **`SSH_HOST`** is the host of SSH clone URLs (`sshHost(env)`, used by `api/views/repositories.ts`) and the name the Spectrum application is created under (`infra/git/setup.mjs` reads it from `wrangler.jsonc`). With a port (`localhost:8788`, local development) the contract's `sshCloneUrl` writes an `ssh://` URL.
- **CI needs the app's `CI_PROXY_URL`, `CI_PROXY_KEY` and `APP_URL`** as this Worker's secrets too (server-core reads them from `process.env`). Without them a push records its run and the dispatch waits for the app's poller, and a run's output and live log are not served here.

- **`webcrypto_modern_algorithms`** is in `compatibility_flags` for the SSH server's post-quantum key exchange (ML-KEM), which current OpenSSH clients warn without.
- `GitPushEvent` in `env.ts` is the queue's message, as the README describes it, plus `forced` per update. `principalActor(principal)` builds its `actor`.
- **`tsconfig.json` lists the `DOM` lib** next to `ES2022`: the SSH package's sources name WebCrypto's types (`CryptoKey`), and they are typechecked from here. It also includes `test/`.
- **`cloudflare:workers` is declared in `src/cloudflare-workers.d.ts`**: the importable flavour of the types has the module's contents (`CloudflareWorkersModule`) but not the module.
- **`tsconfig.json` no longer sets `types`.** The scaffold listed `@cloudflare/workers-types/index` there, which is the global flavour, and with it server-core's sources do not typecheck (its `Buffer` loses Node's methods). Like the other Workers, this package gets Node's globals from the base config and imports Cloudflare's types by name from `@cloudflare/workers-types/index`. `src/index.ts` lost its `satisfies ExportedHandler` for the same reason (Node's `Response` is not Cloudflare's); type the handler's parameters from the import instead.
- **`drizzle-orm` is a dependency of this package** (the query modules need its operators). pnpm does not hoist it from server-core.
- `ENCRYPTION_MASTER_KEY` is the app's own master key and is only needed to check `iwk_` API keys (their stored hash is an HMAC under a key derived from it). Server-core reads it from `process.env`, which `nodejs_compat` fills from the Worker's bindings. If sharing that key with this Worker is not wanted, drop `iwk_` support here (`db/organizations.ts` `verifyApiKey`) rather than work around it.
- These are a separate Worker's secrets (`wrangler secret put`), not part of `infra/terraform`'s `app_env`.

## Auth (`src/auth/`)

### Principals

`Principal` (`principal.ts`) is who a request, an SSH session or a job acts as:

| Kind         | Proven by                               | Reach                                                            |
| ------------ | --------------------------------------- | ---------------------------------------------------------------- |
| `anonymous`  | nothing                                 | Public repositories, read.                                       |
| `user`       | `session` cookie, `token`, or `ssh-key` | What the person may do; a token is capped by its scopes.         |
| `api-key`    | `iwk_` key                              | Its organisation's repositories, with the key's own permissions. |
| `deploy-key` | an SSH key in `git_deploy_keys`         | One repository, read or write.                                   |
| `job`        | `iwj_` token                            | One repository, read or write, until it expires.                 |

`toCaller` projects a principal onto the contract's `Caller`. Only a `user` has a `userId` there: an API key's owner is kept for audit (`principalActor`) and never widens what the key may do.

### `repoAccess`

`repoAccess(principal, repo)` (`repo-access.ts`) answers `none | read | triage | write | admin` and is the only place access is decided. `access.ts` holds the rules as a pure function (`decideRepoAccess`) over two facts from Postgres: the person's permissions in the owning organisation and their collaborator role. The rules, in order:

1. In its own right: a person is `admin` on their own namespace's repositories; `git:admin`, `git:write` and `git:read` in the owning organisation give `admin`, `write` and `read`; a collaborator role gives its level; the highest wins. An API key gets what its permissions give, in its own organisation only. A deploy key and a job token get `read` or `write` on their one repository.
2. A personal access token is capped by its scopes: `repo:write` at `write`, `repo:read` at `read`, neither at `none`. A token never reaches `admin`.
3. A public repository is readable by every principal: at least `read`.
4. An archived repository is read-only for every principal: at most `read`.

`repoAccess.detail(principal, repo)` also answers `unarchived`, the level before step 4. The API middleware uses it for endpoints the contract annotates `AllowedWhenArchived` (settings reads, unarchive, delete). Nothing else should read it.

Other things to know:

- **Break-glass grants reach a session and nothing else.** `loadRepoAccessFacts` asks for permissions with `withElevation: true` only when `via` is `session`. A token or an SSH key gets the role alone, as API keys do in the app.
- **A request that presents a credential we refuse is a 401, not anonymous.** `authenticateRequest` answers `refused: true`. For Git over HTTPS, send `WWW-Authenticate: ${BASIC_CHALLENGE}` with it, and also with the 401 an anonymous caller gets for a private repository, so `git` asks for credentials. For the API, a private repository the caller cannot read is a 404.
- **Private repositories and the plan.** `repoAccess` does not look at the organisation's plan (`planAccess`). Creating a private repository is where that is checked.
- `accessFromPermissions` uses the app's own `hasPermission` (`@infrawrench/server-core/permissions/catalog`), so wildcards mean what they mean there.

### Sign-in (WorkOS AuthKit)

The same WorkOS client and the same `users` rows as the app; this host's own redirect URI, cookie and cookie password.

1. `GET /auth/sign-in?returnTo=` (`handleSignIn`): sets a ten-minute nonce cookie and redirects to `user_management/authorize` with `provider=authkit` and a sealed `state` holding the nonce and `returnTo`. `returnTo` must be a path on this site (`safeReturnTo`).
2. `GET /auth/callback` (`handleCallback`): the state must unseal and its nonce must match the cookie; then `POST user_management/authenticate` (`grant_type=authorization_code`, `client_secret` is the API key); then `provision`; then the session cookie; then a redirect to `returnTo`. Failures land on `/?auth_error=denied|state|exchange`.
3. Each request (`authenticateRequest` > `authenticateSession`): unseal the cookie, verify the access token (RS256 against `/sso/jwks/<clientId>`, cached per isolate). When it has expired, exchange the refresh token (`grant_type=refresh_token`), provision again, and return a `Set-Cookie` in `setCookies`. **The caller must put `setCookies` on the response**: WorkOS rotates the refresh token, and the old one is dead.
4. `POST /auth/sign-out` (`handleSignOut`), and `signOut` for the API's `session.signOut`: clears the cookie and redirects to WorkOS's `sessions/logout`, which returns to the site.

Decisions:

- **REST, not the SDK.** `@workos-inc/node` does run on Workers (it ships an `index.worker` build and the web edge Worker loads it). This worker makes the same four calls with `fetch` (`workos.ts`) and verifies JWTs with WebCrypto (`jwt.ts`), so the bundle carries no SDK, no `jose` and no iron-sealed session. The request shapes were read from `@workos-inc/node` 8.13.
- **The cookie is our own format** (`session-cookie.ts`): `v1.<salt>.<iv>.<ciphertext>`, AES-256-GCM under an HKDF-SHA256 key from `WORKOS_COOKIE_PASSWORD` and a per-cookie salt, with the header bound as additional data. It is not interchangeable with the app's `wos-session`, on purpose.
- **Host-only.** No `Domain` attribute, and the name is `__Host-iwg-session` over HTTPS (browsers then refuse it with a `Domain` or without `Secure`). Over plain HTTP in development it is `iwg-session`. `SameSite=Lax`, `HttpOnly`, 400 days like the app's.
- **No `aud` or `iss` check on the access token**, for the reasons KNOWLEDGE.md gives for the app. The key set is per client, which is the isolation.
- **A refused refresh does not clear the cookie** (`stale`). Refresh tokens are single use, so of two requests racing to refresh, the loser is refused; clearing the cookie on its response could delete the session the winner just set. The loser's request is anonymous and the next one carries the new cookie. A cookie that does not unseal (`garbage`) is cleared.
- **WorkOS being down is an error, not a sign-out.** A 5xx or a network failure on refresh throws; only a 4xx ends the session.
- **Writes that ride on the cookie must come from this origin** (`isSameOrigin`, `writeOrigin`): a write must carry our `Origin` or `Sec-Fetch-Site: same-origin`. One that carries neither is refused when it rides on the cookie (git, Terraform and CI send neither and bring a token). One that says it came from elsewhere, a sibling `*.infrawrench.com` host included (`same-site`), is a 401 whatever credential it carries. `SameSite=Lax` does not cover the sibling host; this does.
- **Provisioning is the app's statement** (`db/users.ts` `provisionUser`): insert `id`, `email` and a display name from first and last name, do nothing on conflict. It runs at sign-in and at each refresh, not on every request (the app runs it on every request; a row cannot vanish in between). `provisionSignedInUser` also upserts `git_users`, whose null `onboardedAt` is the "needs a username" state.
- **WorkOS bearer tokens are not accepted** on this site. The API takes the cookie, `iwg_` and `iwk_`, and `iwj_` on the commit status and trace endpoints only. An MCP client that signs in with OAuth gets an `iwg_` token from this site's own authorization server ("MCP and OAuth" below), not a WorkOS one. If a CLI ever signs in to WorkOS with PKCE, `jwt.ts` already verifies its token; `authenticate.ts` needs a branch.

### Tokens

- **Personal access tokens** (`tokens.ts`, `db/tokens.ts`): `iwg_` and 32 random bytes in base64url. Only the SHA-256 is stored. A presented token is hashed, looked up by the hash, and the stored hash compared again in constant time. Unknown, revoked and expired are one answer. `mintAccessToken()` returns the secret to show once.
- **CI job tokens** (`job-token.ts`): `iwj_<claims>.<HMAC-SHA256>` under `GIT_JOB_TOKEN_KEY`, stateless. Claims: repository id, write or not, run id, expiry, and optionally a commit or a Terraform workspace. Default lifetime one hour, at most six (client-core `git-job-token.ts` owns the format; `job-token.ts` here only maps its claims). They cannot be revoked one at a time; rotating the key revokes all. The MAC is checked before the claims are parsed. `server-core/src/ci/` mints these when it dispatches a run from a repository here, with the same key. A token with a commit is good for that commit's archive alone, and one with a workspace for that workspace's state and plans alone: `authenticateRequest` refuses the second everywhere unless the caller says it serves workspaces (`workspaceTokens`, which only `terraform/directory-db.ts` does), so it is a 401 on smart HTTP, the raw and archive routes and the API, and `repoAccess` gives such a principal nothing of the repository even if one were made.
- **Basic auth** (`credentials.ts`): the username is ignored. The password is the credential; when the password is not one of ours the username is tried (`https://<token>@host/`). The prefix decides the kind.
- **API keys** (`db/organizations.ts` `verifyApiKey`): the app's own check, restated: keyed hash, not revoked, not expired, owner still a member, permissions are the scopes intersected with the owner's role. A key on the legacy SHA-256 hash is accepted until its sunset but not rehashed here.

### SSH

- `authenticateSshKey(key, { markUsed })` resolves an offered key to a `user` (via `ssh-key`) or `deploy-key` principal by fingerprint, and checks the stored blob equals the offered one. The SSH server calls its `authenticate` callback before and after the signature check: pass `markUsed: true` only the second time.
- `ssh-keys.ts` parses a pasted `.pub` line and computes `SHA256:` fingerprints. Accepted: `ssh-ed25519`, `ecdsa-sha2-nistp256/384/521`, `ssh-rsa` of 2048 bits or more. The algorithm the line names must be the one inside the blob.
- A key names one principal. `git_user_keys` and `git_deploy_keys` each have a unique fingerprint index; `db/keys.ts` checks the other table in the inserting transaction.

## Data access (`src/db/`)

- **`withDb(env, ctx, fn)`** (`client.ts`) wraps one invocation's work. It is server-core's `withEdgeInvocation`: a postgres.js client over Hyperdrive made with `createDb`, closed after everything handed to `keepAlive` settles. Inside it, the `db` that server-core exports is this invocation's handle, so the modules here import `db` and use it, and nothing holds a connection between requests. Calling a query module outside `withDb` throws (there is no pool to fall back to). A Durable Object needs its own `withDb` per request or alarm.
- **Fire-and-forget writes are `void keepAlive(...)`** (`touchKey`, `touchAccessToken`, `touchApiKey`).
- **Only light server-core modules are imported**: `db/client`, `db/schema`, `runtime/*`, `encryption`, `permissions/catalog`, `permissions/system-roles`. `@infrawrench/server-core/permissions` (the resolver) is deliberately not: it reaches break-glass's notification code and through it `ssh2` and its native addons, which does not bundle for a Worker. `db/org-permissions.ts` restates the resolver's rule (role permissions, legacy role fallback, live grants) as a pure function, and `db/organizations.ts` reads its rows. If the app changes what a role or a grant means, change that file too. The better fix is a server-core resolver module with no notification imports; then this one goes away.
- Modules, one per table group: `users`, `namespaces`, `repositories` (and stars), `collaborators`, `keys`, `tokens`, `organizations`, `threads` (issues, comments, labels, assignees, milestones, timeline events), `pulls` (branch pages, which the storage keeps in `git_pull_requests`, their reviews and review comments), `branch-pages` (what names a page: its key), `policy` (protected branches, commit statuses), `repository-lists` (the list and search query), `automation` (CI runs as read here, Terraform workspaces, runs, state versions and managed resources). `policy-rules.ts` and `org-permissions.ts` are the parts with no database.
- **Conflicts come from the unique indexes**, never check-then-insert: claim, create and rename functions catch Postgres `23505` (`isUniqueViolation`) and answer null or a reason.
- **Counters move with their rows**: `next_number`, the open counts, `comments_count`, a milestone's counts, `stars_count` and `forks_count` each change in the transaction that changes what they count. `setThreadState` and `markMerged` answer null or false when the row was already in that state, so a race produces one change.
- **Lists are `(timestamp, id)` keyset pages** (`cursor.ts`), fetching `limit + 1`, with the timestamp compared to the millisecond (see "The JSON API"). `listThreads` also sorts by comment count and searches title and body; `repository-lists.ts` `searchRepositories` serves every repository list, with its own cursor per sort.
- `visibleTo(viewer)` is the SQL twin of `repoAccess >= read` for a whole page: public, own namespace, collaborator, or an organisation in `readableOrganizationIds`, which the caller resolves (the organisations where the viewer holds `git:read`).
- **Deleting a repository's row does not delete its objects.** R2 packs and the Durable Object are keyed by the id `deleteRepository` was given; the caller removes them. Deleting an account or an organisation in the app cascades to namespaces and repositories here, leaving objects only a sweep by id can find.

## Routing (`src/index.ts`, `src/http/`)

- `src/index.ts` is the composition root and nothing else: it wires `Routes` and loads the server code on first use (the API's layers and server-core's schema are not start-up work).
- `http/router.ts` `routeOf(pathname)` is the whole split, as a pure function: `/api` is the JSON API, the three `/auth` paths are sign-in, `/mcp` is the MCP server, the four `/oauth` paths are its authorization server and everything under `/.well-known` is their discovery (JSON, never the UI's shell), `/<owner>/<repo>.git/...`, `/<owner>/<repo>/raw/...`, `/<owner>/<repo>/archive/...` are the storage's, `/<owner>/<repo>/terraform/<workspace>/state...` and `/<owner>/<repo>/terraform/<workspace>/runs/<id>/plan` are Terraform's, and everything else is the UI. `/<owner>/<repo>/terraform` and `/terraform/<workspace>` are the UI's Infrastructure pages, not the state backend. `/-/image` is the image proxy, `/-/avatar/...` an organisation's uploaded picture ("Profiles and uploaded pictures" below) and `/-/og/...` the link preview images ("Link previews" below); a page of the UI goes through `Routes.page`, which puts its tags in.
- **The storage's and Terraform's routes are optional members of `Routes`** (`smartHttp`, `raw`, `archive`, `terraformState`, `terraformPlan`), each documented where it is declared. All are wired in `src/index.ts`; a build without one answers it 503 with `Retry-After`, never the UI's shell, so `git clone` and `terraform init` fail saying why. `connect()` for SSH and the Durable Object exports have their own marked places in `src/index.ts`.
- **`serve` puts the security headers and `X-Request-Id` on every response**, whatever produced it (`http/security-headers.ts`): `nosniff`, `X-Frame-Options: DENY`, a referrer policy, HSTS over HTTPS, and a CSP: the page's policy for HTML (scripts, fonts, images and requests from this origin only, an image from another site coming through `/-/image` (`images/proxy.ts`), `form-action` allowing WorkOS for sign-out, `frame-ancestors 'none'`) and `default-src 'none'` for everything that is data. A response that set its own CSP keeps it, which is what the raw route's `sandbox` needs. The request id is Cloudflare's ray id when there is one.
- A route that throws is logged with the path only (a query string can carry the archive route's token) and answered with a bare 500.

## Profiles and uploaded pictures (`api/handlers/session.ts`, `images/avatar.ts`)

- **A profile is its namespace's row**: `display_name`, `description` (the bio), `website_url`, `location`, `avatar_url`. `namespaces.update` writes the first four for whoever `namespaceView` calls `canAdminister`: the person themselves, or `git:admin` in the organisation, and only in a session (a token never reaches settings). The bio is at most `BIO_MAX_LENGTH` (280) characters by the contract's schema and is stored as typed; the UI shows it as text with its addresses linked.
- **Only an organisation uploads a picture** (`setAvatar`, `removeAvatar`). A person's `avatar_url` stays null and `namespaceAvatarUrl` falls back to `git_users.avatar_url`, the picture they signed in with; a personal upload is refused with a sentence that says where theirs comes from.
- **What a file is comes from its bytes** (contract `profile.ts` `inspectAvatar`): a PNG, JPEG or WebP by its signature and a header that parses, still (an `acTL` chunk or the VP8X animation flag refuses it), 1 MiB at most and 16 to 2048 pixels a side. The upload is base64 in the JSON body, capped by the schema at the base64 of 1 MiB; no content type is ever read from the sender. Nothing is re-encoded in the Worker: the UI draws the square it sends, and a client that skips that still passes the same check.
- **Stored at `avatars/<namespace id>/<32 hex of SHA-256>.<png|jpg|webp>`** in `OBJECTS`, and `avatar_url` is the path it is served at (contract `avatarPath`, `/-/avatar/<namespace id>/<name>`). The name is the content, so the answer is `immutable` for a year and a new picture is a new address; the one before it is deleted after the row moved (`deleteStoredAvatar`, which only ever deletes a path of that namespace's own).
- **Served by `serveAvatar`** to anyone, as a namespace's page is: `GET` and `HEAD`, the type its extension says, `nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`. Only a path `parseAvatarPath` accepts reaches the bucket, so nothing else in it (a pack, a Terraform state) can be named through this route. On this origin, so the page's `img-src 'self'` shows it without the proxy. Counted by address like the proxy (`http/admission.ts`), and in the dev server's proxy list.

## Link previews (`src/og/`)

What Slack, X, Discord, iMessage, LinkedIn and Bluesky show for a link to the site: Open Graph and Twitter tags in the page's HTML, and the image they name.

- **The privacy rule: a preview is what a signed-out visitor sees, whoever asks.** `og/lookup.ts` resolves the repository with `getRepository`, asks `repoAccess(ANONYMOUS, ...)` (the only place access is decided), and reads the one row the page is about. A private repository, a missing one, a namespace or page that is not there, a signed-in person's page (settings, new, start, the person's own lists) and any lookup that fails or takes longer than 1.5 s all get `genericMeta` and the site's card: the same bytes for a private thing as for a missing one, and the same for every such path (`og/__tests__/mount.test.ts`, `src/__tests__/db/og.test.ts`). The lookup never writes: a branch page is read with `resolveBranchKey`, not `branches.get`, which opens a page for a branch that has none.
- **Tags** (`og/meta.ts`, `og/shell.ts`). The UI's shell (`git/packages/web/index.html`) carries every tag with the site's own values, so a page served without the Worker's edits still says the right thing; `Routes.page` sets each value with `HTMLRewriter`'s `setAttribute` and `setInnerContent` as text, which escape what they are given. No HTML is written from data. The router hands `page` only a `GET` the asset layer answered `200` with HTML, asks for `index.html` without its conditionals (a `304` would keep another page's tags), and the rewritten shell drops its `ETag`. `og/__tests__/shell.test.ts` holds the shell and the edits together. A page's lookup is counted against the anonymous read budget at its address; past it the page loads with the site's tags.
- **Images** (`og/mount.ts` `ogImageFetch`, contract `ogImagePath`): `/-/og/<version><page path>`, for the home page, a namespace or bot, a repository, a commit, an issue and a branch page (every other page names its repository's card or the site's). `version` is 16 hex digits of a SHA-256 over what the card draws and `CARD_DESIGN`; the route draws what the page is now whatever version was asked for, and only the current one is kept a day by browsers and crawlers (`imageCacheControl`). Drawn PNGs are kept in the `og` cache by version for a week (an hour when a picture could not be fetched); facts for 120 s. `/-/og/` is counted by address like the image proxy, never authenticates, and is in the dev server's proxy list.
- **The renderer** (`og/card.ts`, `og/render.ts`, `og/assets.ts`): Satori lays out an element tree (no React) and turns text into paths, resvg draws the PNG (both MPL-2.0, used unmodified). Both are WebAssembly modules of the upload (`satori/yoga.wasm`, `@resvg/resvg-wasm/index_bg.wasm`, compiled by Cloudflare at deploy) and the fonts are `.woff` Data modules (`rules` in wrangler.jsonc): Inter 400, 600 and 700, Latin and Latin Extended, from `@fontsource/inter` 5.2.8 (SIL OFL 1.1, `og/fonts/OFL.txt`). Satori stays on 0.32: 0.33 and later shape text with `harfbuzzjs`, which fetches and compiles its WebAssembly at run time, which a Worker refuses (found under `wrangler dev`; the Node tests pass either way). The renderer is imported only by the image route; the script grew about 0.8 MB (`import-graph.test.ts`), the upload about 1 MB gzipped, and `wrangler check startup` moved from about 105 to 108 ms locally.
- **Pictures on a card** (`og/images.ts`): another site's avatar is fetched by the image proxy's address rules (`imageSource` at every redirect, public addresses only, nothing of anyone's sent), PNG, JPEG or GIF only, 1 MiB and 2.5 s at most, else the card shows initials. A bot's picture is read from the built UI (`/assets/...`), and an organisation's uploaded one from the bucket (`readStoredAvatar`; a WebP upload is not drawn, so that card shows initials).
- **Look at the cards**: `OG_CARDS_OUT=<dir> npx vitest run src/og/__tests__/render.test.ts` writes every card as a PNG.

## The JSON API (`src/api/`)

The contract's `GitApi` served by Effect `HttpApi`, the way the app's web server serves its domains.

- **`api/server.ts` `makeGitApi(options)`** builds one `fetch`-shaped handler: `HttpApiBuilder.layer(GitApi)` with every group's handlers (`HandlersLive`, which does not typecheck while a group lacks one) and the three middlewares, plus a JSON 404 for an `/api` path nothing routes. HEAD is the GET without its body, and the request is detached from the client's abort signal so a handler that has started a write finishes it. `options` replaces the authenticator, the reader factory and the middlewares, which is how tests run it.
- **Handlers are promise code** (`api/handlers/*.ts`, one file per subject): an `async` function per endpoint that calls the query modules and the `RepoReader`, returns the endpoint's success type and **refuses by throwing one of the contract's error classes**. `op` and `repoOp` (`api/context.ts`) wrap one as an Effect: they build its `Cx` (the caller, the repository in the path, `cx.git`, `cx.reader(other)`, `cx.viewer()`, `cx.background(promise)`) and run the whole handler as **one call inside the invocation's request scope**. That is the app's rule for AsyncLocalStorage and Effect (KNOWLEDGE.md): `db` resolves through an AsyncLocalStorage scope, Effect does not carry it, so Effect code here never touches `db` and everything that does goes through `inScope`.
- **The gates are the middlewares** (`api/middleware.ts`), enforced before a payload is decoded:
  - `Authentication`: a refused credential is a 401 whatever the endpoint; `RequiresUser` means a person (a session or a personal token); the `account` group is session only; `RequiredOrgPermission` is checked with the person's effective permissions (a session) or an API key's own; and **a signed-in person without a username can read and cannot write** (403 `username_required` on every non-GET outside the `session` group).
  - `RepositoryAccess`: missing and unreadable are the same 404; `RequiredAccess` is judged against the un-archived level where the endpoint is `AllowedWhenArchived`; and **an archived repository refuses every write that is not `AllowedWhenArchived`** (403 `repository_archived`), which is what stops the writes that only need `read` (a comment, a new issue). Starring and forking are the exceptions (`ARCHIVE_SAFE`).
  - They leave what handlers read on the fiber as `Context.Reference`s (`AuthRef`, `RepoRef`), so a handler needs no service the server would have to provide.
- **`RequestErrors`** (`api/errors.ts`) renders everything that refuses: the contract's classes as `{ error, code? }` with their status, declared on the endpoint or not; a schema failure as the 400 with its issues; a `RepoReaderError` by the table there (`unavailable` 503, `ref_not_found` and `path_not_found` 404, `not_a_file`, `not_a_directory`, `too_large` and `repository_empty` 422, `ref_exists` and `head_moved` 409, `invalid_ref` 400); anything else as a 500 with a correlation id and nothing of the error. A handler that wants another answer for a reader refusal catches it (`ref_not_found` for a ref named in a payload is a 422).
- **A refreshed session's cookie** is collected on the invocation and appended to the web `Response` by `handle`, one `Set-Cookie` header per line, so it is on refusals too.
- **Views** (`api/views/`) turn rows into the contract's shapes a page at a time: one lookup for the people, one for labels and assignees, one for milestones. `commitDecorator` adds what Postgres knows to a reader's commits (who each address is, the combined status). The namespace's kind picks the branch, so an organisation's address never counts in a person's repository, connected to that organisation or not, and a person's never counts in an organisation's or in someone else's). Two queries a page, run together, whatever the page's length. The `author=` filter of the commit list takes a bot's username as it takes a person's.

  - **A push moves a base.** The open pages on it whose head is in the same repository (a fork's branch is its owner's), at most `MAX_LANDED_HEADS` (100) of them, the most recently active first, in one call to the object: one session, so the base's history is read once. Open pages whose branch is already gone are measured too, which is how pages left open before deleting closed them are settled.
  - **A push deletes a page's branch.** Merged as above if the base has it, else closed (a page no longer stays open without its branch; restore the branch and reopen it). When the storage does not answer the page stays open for the next push to the base. Timeline entries are stamped from the push's time a millisecond apart (`stepOf`), since `listTimelineEvents` orders by the millisecond: merged, then branch deleted; or branch deleted, then closed.

## Events (`src/events/`)

- `events/consumer.ts` is the `infrawrench-git-events` consumer: one database client per batch, each message acked or retried on its own. ### Where things run

The front Worker authenticates, resolves the repository and its access, and loads the push policy. The Durable Object runs the protocol against its own storage. Between them is one internal `fetch` (`repoClient(...).serve`): a JSON header (`GitCall`: the `ServeRequest`, the actor, the policy), the client's bytes as the request body, the server's as the response body.

- **The Durable Object never opens Postgres.** Protected-branch rules travel with the push (`PushPolicy`) and are applied in the object (`policy.ts`), because only it knows whether an update is a fast-forward.
- **SSH needs both bodies open at once**, and gets it from the same `fetch`: the response starts (the ref advertisement) while the request body is still open, and the negotiation goes back and forth on the pair. Cloudflare's documentation does not promise full-duplex for a `fetch` to a Durable Object stub, nor for a stream passed to and returned from one RPC call. It works in workerd (`test/e2e` fetches with haves over SSH in protocol v0, which cannot work otherwise) and has to be confirmed in production before SSH is opened. If it does not hold there, the stub's `connect()` (a raw socket to the object, public beta) is the documented duplex, and `sshConnect` would hand `channel.stdin`/`stdout` to that instead; nothing else changes. Smart HTTP never needs duplex: each request is read, then answered.
- **The Worker runs beside Postgres, the repositories beside R2.** `placement` pins the Worker to `aws:us-east-2` (Neon), as the app's Workers are; from London every query was its own transatlantic round trip, 650 ms to 1.5 s for a page's list. The UI's hashed files and favicons skip the Worker (`run_worker_first` patterns) and carry the Worker's headers from `web/public/_headers`, which `static-headers.test.ts` holds equal. A repository's Durable Object is created with `locationHint: "enam"` (`REPO_LOCATION`), beside the bucket: an object created near its first visitor waited ~100 ms on every R2 read. A hint only counts when an object is created, so repositories made before it stay where they were. Whether `placement` applies to the `connect` handler (SSH through Spectrum) is to be seen when SSH opens.
- **A page shows before its history is walked.** The UI asks `tree` with `lastCommits=false` and `blob` with `lastCommit=false`, then `latestCommit` (a path's newest commit, and the count at the root) and `treeLastCommits` once the page is up, and prefetches a folder or file when the pointer rests on its link (`web/src/features/code/requests.ts`).
- **Smart HTTP carries both bodies through the Worker's own code** (`carried` in `transport/http/routes.ts`). Returning the object's response untouched ends the Worker's request at once, and the upload still flowing into the object then has Cloudflare's 30 seconds after a request ends before it is cancelled: a 32 MiB push the object took 63 seconds to read failed in production with "client disconnected". A body the Worker pipes itself keeps the request open until the answer is complete. `wrangler dev` does not apply the 30 seconds. **The pipe reads in large pieces** (`bigReads`, `repo/do/big-reads.ts`): read the ordinary way, the runtime hands its own streams to JavaScript 4 096 bytes a read, so a 45 MiB pack crossed the Worker in 11 500 turns of the event loop, which is the 1.4 MiB/s of #1447 ("What a fetch costs", below). A push's upload waits for 256 KiB at a time (`readAtLeast`); an answer is passed on as it arrives, because it carries keep-alive packets.
- **A push over HTTPS is stored before it is indexed** (`IngestOptions.whole`, `ingest.ts`). Indexing (inflating, hashing with the collision-detecting SHA-1, resolving deltas) runs well below the network's pace, and a client held back by it for about a minute has its connection reset by Cloudflare's edge: an 88 MiB push failed that way (git's `HTTP/2 stream was not closed cleanly: INTERNAL_ERROR`). So the request's bytes go to R2 as fast as they come (three 5 MiB parts in flight), and the indexer then reads the stored pack back. Over SSH the stream stays open after the pack and only parsing finds its end, so SSH still indexes as it receives. Once the pack is in, receive-pack sends git's keepalive (an empty data-band packet, `receive.keepAlive`) every five seconds until it answers (`ServeLimits.keepAliveMs`).
- **Backpressure is the streams' own** in both directions: a slow client slows the pack writer, a slow R2 upload slows the client's push.

### `RepoDO` storage

SQLite holds four small tables: `refs` (name, id, and what a tag peels to), `packs` (the catalogue), `meta` (`repo_id`, `head`, `ready`) and `reader_cache` (answers the reader walked history for; "The reader"). Packs are `repos/<repoId>/packs/pack-<id>.pack` with `pack-<id>.idx` beside each. The id is time-ordered and random, not the pack's checksum (the README said checksum): the key has to exist before the first byte is uploaded, and R2's binding cannot rename or copy.

**No row per object.** An object is found through each pack's `.idx`, held in memory while the object is awake. The numbers that decided it:

|                       | A row per object in SQLite                               | `.idx` in R2, in memory                     |
| --------------------- | -------------------------------------------------------- | ------------------------------------------- |
| A push of 93 000 objs | 93 000 billed row writes (about $0.09), again per repack | 13 row writes, one extra R2 put             |
| A million objects     | about 70 MB of the object's 10 GB, $1 a write pass       | 28 MB in R2, 28 MB of memory while awake    |
| Lookup                | One indexed read                                         | A binary search per pack, in memory         |
| Waking up             | Nothing to load                                          | One R2 get per pack (2.5 MiB for this repo) |

The price is memory: every live pack's index is loaded (28 bytes an object, plus 12 once a fetch needs entry lengths), so a repository of a few million objects no longer fits. Paging indexes by range (the fan-out table makes a lookup one range read) is the way past that, and is not built.

**An object in several packs is read from the oldest** (`PackStore.locate`). A delta's base was in its own pack or already in the repository when the pack arrived, so with that rule every chain of deltas across packs leads to older packs and cannot loop. It is also why a repack merges a run of adjacent packs and gives the result the first one's place.

**No push lock.** A push writes its pack under its own key and touches nothing shared until `updateRefs`, which publishes the pack and moves the refs in one synchronous SQLite transaction (`transactionSync`). Each ref is compared with what the client saw, so of two pushes racing for a branch one wins and the other gets `stale info`. A pack is `incoming` until then: readable only by the push that brought it, deleted if no ref moves, and swept by the alarm after a day if the push never finished.

**Receiving** (`ingest.ts`): bytes go to an R2 multipart upload in 5 MiB parts (R2's minimum, and every part but the last must be the same size) while `PackIndexer` reads them. A pack smaller than one part is a plain `put`, and stays in memory for the checks that follow. After the upload completes the indexer's second pass reads back what it must by range. Then every object's references are checked against the pack and the repository (`ConnectivityCheck`; the protocol's notes say why every object and not only the new tips), the `.idx` is written, and the pack waits for `updateRefs`. Any failure aborts the upload and removes the files and the row.

**Sending** (`pack-stream.ts`):

- A full clone of a repository that is one self-contained pack is that pack, read from R2 as 4 MiB ranges with three in flight (`streamWhole`) and sent as it is.
- A full clone of several packs is every entry of every pack, once, in file order, copied as stored. Nothing is inflated and no history is walked.
- Anything else (a fetch with haves, a shallow clone, a single branch) walks history in the protocol and sends the chosen objects' stored entries. Only an `ofs-delta` header is rewritten. A delta whose base is not going out and that the client is not known to have is the one case read whole and compressed again.
- **The bucket is read by a plan, not as it comes** (`generate`). The chosen entries are laid out in file order and read as runs: neighbours less than 64 KiB apart share one range request of at most 4 MiB, up to eight requests (12 MiB) are in flight or waiting for the writer, and nothing that is not going out is read but the gaps between neighbours. An entry over 4 MiB is read a piece at a time with two pieces ahead. The plan is made as it is used, so a clone of half a million objects holds no list of runs.
- **Deltas that must be rebuilt are found ahead of the writer**: the next 128 entries are looked at as soon as their run has arrived, and those to rebuild are read and compressed while earlier entries go out, within 4 MiB of objects at a time (512 KiB each; a larger one waits its turn). In a repository that grew by pushes, the newest version of a changed file is a delta on an older one, so a shallow fetch rebuilds one object in six.
- **The stored packs go out only while every stored object is known to be reachable from a branch or a tag** (`meta.unreachable`, `Repository.everythingReachable`). Creating a ref and moving a branch forward keep that true when everything the pack brought hangs off the new tips. A forced update, a deletion, objects the server wrote, an import from a fork and a fork's copy do not, and the next full clone walks history once to find out; the answer is kept until refs or packs change. A repository that does hold leftovers (branch pages from forks, a forced push) is walked by every full clone, as git does. Leftovers stay stored until a pruning repack exists; they are no longer served.

**Repacking** runs from the alarm when there are more than 12 live packs: the newest run of packs under 256 MiB (at most 1 GiB, at most 500 000 objects) is streamed into one new pack through the same ingest path, so the result is indexed and verified like a push. The catalogue switches in one transaction; the old files are deleted after 24 hours, for a clone still streaming them. It merges and does not prune: unreachable objects stay.

**Forks copy** (`importFork`): the parent's live packs and indexes are copied R2 to R2 under the fork's prefix, with its branches and tags (not `refs/pull/*`). Sharing the parent's packs instead would make every repack and delete of the parent depend on its forks (reference counts across Durable Objects, with no transaction to keep them right), and bill a parent's storage to whoever was forked from. The copy runs through the object (the binding has no server-side copy), which is a pass of R2 traffic and no egress.

**Deleting** (`destroy`): every key under `repos/<repoId>/`, then `deleteAll`. The object is empty and can be reused.

**Size** (`stats().sizeBytes`): bytes of live packs and indexes plus what is waiting to be deleted or still arriving. That is what R2 holds and what `git_repositories.size_bytes` should be set from.

### What a fetch costs (#1447)

A one-commit shallow fetch of a copy of this repository (14 000 objects, 45 MiB) took 40 seconds from production: 8 choosing objects, then 32 for the pack at 1.4 MiB/s. Locally it was two. Nothing was slow that a local run could show; four things were, in production:

1. **The pack crossed the Worker 4 096 bytes at a time.** `carried` was an identity `TransformStream`, and a stream the runtime owns gives JavaScript 4 096 bytes a read however much is waiting (measured in workerd: 10 250 chunks for a 42 MiB pack, 44 with `bigReads`). A turn of the event loop is tens of microseconds here and milliseconds in production. The same was true of the object reading a push's body, and of it reading a stored pack back to index it or to send it.
2. **Every read of R2 waited for the one before.** The issue's 8 seconds of choosing were 136 block reads, one at a time, 59 ms each. The walk now reads 32 trees at once (`TREES_AT_ONCE` in the protocol) through one block cache the repository's packs share (`newBlockCache`: 256 KiB blocks, 12 MiB, two blocks read ahead when reads march forward), in which reads that miss the same block wait for one fetch.
3. **A shallow client was sent everything again.** A runner that had the last commit and asked for the next at depth 1 got every file of it, because the walk found no edge (the protocol's notes, `shallowEdges`). That is every pipeline read after a runner's first, and why the issue saw 40 seconds on every new commit and not once.
4. **Nothing was remembered between fetches.** Commits, trees and tags of the live packs are now kept by id while the object is awake (`PackStore.read`, 6 MiB, apart from the cache that fetches fill with rebuilt files), and a push reads the trees of the branches it moved while it is being answered (`Repository.warm`), so the fetch CI makes a moment later reads none.

`test/pack-bench.test.ts` runs the storage code on Node over a bucket whose reads cost what R2's do (`test/support/slow-bucket.ts`), with a repository object that has just woken. A read costs 55 ms before its first byte, then 60 MiB/s, which is what the issue's own walk works out to. This repository: its newest tree as one commit (14 028 objects, 45 MiB), and the history of one branch (100 011 objects, 81 MiB, one pack as git wrote it).

### The reader

`RepoReader` (`repo/reader.ts`) is implemented once, in `repo/queries/`, against `Repository` and `@infrawrench/git-ops`: `refs.ts` (branches, tags, ref changes), `content.ts` (tree, blob, README), `history.ts` (lists of commits, blame), `diffs.ts` (commits, comparisons, their diffs), `merges.ts` (mergeability, merge, update branch), `index.ts` (lifecycle and the composition), `session.ts` (one call's view, ref resolution, the contract's shapes), `state.ts` (what is kept between calls). `localRepoReader(repository, state, locator)` is that reader wherever a `Repository` is.

**Every method runs inside the Durable Object.** `RepoDO.reader(repoId, locator, method, args)` runs one method next to the data and the Worker's reader (`reader-do.ts`) is nothing but that call. The alternative, the same code in the Worker with the object as an object store, was measured in workerd on this repository (2 870 commits, 93 303 objects), timed in the Worker around each call:

| Request                                  | In the object (one call) | In the Worker (a call an object) |
| ---------------------------------------- | ------------------------ | -------------------------------- |
| History, first 30 commits                | 1 ms                     | 33 ms, 62 calls                  |
| History of `KNOWLEDGE.md`, first 30      | 3 ms                     | 110 ms, 332 calls                |
| Last commits of `/`, 300 commits of walk | under 373 ms (see below) | 330 ms, 602 calls, and not done  |

Locally a call to the object is about half a millisecond, which is the best it will ever be: in production it is a hop to wherever the object lives. So the number that decides it is calls, not milliseconds here, and every operation that walks needs tens to hundreds of them. The operations that do not walk (a blob, a ref, a tree without history) are one call either way, and gain nothing from a second code path. `readObjects` batching does not help a walk, which learns the next id from the last object. So there is one implementation and one place it runs. The costs of that choice: reads share the object's 128 MB and its one thread with pushes (a diff holds two files of at most 1 MiB and its hunks; a push peaks near 88 MiB, "Memory" below), and a refusal has to cross the boundary as a value (`ReaderReply`), because an error thrown across it keeps only its message. An error the platform raises for the object itself (`overloaded`, `retryable`) becomes `unavailable`; anything our code throws stays a 500.

**Only types come from the contract in `queries/`.** The object's module graph is loaded at the Worker's start-up, and the contract's entry evaluates every schema of the API. `rawUrl` and the 1 MiB text limit are restated there; `test/reader.test.ts` holds both equal to the contract's.

**What is kept between calls** (`ReaderState`, one per object, gone when it sleeps):

- **The commit graph**: parents, tree and commit time of every commit a walk has read (`CommitGraphSource` in git-ops), up to 200 000 commits. Each request's `ObjectCache` reads through it, so only the first walk after a wake-up reads commits. It is in memory only. Loading it is what a cold request pays: counting this repository's 2 870 commits from nothing is about 120 ms on Node. A graph written down (with generation numbers) was not built: once the two answers below are stored, no request on the code page walks from the top, and at this size the cold cost is not worth a table. At a hundred thousand commits it would be (about four seconds cold for a count), and that is where to add it.
- **Sizes** (50 000), **diff summaries** (the changed files of a pair of trees with their line counts, 8), trial merges and last-change answers (256).
- **The file table's last commits, in steps.** `tree` walks for at most 2 000 commits or 150 ms and answers what it has (`lastCommitsComplete`); `treeLastCommits` carries the same walk on from where it stopped (10 000 commits or 400 ms a call). The continuation stays in the object's memory, keyed by commit and directory; if the object slept in between, the walk starts again.
- **Written down** (`reader_cache`, at most 128 rows, oldest pruned): a finished file table per directory and commit, and the number of commits a ref reaches. A woken object reads the row instead of walking, and a new head walks only as far as a commit that has a row (`known`, git-ops), or counts only what was added. This is one billed row write per directory viewed per new head.

**Sizes come from the pack, not from reading the object** (`PackStore.size`): the entry's header for a whole object, the second number of a delta's instructions for a delta (the first bytes of its zlib stream). One range read of 128 bytes, its own and not the block cache's, so a file table's size column (a probe per file, 24 at a time) does not push the commits and trees a walk is reading out of the cache. git-ops asks through it before reading a blob for a diff, a blame or a merge.

**Time budgets see time pass only across I/O.** In workerd `Date.now()` does not advance while code runs, so a walk over objects already in memory never reaches a `maxMillis`. Every budget therefore also has a count (commits, files, lines; `ReaderLimits` in `session.ts`), and the count is the real bound.

Reading exact ranges, sorted and joined, would cut both the reads and the bytes, and is not built; the count stops after 2.5 s and says so (`filesTruncated`).

**Writes** are compare-and-swap on the base, like a push. A merge (merge commit, squash, rebase) is computed by git-ops against the base as it was read, its objects are written as one small pack (`writeObjects`), and `applyUpdates` moves the branch only if it is still there, sending the push event with the merging person as its actor. If the base moved, the merge is computed once more against where it went; if it moved again the caller is told (`base_moved`). The objects of a lost attempt are unreachable, as a refused push's would be. `updateBranch` is the same with the sides swapped (a rebase is a forced update of the head branch, and its event says so). `createBranch`, `deleteBranch` and `setPullRef` are one compare-and-swap each; `setPullRef` sends no event.

**A fork's branch page is read in the base repository.** Before anything that needs a commit from another repository (`compare` with `headRepositoryId`, `mergeability`, `merge`, `setPullRef`, `diffAnchor`, and `updateBranch` taking from the base), the object asks the other repository's object for a pack of what that commit reaches and its own branch and branch page tips do not (`exportPack`, one object calling the other and streaming the answer), takes it in through the same path as a push (indexed, every reference checked), and from then on reads one repository. A head named by branch is resolved in the other repository's refs first. The copy is skipped when the commit is already here, and capped at 512 MiB (`maxImportBytes`). The objects are unreachable until `refs/pull/<n>/head` points at them, which is how GitHub keeps a fork's branch page too. Two things follow: whoever may open a comparison against a fork can make the base repository store that fork's commits (the handlers only offer repositories the caller can read), and a full clone carries them, since a clone of everything includes what no branch reaches (see "Sending").

**Lifecycle.** `init` sets `HEAD`, marks the storage `ready` and, when asked, makes the first commit from `templates.ts` (a README; a `.gitignore` for Terraform, Node, Python, Go or Rust; MIT, ISC or Apache-2.0, the last byte for byte as published); a template it does not know is left out. A repository whose storage was never made, or was destroyed, refuses `unavailable` rather than looking empty. `forkFrom` is `importFork` (with only the default branch's ref when asked; the packs are copied whole either way). `destroy` empties the bucket prefix and the tables and can be called again. The API's handlers already called all three; `repositories.create` now also reads `stats()` after a first commit, which sends no push event.

**Where it differs from what the contract says.** `DiffFileSummary.additions` and `deletions` are exact for the files counted, and zero for a file over the text limit (`tooLarge`) or past the 300; `stats` adds up what was counted. `BlameRange.previousCommitOid` is the first parent that had the file under the same name, so it is null across a rename. A tag of a tree or a blob resolves to nothing (`ref_not_found`), as does an abbreviated id in another repository. Cursors are positions, so a branch list that changes between pages can repeat or skip a branch.

### Events

After refs move, the object sends `{ type: "push", repoId, actor, updates: [{ name, oldOid, newOid, forced }], at }` to `EVENTS`: from a push through the protocol's `ReceiveHooks.after`, and from `updateRefs` (merges, web edits) unless told not to. `forced` is an update whose new commit does not descend from the old one, decided by an ancestry walk. A failed send does not fail the push: the refs have already moved. Nothing retries it; the consumer should be able to resynchronise from `listRefs`.

### Smart HTTP

`gitHttp(request, env, directory)` answers null for a request that is not one of its routes, so the router tries it first.

- **Who gets what** is at the top of `routes.ts`: 401 with the Basic challenge for anyone without credentials who may not proceed (a missing repository included, so names are not probed), 404 for someone signed in who cannot read, 403 with a `text/plain` reason for someone who can read but not push (`git` prints it after `remote:`), and 403 for an archived repository's push.
- `Git-Protocol` selects v1 or v2 for fetch; a push that asked for v2 is answered in v0.
- `Content-Encoding: gzip` request bodies are inflated. Responses carry the three no-cache headers.
- **CI's routes**: `GET /<owner>/<repo>/raw/<sha>/<path>` (any credential that can read; `Bearer` for a job token) and `GET /<owner>/<repo>/archive/<sha>.tar.gz` (a credential, or `?token=` with the commit-bound job token, which is refused everywhere else). Both answer `Cache-Control: private, no-store`. `<sha>` is a full id. The raw route is served as `application/octet-stream` with `nosniff` and a sandboxing CSP: it is somebody's file on our origin.
- A personal access token never administers (`repoAccess` caps it at `write`), so a token is bound by protected-branch rules even when it is the owner's. An SSH key is the person.
- The 100 MB request body limit of the zone's plan applies to a push over HTTPS. Over SSH there is none.

### SSH

- The username must be `git`. A key is looked up by fingerprint (`authenticateSshKey`); `markUsed` only once the signature has verified.
- Commands: `git-upload-pack` and `git-receive-pack` (also spelled `git upload-pack`), with the path quoted as git quotes it, with or without a leading slash and `.git`. `~` paths, anything with more or fewer than two segments, and every other command are refused with a line on stderr and exit status 1. The command string is parsed, never executed.
- `GIT_PROTOCOL` from the client's `env` selects the version.
- `ssh git@host` without a command gets "Hi <username>! You've authenticated, but git.infrawrench.com does not provide shell access."
- The idle timeout is raised to 30 minutes, because the protocol sends no keepalive while a push is indexed.
- **Failed authentication is limited per address** in the Cache API: 20 connections that end unauthenticated within 10 minutes and the address is refused until the window passes. Per data centre and best effort, on purpose (`rate-limit.ts` says why it is not a Durable Object).
- `SSH_HOST_KEY` is loaded once per isolate.

Two or three runs each, with the machine's load average around 6, which is where the ranges come from. The push is two to three times slower than the same code on Node (8 to 9 s). The likeliest cause is the indexer's second pass, about 900 range reads, each a round trip to the local R2 simulator; it was not profiled.

Measured again for #1447 (November 2026, the history now 100 037 objects in an 80.5 MiB pack, load average 5), over HTTPS, before and after its changes:

| Push of the whole history                 | 96.5 s           | 99.3 s            |

Why is not known.

A clone's wall time is mostly the client's own `index-pack`; "server only" is the same pack downloaded and thrown away. workerd's resident memory grew by over a gigabyte during a push and came back: locally nothing limits an isolate, so garbage is collected late, and the figure says nothing about the 128 MB limit.

## Versions and review (`repo/do/versions.ts`, `events/versions.ts`, `db/review.ts`, `review/`, `t3/`)

A branch is reviewed as a record of versions on its page. Every branch but the default one has a page, and the API, the MCP tools and everything a person or an agent reads speak of branches. The storage keeps its names (`git_pull_requests`, `pull_request_id`, `refs/pull/<n>/head`), and so do internal identifiers where renaming them was not worth it. `git/README.md` ("Agent work review") has the product; this is what the Worker does.

### What names a page (`db/branch-pages.ts`, `api/branch-page.ts`)

- **A page is named by its key** (`BranchKey`, client-core `git-branch-key.ts`, re-exported by the contract as `parseBranchKey`): `feature/a`, `owner/name:feature/a` for a fork's branch proposed here, `-:feature/a` once that fork is deleted (`head_repository_id` null), and `~n` for an earlier page of a reused name. In an API path it is one percent-encoded segment; the router hands handlers the decoded key (`api/__tests__/branch-keys.test.ts`).
- **The resolver** (`resolveBranchKey(baseRepositoryId, key)`) reads the pages of one head (base repository, head repository, head ref), oldest first by thread number, and picks with `pickPage`: `~n` is the n-th; the bare name is the open page, else the newest. A fork is found by namespace and name alone (the page lives in the base, which the caller can already read). Text that is no key resolves to nothing. Every handler under `/branches/:branch` goes through `pageOr404` (`api/branch-page.ts`), so a missing page and garbage are the same 404.
- **The canonical key** (`pageKeys`) is computed for a batch of pages in one query: a window over every page sharing a head with one asked for (`row_number()` for the ordinal, `first_value` ordered open first then newest for the page the bare name names), with the fork's `owner/name` joined in. Bare when the bare name resolves to the page, `~n` otherwise. Everything the contract carries a key in uses it: summaries and pages, the Changes list and suggestions, the inbox, activity, `Branch.page` and `Comparison.page`, a commit's `branchPages`, mentions (only for threads in repositories the viewer is shown, as titles were), and CI and Terraform runs (`pageKeysByNumber`, from the number a run records). `ci.listRuns` and `terraform.listRuns` take `page=<key>`; a key that names no page lists nothing.
- **`branches.locate`** answers the key of the page a thread number names (`#12` in a comment), 404 for an issue's number.
- A fork's key names the fork even for a reader of the base who cannot read the fork (a private fork is only ever proposed to a private base of the same owner, so only its name is told).

### Recording

- **The Durable Object records a version in the transaction that moves the branch** (`Repository.updateRefs` calls `recordVersions`). Every push to a branch other than `HEAD`'s is one, forced or not, whichever way the ref moved (a push, a merge from the UI, `updateBranch`). SQLite holds `versions` (branch, lineage, number, tip, previous, forced, at) and `version_branches` (the lineage and number given out last, which outlive pruning so neither is reused). A push that loses its compare-and-swap moves nothing and records nothing, so a client's retry cannot count twice.
- **Lineage.** A branch created where none was starts lineage `n + 1` at number 1. Created at the commit its last version had (a deleted branch restored) it carries on and records nothing. Created at a commit the default branch already has (start work, `git push origin main:topic`) it starts the lineage with no version: the first push with work in it is version 1 (`bringNothing`, an ancestry walk done before the transaction).
- **Each version's commit is kept by a ref**, `refs/infrawrench/versions/<lineage>/<number>/<branch>`, in the same `refs` table as every other ref. That is what makes it readable by id after a forced push (`Repository.isReachable`, `queries/session.ts` `reachable`), which the branch page's diffs of older versions need.
- **No client sees or writes those refs.** `Repository.backend().listRefs` leaves out `refs/infrawrench/*` (`isHiddenRef`), and the protocol lists, resolves wants and checks old values from that one listing, so `ls-remote`, a clone, a fetch by id and `want-ref` never meet them. `policy.ts` `namespaceRefusal` already refused `refs/infrawrench/` to every push. `refs/pull/*` is still advertised: CI fetches it.
- **The full-clone fast path is untouched by a version ref.** The ref points at the branch's new tip, so recording one changes nothing about what branches and tags reach, and `changed()` is told only what the push itself did. A commit only a version ref holds exists because a forced push or a deletion left it, and that update has already cleared the "everything is reachable" answer. `Repository.pruneVersions` clears it too, in the transaction that removes the refs. Version refs are not branches or tags, so `countReachable`, `exportPack` and a fork's copy never follow them.
- **The queue consumer copies versions to Postgres** (`events/versions.ts` `recordVersions`, called from `handleBranch` before the "branch has moved on" return). It asks the object for every version after the newest one it has (`RepoReader.listVersions`) and inserts each, unique on repository, branch, lineage and number. So a redelivery writes nothing, and a push whose event was lost is copied by the next push to the branch (without a pusher: the event that named them is gone). The merge base and the stats come from `compare` against the branch page's base, else the default branch, when the storage answers.
- **A push claims the trace entries waiting on its branch** (`claimTraceEntries`: those written at or before the push), and a new version in a lineage clears that lineage's `prune_after` and sets it on the lineages before.

### The branch page

- **A branch's page is opened, as a draft, at its first push** (`openBranchPage`), always: there is no setting (`auto_open_branch_pages` and `has_pull_requests` are in the schema still, unread). Not for the default branch, a fork (its branches are proposed to the parent by a person, `branches.propose` with `headRepository`), an archived repository, a branch with nothing ahead of the default branch, a branch that has an open page, or a lineage that ever had one (closing the page does not reopen it at the next push). The title is the commit's subject when one commit was pushed, else the branch's name as words (`titleOf`). CI hears `opened` and Terraform plans are queued, as for one proposed by hand.
- **A branch with no page gets one when it is read** (`pageOrOpen`, `branches.get` only): a bare key, a branch of this repository that exists and has commits the default branch does not, in a repository that opens pages, and no page ever for that head (a closed one stays closed). That covers branches pushed before every branch had a page, or whose event was lost. It runs after the repository's read gate, so a private repository answers as missing first. The author is the reader when signed in, else nobody (`author_user_id` null). `openDraftPage`, which both paths call, checks and inserts under one advisory lock per branch, so a push and a reader opening it at once open one page, and announces it exactly as a push does.
- **At most one open page per head** (base repository, head repository, head ref), whatever its base branch: `branches.propose` and `branches.reopen` answer `branch_page_exists` otherwise. `propose` defaults `base` to the default branch and `title` to the branch's name as words.
- **Versions belong to a page** by `pull_request_id`: set when the version is copied (the first open page whose head is the branch), and by `linkVersionsToPull` when a page is opened on a branch that already has versions. `versionsForPull` reads those, of the newest lineage; a second page of the same head has none of its own and reads the branch's.
- **Start work** (`handlers/agents.ts`) creates the branch at the base's commit and its draft page whose body is the ask, with no commits between them (`branches.propose` refuses that; this handler does not go through it). It answers `page`.
- **Review comments are written on a version** (`git_review_comments.version_number`) and carried forward by the consumer (`carryThreads`, in `syncHead`): `RepoReader.mapLines` says where an anchor's lines are at the new head. Lines that stand move the thread to their new numbers (`commit_oid`, `line`); lines that changed mark it `outdated` with `answered_in_version`. `RIGHT` anchors are compared head to head, `LEFT` ones merge base to merge base (from the versions' rows). A file renamed between versions counts as changed. Safe to repeat: a thread already at the new head is skipped.
- **Diffs** (`queries/versions.ts` `versionDiff`, on the head repository's reader, which has every version's commit and each one's base): the whole change is base to tip. An interdiff with one base is tip to tip. After a rebase the older version is first carried to the newer base by a three-way merge in memory (`mergeTrees(oldBase, newBase, oldTip)`, nothing stored), and that tree is compared with the newer tip, so what the rebase brought does not show. When that merge conflicts the tips are compared as they are and the answer says `exact: false`. The merge is redone for each page of the diff.
- **The must-fix merge block is live** in `mergeabilityDetail` (`must_fix_findings`, never bypassable with `bypass: true`): an open must-fix finding no `git_merge_overrides` row covers, where the repository's settings hold merges on them. `findings.override` (an administrator, signed in, with a reason) writes that row for the findings named, or for every open must-fix finding not yet covered; one raised afterwards is not covered.
- **Pruning removes the refs and keeps the rows** (`review/prune.ts`, the hourly cron trigger): `prune_after` is set thirty days out when the branch is deleted (the consumer) or its branch page merged (`branches.merge`). The run removes the refs in the object (`Repository.pruneVersions`, which clears the "everything is reachable" answer in the same transaction, as before), then sets `pruned_at` on the rows. The commits are what cost storage; the row is the record, and everything that names a version (trace entries by `version_id`, findings, review comments, instructions and reviewed marks by number) keeps naming it. `dueVersions` leaves out rows already marked, the partial index is on `prune_after` where `pruned_at` is null, and a run that stops between the two steps is finished by the next (dropping a ref twice drops nothing). A repository whose storage does not answer is left for the next run. The object's own SQLite rows for those versions still go with the refs: it numbers versions and has no use for a record.
- **A pruned version's diff is served only while a ref still reaches its commits.** The objects are usually still stored (repack drops nothing), but what only a version ref held is a leftover, and a leftover is not read by id. So `versions.diff` passes `reachableOnly` for a pruned version and the reader checks both tips with `reachable` first (`queries/versions.ts`). A merge commit keeps the branch's commits reachable for ever, and `refs/pull/<n>/head` keeps a page's last head, so in practice it is the versions a forced push left behind, and a squashed branch whose pull ref is gone, that stop. When they do: the whole change of the version that was merged is read from `merge_commit_oid` against its first parent (`mergedChange`, for `merge` and `squash`; `source: "merge"` in the answer), and anything else answers 422 `version_pruned`, which the page shows as a sentence, not an error.

### The record on the default branch (`db/review-history.ts`, `views/review-history.ts`, `handlers/contents.ts`)

- **`contents.commitReview`** answers the branch page a commit was merged as, by `git_pull_requests_merge_commit_idx` (repository, `merge_commit_oid`): the page's key and title, its versions (counted from the kept rows), the first `ask` entry of its trace, and every finding as the merge left it, the gravest first. An open finding carries the newest `git_merge_overrides` row that names it: who let the merge past it and why. The commit is matched by its whole id (a prefix names no page), and nothing asks the repository's storage. `merge_commit_oid` was already recorded by `markMerged` for all three methods; no column was added.
- **`contents.pathReview`** answers the findings merged pages left on a path, by page, the newest merge first (5 pages by default, 50 at most). `git_review_findings_path_idx` (repository, path, where the path is not null; migration `0205`) finds the path's findings, the pages are read by their keys, and `recordsOfPages` reads findings, overrides and version counts in three statements however many pages. The path is matched as the finding named it: a file renamed since has the history of its new name only.
- **Both take `read` and nothing else**, behind the repository's gate like every `contents` endpoint, so a private repository answers 404 before either runs.
- **The blame is not changed.** Marks on a blamed file are placed in the browser from `pathReview` and the blame's own ranges (`web/src/features/code/review-history.ts` `placeOnBlame`), one request beside the blame and none per line. A finding's lines are numbered in `commit_oid`; it gets a line when a blame range of that same commit covers them all (a merge commit keeps the branch's commits in history), or, for a squash, when a range of the merge commit does and the finding was last seen on the head that was merged (`linesAtHead`). The squash case assumes the base did not change the same file between the merge base and the merge; where it did, the mark can be off by the lines the base added above. Everything else is counted on the file's header, never guessed onto a line. A rebase gives its commits new ids, so its findings are only ever counted.

### Review agents (`review/`, `events/reviews.ts`, `db/findings.ts`, `handlers/findings.ts`)

- **A run is a row and a message.** `events/reviews.ts` queues one `git_review_runs` row for a new version of a branch with an open branch page (from `handleBranch`, after the head is synchronised), where the repository has review agents on, an organisation owns it and a model is configured, and sends its id to the `REVIEWS` queue. One run a version (`queuePushRun`, under an advisory lock on the branch page, so two deliveries of a push queue one); a queued run of an older version is deleted, since nothing ran. A fork's branch page queues nothing on a push: the base's organisation pays, and anyone can push to a fork, so someone with `write` asks for it (`findings.requestRun`).
- **Why a queue of its own.** A run is minutes of waiting on a model: in the push queue it would sit in front of other pushes. A Workflow would lift the consumer's 15 minutes of wall time, but it stores each step's result, and a run's steps are prompts and answers made of the repository's code. A run is bounded well inside 15 minutes instead (`review/policy.ts` `REVIEW_LIMITS`: a 10 minute deadline, 24 model calls and a budget per reviewer) and restarts cleanly, since findings are upserts.
- **No run stays `running`.** `claimReviewRun` takes a run that is queued, or one `running` longer than the lease (16 minutes, past the consumer's limit: its invocation died). A second delivery finds it finished (`ignored`) or held (`busy`: retried in two minutes). A delivery past `maxAttempts` fails the run. An error of ours (the database) gives the claim back and retries the message. The hourly sweep sends queued runs nothing picked up, and fails what waited three hours or ran past twice the lease. The message is only the id: the runner decides everything from the rows as they are now (the branch page still open, this still the newest version, agents still on).
- **The loop** (`review/reviewer.ts`) is one conversation per reviewer over the Messages API, append-only, replayed whole each turn with the system prompt and the history cached. Tools (`review/tools.ts`) read (`read_diff`, `read_file`, `list_directory`, `read_trace`, `read_checks`, `read_terraform_plan`, `list_findings`) and write findings (`report_finding`, `recheck_finding`), and nothing else: there is no tool that approves, merges, comments or reaches the network. A tool's input is validated by hand (the model's JSON is not trusted), its answer is bounded and says when it was cut. The model is one constant per reviewer (`REVIEWER_MODELS`, all `claude-opus-5-5`; thinking is adaptive there and effort is the control).
- **The model is server-core's Anthropic client** (`anthropic-client.ts`, AI Gateway on Unified Billing), behind `ReviewModel` (`review/model.ts`) so tests hand the runner a script. The SDK and server-core's `billing/ai-usage.ts` are in the bundle; `import-graph.test.ts` still passes, and the client is loaded at a run's first model call.
- **Never logged.** A prompt and an answer hold a repository's code and CI logs. Nothing of them is passed to `console`, and a failed call is kept as its class and HTTP status (`describeModelError`), never its message.
- **What a finding holds is masked before it is stored** (`review/findings.ts` `prepareFinding`, through `maskSecrets`): title, body and evidence, whoever reported it. CI log excerpts are masked before the model reads them too.
- **A fork's review reads less.** Its code is anyone's, and what the model reads it can be talked into repeating in a finding the fork's author reads. So for a fork's branch page `read_checks` gives check names and states and no log, and `read_terraform_plan` nothing (a fork never has a plan). For every branch page, a Terraform run's log is never read (it prints attribute values and takes `write`; a finding takes `read`), and a plan is its summary (addresses and attribute names), never its cost: costs are behind `costs:read`.
- **Fingerprints.** A finding is one row per branch page and fingerprint (reviewer, path and normalised title, not the line). Reported again it is updated (`seen`), reopened when it was fixed, and left exactly as it was when a person dismissed it. An older version's run never overwrites what a newer one saw (`upsertFinding` compares `last_seen_version_number`).
- **Fixed.** The forge's reviewer is shown its own open findings and says of each `fixed` or `still_present` (`recheck_finding`); one it does not recheck stays open. A reviewer outside the forge says its report is `complete`, and its open findings last seen before that version are marked fixed.
- **Back to the agent.** A must-fix finding that is raised, or comes back after being fixed, on a branch page with an agent link becomes a queued `git_instructions` row (`db/finding-instructions.ts` `queueFindingInstructions`, the one place a finding becomes an instruction; `instructions.send` uses it for a finding a person sends). Not when it is merely seen again.
- **The forge's reviewer names are its own.** `findings.report` refuses `general`, `security`, `tests`, `terraform` and `intent`: a report that says it is complete marks that reviewer's other findings fixed, and the merge block reads them. A CI job's token reaches the `findings` group (`middleware.ts` `JOB_GROUPS`) to list and report, and the handlers refuse it everything else.
- **Writing a finding is server-core's** (`server-core/src/git-review/findings.ts`): `prepareFinding`, `fingerprintOf`, `upsertFinding`, `markUnseenFixed`, `recordFindings` and `queueFindingInstructions` moved there, with `masking.ts`, `needs-code.ts`, `trace.ts` and `trace-rows.ts` beside them, because the app's CI writes a job's note commands through the same functions (below). `review/findings.ts`, `review/masking.ts`, `review/needs-code.ts`, `review/trace.ts`, `db/findings.ts`, `db/finding-instructions.ts` and `db/traces.ts` re-export them under the names they had, and their tests here still run against them. They reach nothing but Postgres, so the bundle test holds.
- **CI's names are CI's.** The app writes a job's `::must-fix`, `::should-fix` and `::note` lines as findings under `ci:<pipeline>/<job>` and its `::doubt`, `::decision`, `::step` and `::evidence` lines as trace entries by an agent of kind `ci` (server-core `ci/git-notes.ts`; KNOWLEDGE.md "CI notes"). `findings.report` refuses a `ci:` reviewer (`isCiReviewer`) and `traces.record` an agent of kind `ci`, both 422: a job that passes marks its name's other findings fixed, and the page says "CI" by those names. Nothing else in the Worker knows about them: the rows are findings and trace entries like any other, so the tally, the placement on the diff, dismissing, the override and the merge block need nothing. Two functions exist for CI alone, `markOthersFixed` (fixed by what was not reported, so a job run again on one version fixes there) and `carryFindings` (a cached job did not look again). The page's label is `web/src/features/review/Trace.tsx` `CiSourceLabel`, fed by `branch.ts` `findingCiSource` and `traceCiSource`; the link is the `ci` evidence's URL on a finding and `evidence.url` on a trace entry, which the app writes as the run's page at the job and the log line.
- **Billing** (`review/runner.ts`, `review/policy.ts`). A run draws on the organisation's AI spend pool, the one chat and `infra.ai()` use (server-core `billing/ai-usage.ts`): `reserveAiSpend` before the first model call (the cap reached ends the run `failed` with a reason that starts "Skipped"), and each reviewer's usage written with `recordWorkflowAiUsage` under `workflow_id` `git-review:<repository id>` and to the run's row. The Worker holds no Stripe key, so the meter event is sent by the app's `git-storage` poller pass (`server-core/src/git/billing.ts` `reportGitReviewUsage`), with the usage row's id as its identifier. A reviewer outside the forge pays for itself; what it reports with `updateRun` is only shown.

### Instructions (`db/instructions.ts`, `review/instructions.ts`, `handlers/instructions.ts`)

- **What the agent is told is written out when it is sent.** A review thread becomes its path, lines, version and every submitted comment quoted, then the reviewer's words; a finding its severity, place and text (`findingBody`, which whoever queues one itself can use). So an edit, a resolved thread or a pruned version does not change what was asked. A comment of a pending review cannot be sent.
- **States.** `queued`, `delivered`, `answered`, `dismissed`, each a single conditional `UPDATE`. `answered` without a version means "my next push": the row has no version number until `settleAnswered` gives it one, called from `recordVersions` for each version copied, for the instructions answered at or before that version's push. One marked answered after the push waits for the next. Settling also sets `answered_in_version` on the review thread the instruction came from, where a push has not already (`carryThreads` only does when the lines changed). `openInstructionCount` counts an unsettled answer as open, so the branch stays `agent_working` until the push arrives.
- **Who.** Sending and withdrawing take `write` and a person or an API key: a CI job's token is refused both (`peopleOnly`). Marking delivered and answered take `write` too, and that is the one place a job's token with write access reaches this group (`JOB_GROUPS`); a read-only job token lists and nothing else.
- **Delivery is `deliverInstructions(env, pullRequestId)`**, over rows, whoever inserted them. Whatever queues an instruction (the API, the review runner for a must-fix finding) inserts a `queued` row and calls it. It claims a row (`queued` to `delivered`, `delivered_via` the agent's kind) before telling the agent and puts it back if that fails, so two callers never tell an agent twice; it goes oldest first and stops at the first failure, so they arrive in order. Only `t3` has a sender (`t3/work.ts`). `infrawrench`, `mcp` and a branch with no agent named are pull: the agent lists its instructions and marks them itself.
- **The sweep** (`sweepInstructions`, the `*/2 * * * *` cron; `index.ts` tells the two crons apart by expression) delivers rows older than thirty seconds on branch pages whose agent has a sender. It is the backstop for a caller that did not deliver and for an environment that was asleep.
- **Sending answers after trying to deliver**, so the row a reviewer gets back already says `delivered` when the agent was reached. A T3 Code environment that does not answer costs the request its timeout (ten seconds) and leaves the row queued.

### T3 Code (`t3/`, `handlers/t3.ts`, `review/agent-connect.ts`)

Verified against T3 Code 0.1.11; the model tools (`orchestrator_capabilities`, `modelSelection`) were read from its source at 0.1.13. An environment serves MCP at `<origin>/mcp` with MCP's OAuth; the forge is a client of it.

- **Reachability.** A Worker reaches public addresses only, so an environment is added by its public `https:` address: the one T3 Connect gives, which the form asks for first, or a person's own proxy ("Use an address"). `localhost`, a LAN address and a tailnet name cannot work and the first two are refused when typed, with a sentence that says to turn T3 Connect on.
- **T3 Connect** (`t3/connect.ts`, the contract's `t3-connect.ts`). Read from T3 Code's relay source (`infra/relay/src/deploymentConfig.ts`, `ManagedEndpointProvider.ts`), its docs (`internals/06_t3-connect.md`, `user/outside-agents.md`) and the 0.1.11 server bundle:
  - Linking T3 Connect gives an environment a Cloudflare tunnel of its own at `https://prod-<digest>.<tunnel zone>`, the digest being the first 16 hex characters of SHA-256 over `prod:<T3 Connect user id>:<environment id>`. The relay (`relay.t3.codes`) allocates it and is not in the path of a request, so the forge calls the tunnel address directly and holds one credential, the environment's own OAuth token. There is no relay token to store.
  - The forge cannot work the address out or look it up. The digest needs the person's T3 Connect user id, and the relay's listing (`GET /v1/environments`) takes a session of T3 Code's own apps (Clerk, one public client whose only redirect is a loopback port). There is no sign-in to send a person through, so they paste the address: T3 Code copies it as the MCP URL (Settings, Environments, Copy MCP URL).
  - **The tunnel zone is `t3coderelay.com`** (`T3_CONNECT_ZONES`). T3 Code sets it as a deployment variable (`RELAY_TUNNEL_ZONE_NAME`) the source does not state, but its own tests use `t3coderelay.com` for tunnel addresses throughout, and the domain is registered at and served by Cloudflare, where the tunnels are. A T3 Connect address must be `https:`, the default port, `prod-` and 16 hex, directly under that zone. If a real address turns up under another zone, add it to the list; "Use an address" connects it meanwhile.
  - `create` with `via: "t3-connect"` takes only such an address (`connectOrigin`), and still passes it through `publicHttpsUrl`: the check narrows, it never lets through what `t3/http.ts` refuses. `via` absent or `"address"` is the rule as it was. Nothing is stored about how an environment was added; the list shows "T3 Connect" from the address.
  - On a T3 Connect address T3 Code builds its issuer and every OAuth endpoint from the request's own origin, so `discover` refuses documents that name any other host there, public or not. A typed address may still name an authorization server of its own.
  - The sign-in page on a tunnel address sends the browser to `app.t3.codes/approve-agent`, where the person approves with their T3 Connect account. That is a redirect in their browser, not a request of this Worker's. A pairing code is another way to approve on that page and nothing the forge ever sees.
- **Every request goes through `t3/http.ts`.** `https:` to a host `blockedHost` (the image proxy's rule) lets through, never this site, no credentials in the URL, `redirect: "manual"` with any 3xx a failure, a ten-second timeout (sixty for a clone or a launch) and a one-megabyte body cap. That applies to the addresses in the OAuth documents too (issuer, authorize, token, registration), which the environment chooses. The resource metadata address in a `401` challenge is used only on the environment's own origin. No `Origin` and no cookie is ever sent (T3 Code answers 403 to any `Origin`).
- **OAuth** (`t3/oauth.ts`): protected resource metadata, then authorization server metadata (RFC 8414 and the OpenID fallbacks, in the specification's order), dynamic registration as a public client with only `client_name`, `redirect_uris` and `token_endpoint_auth_method`, PKCE `S256` (a server that does not list it is refused), and the `resource` indicator on both requests. The redirect address is `SITE_ORIGIN` + `AUTH_PATHS.t3Callback`; nothing needs registering anywhere by hand.
- **A sign-in belongs to a session.** `state` is 32 random bytes on the row, single use, ten minutes. `t3/callback.ts` requires the browser's session to be the row's person before anything is exchanged, clears the state before the exchange, checks `iss` (RFC 9207), and redirects to a path stored when the sign-in began with `t3=connected` or `t3=failed`; nothing from the query reaches the answer.
- **Tokens.** One JSON object per row (`credentials_ciphertext`), sealed with `encrypt` under `ENCRYPTION_MASTER_KEY` and bound to the row. T3 Code issues an access token for thirty days and no refresh token, and has no revocation endpoint: a sign-in ends by running out or by being removed in T3 Code. Where a server does issue refresh tokens they are used a minute before expiry inside a transaction that holds the row (they rotate, so two requests must not spend the same one), and removal revokes where there is an endpoint.
- **`last_error` holds only sentences written here or T3 Code's own refusal** (cut to 500 characters, shown as text). Only a sign-in that no longer holds makes the status `error`; an environment that is asleep stays `connected`.
- **MCP** (`t3/mcp.ts`): Streamable HTTP, one `POST` per message, JSON or an event stream read to the response for the request's id. The client offers `2025-11-25` and takes what the server answers (T3 Code: `2025-06-18`, with a session id). A session lasts one request of the forge's; a `404` for it starts another.
- **Starting work** (`review/agent-connect.ts`, from `agents.startWork` and `agents.set`): `prepareAgent` runs before the branch is made and finds the environment's project by the repository's remote (`t3_project_list`), or clones it to `~/infrawrench-git/<owner>/<repo>` and registers it (`t3_project_clone`, `t3_project_create`, which need the person to have approved this site for full access). Then `t3_thread_launch` on a worktree named for the branch, from `origin/<base>` (the commit the forge made the branch at), with the ask, the branch to push to and how to report to the reviewers (below) as the first message, and `clientRequestId` keyed by the branch page so a retry finds the same thread. The link's `externalRefs` are `threadId`, `projectId`, `threadUrl` and the model the thread got (below). A launch that fails keeps the branch page and leaves `launchError`; `agents.set` with the same environment and no `threadId` tries again. The refs the forge writes (`FORGE_REFS` in `t3/work.ts`: `startUrl`, `launchError`, `threadStatus`, the model's, `sendError`) are dropped from what a client sends.
- **The model** (`t3/models.ts`, `t3/work.ts` `launchThread`, `t3.listModels`). What T3 Code does, from its source (`packages/contracts/src/orchestratorMcp.ts`, `modelSelection.ts`, `apps/server/src/mcp/toolkits/project/handlers.ts`):
  - `t3_thread_launch` takes `modelSelection: { instanceId, model, options? }`, `options` being `[{ id, value }]`, and answers the `modelSelection` the thread got. Without one, a caller outside a thread gets the project's default and is refused when there is none ("Pass modelSelection: the project has no default model..."). That refusal, shown as "Idle", is what this was written for.
  - `orchestrator_capabilities` answers `providers`: `{ providerInstanceId, driverKind, displayName, models: [{ id, label?, options?: [{ id, values, default? }] }], constraints }`. A provider with anything in `constraints` (disabled, not installed, not signed in) cannot run a thread and is left out. The list is short (pinned and current models); `search` finds the rest, which the picker does not use.
  - A project (`t3_project_list`) carries its own `defaultModelSelection` or null. A default set for every project in T3 Code's settings is not there, so such a project reads as having none here while a launch without a model would still work.
  - The capabilities do not say which option is the reasoning level: the `role: "reasoning"` of T3 Code's descriptors is not passed on. It is found by id, the list T3 Code's own clients use (`REASONING_EFFORT_OPTION_IDS`: `reasoningEffort`, `effort`, `reasoning`, `variant`, `reasoning_effort`, `thinking_level`, `thought_level`). Only string levels are offered; a boolean `thinking` option is not a level.
  - **The person chooses.** Start work always asks for the model (and the level, for a model with levels), starting at the project's default for the repository, and waits for a choice when there is none. The choice travels as `AgentLinkSet.t3Model` and is sent as `modelSelection`. T3 Code checks it against its own list and refuses a model or a level it does not have; nothing is checked here first.
  - **Nobody chose** (the API without `t3Model`, Try again on an old branch): the launch is sent without a model, which runs the project's default. Refused for want of one, `pickModel` chooses (what the environment says it would inherit when it says, else a Claude provider's first model, else the first provider's first model, each at the model's own level) and the launch is sent again. Both sends carry the same `clientRequestId`, and the retry only happens on that one refusal.
  - **What the thread runs is what T3 Code answers**, not what was sent: a retry that found the first try's thread has that thread's model. It is kept on the link (`modelProviderId`, `modelId`, `modelName`, `reasoningLevel`, and `modelPickedBy: forge` when it was picked here), with names from one more `orchestrator_capabilities` call that is allowed to fail.
  - `t3.listModels` takes `owner` and `repo` only to find the project among the environment's own by its remote. The repository is not looked up, so the answer says nothing about a repository the caller cannot read.
- **A launch that failed is shown as failed.** The branch page's Agent panel reads `launchError` from the page's state and shows T3 Code's sentence with Try again (`agents.set` with the environment, a model and no `threadId`), for the environment's own person. "Idle" is a thread that exists.
- **An instruction that did not arrive is said.** `sendInstructionToThread` leaves the reason on the link as `sendError` (one `jsonb` statement, `noteAgentLinkRef`, so it cannot undo a ref written meanwhile) and takes it away when one arrives. The row is still queued and the sweep still sends it.
- **The thread pushes with its own machine's Git credentials.** Nothing of the forge's (no session, no token) is sent to an environment, and the prompt says so.
- **What the thread is told about reporting** (`t3/work.ts` `reportingGuide`, in `workPrompt`; `instructionMessage` for each instruction): the commands that give it the forge's tools (`markerSetup`), one whole `tools/call` of `record_trace` as `curl` sends it, then a numbered list: every trace kind and when (`ask`, `step`, `decision` with its reason and what was ruled out, `evidence` with command, exit code and output, `doubt`, `note`), anchors, `needs_code`, recording before the push, `mark_instruction_delivered` and `mark_instruction_answered`, `report_finding` for a thread that reviews, a CI job's note commands, and the skill's address for the rest. A change to a tool's inputs changes this text; `t3/__tests__/client.test.ts` holds the names.
- **The thread gets its own token; the forge sends none.** Why, checked against T3 Code's source and the 0.1.11 bundle:
  - An agent in a thread cannot finish the MCP server's OAuth by itself. T3 Code runs Claude Code with the person's own settings (`settingSources: ["user", "project", "local"]`, `ClaudeAdapterV2.ts`), and a server that needs sign-in shows the person a **Sign in** notice on the thread (`docs/user/providers-claude.md`). That works, with a person; the agent alone gets a 401.
  - An outside MCP client cannot hand a thread a secret. `t3_thread_launch` and `t3_thread_send` take a message, attachments and modes, no environment (`mcp/toolkits/project/tools.ts`, `contracts/orchestratorMcp.ts`). `request_secret` is hidden from outside clients (`hiddenFromOutsideClients`), and its card is answered only over T3 Code's own client socket (`ws.ts`, `secretRequests.answer`); `t3_pending_request` answers questions, not secret cards. `t3_project_update` takes scripts, which would store a token in the project's settings. Provider environment variables are a person's settings and not in `t3_environment_preferences_update`. So a token the forge sent would be message text, kept in the thread's history.
  - So the thread asks. `markerSetup` is three commands: `git credential fill` for this host (never prompting), its password turned into a `curl` configuration line on standard input (never an argument, never a variable), `POST .../branches/<key>/agent/token`, the answer's token written under `umask 077` to `<git dir>/infrawrench-git-token` (the worktree's own Git directory: not in the tree, so no commit or push carries it), then `claude mcp add --header` reading that file. Nothing in the message is a secret. `t3/__tests__/marker-setup.test.ts` runs the commands under `sh` with stand-ins and checks where each value goes and that nothing is printed.
  - A session that started before `claude mcp add` does not have the tools until it starts again, and Codex takes a bearer token only from an environment variable of its own process. So the prompt also shows a tool called with `curl`: `/mcp` is stateless and answers a lone `tools/call` (`mcp/__tests__/mcp.test.ts` holds that).
  - A machine with no HTTPS credential for the forge (it pushes over SSH) gets an empty file. The prompt says to say so and carry on; the person can sign the server in from the thread's notice.
- **State.** `agents.get` adds `externalRefs.threadStatus` (`idle`, `running`, `waiting`, ...) from `t3_thread_read`, kept fifteen seconds per isolate. The branch page's state does not ask the environment. T3 Code 0.1 has no event subscriptions, so nothing is pushed back.
- **An Infrawrench agent** is started by the app, never from here (the forge's Start work page no longer offers one, so this is for the API, the MCP server and pages that already have one): its link carries `startUrl` (`<app>/org/<id>/agents?git=<owner>/<repo>&branch=<key>`; links stored before the change still carry `&pull=<n>` until the agent is set again) and `organizationId`, and the app writes `sessionId` on the same row when it starts the session. A person's repository has no organisation to start one in and is refused, unless a session that already runs is being named.

### Traces (`api/handlers/traces.ts`, `db/traces.ts`, `review/trace.ts`, `review/masking.ts`)

- **Who records.** A person or an API key with `write` on the repository. The endpoint's gate is `read`, because that is all a CI job's token has, so the handler checks the level itself (`authorOf`). A personal token also needs `repo:write`, which is `runHandler`'s check for every non-GET.
- **A CI job's token records on its run's branch and nothing else.** The token names a repository and a run. The handler reads the run (`ci_runs`, through `getCiRun`, which also holds it to the organisation that owns the repository now) and refuses when there is none, when it is a fork's branch page (`from_fork`), or when the entry's branch is not the run's `head_ref`. A token minted for no run (`runId` null) records nothing. A deploy key never does: it pushes, it does not speak for an agent.
- **Masked, then cut, then stored** (`review/trace.ts` `prepareTraceEntries`). Every string of an entry goes through `maskSecrets`: the body, the command, the output, the link, the anchors' paths, and what the agent calls itself. Masking comes first because a secret cut in half has lost its shape. The answer to `record` is the stored rows, so an agent sees what was kept.
- **`maskSecrets` is a filter over text** (`review/masking.ts`, whose header lists what it knows): shapes (every `iw?_` prefix, the common providers' tokens, JWTs, private key blocks, webhook addresses), a password or a long token in a URL, `Authorization` and `Cookie` headers, values given to a name that says secret (`KEY=`, `"password":`, `--token x`, `curl -u`), and a random-looking value given to an `UPPER_SNAKE` name (`looksRandom`: entropy and mixed character classes; a 40-digit hex commit id and a path are kept). Eager on purpose. It cannot know a secret with no shape and no name; the MCP tool's description tells agents not to record one. Every pattern starts from a boundary, so a long line is one pass (a test holds 200 kB of one character under two seconds).
- **Limits** (`TRACE_LIMITS`, in UTF-8 bytes): a body is 32 KiB and refused past it (422 `too_large`, naming the entry, nothing of the call stored); an output is cut to 16 KiB keeping its first 4 KiB and its end with a line between saying how much is gone; a command to 4 KiB. A branch holds 1,000 entries waiting for a push and a repository 20,000 over all its branches (a branch need not exist to be written to, so the first bound alone bounds nothing). The contract's schema bounds the same fields further out, in UTF-16 units, before the handler runs.
- **Entries of one call are dated a millisecond apart, ending at the call's time.** Order within a call is the order given whatever the ids sort like (lists page by timestamp to the millisecond, then id), and none is dated after the call, so a push that follows at once claims them all (`claimTraceEntries` takes what was written at or before the push).
- **Entries no push claims are dropped after thirty days** (`pruneStaleTraces`, in the hourly cron beside `pruneVersions`). A claimed entry is kept: its version's row outlives pruning, so the foreign key's cascade only ever fires when the repository goes.
- **Rate.** The API's admission counts `record` against its caller as a write (120 a minute signed in), like every other write.
- **Reading** is the repository's readers'. `list` takes a `branch` of this repository (a name, not a key): its versions' entries plus what waits on it for the next push.
- **Default branch.** `record` refuses it: it has no versions, so an entry there would never be claimed.
- **`needsCode`** (`review/needs-code.ts`, `needs_code` on both tables) says the reader has to see the code an entry is about to understand it: the page shows the anchored lines beside the text when it is true, the text alone when it is false. It is on trace entries and on findings, and one pure function resolves it for both when the row is written (`resolveNeedsCode`, called from `prepareTraceEntries` and `prepareFinding`), so it is stored and every read shape carries it. Left out, it is true when the entry points at a line (a trace anchor with a `startLine`; a finding with a path and either line) and false otherwise. Said false, it is false. Said true with no file at all (no anchor, no path), it is stored false: there is no code to show. A finding reported again on a later version takes the newest report's value with the rest of its content (`upsertFinding`); `recheck_finding` moves lines and leaves it alone. The tools name it `needs_code`, like their other inputs (`record_trace`, both `report_finding`s), and the reviewers' prompt says when to set it. Rows written before the column read false.

### A person's work across repositories (`/api/workspace`)

`db/workspace.ts` and `api/handlers/workspace.ts` answer the home page (`workspace.home`), the Changes list (`workspace.changes`) and the comments that mention them (`workspace.mentions`). `workspace.threads` is gone with the classic view.

- **The scope is `tiedTo`, not `visibleTo`.** A workspace is the repositories the viewer has a tie to (their own namespace's, their organisations', the ones they collaborate on), optionally one namespace's share of them. A public repository they have nothing to do with is not their work, and a private one they cannot read is in none of it: asking for a namespace they have no tie to answers an empty workspace, the same as one with nothing in it.
- **A row's state is read in the statement that reads the row.** `changeColumns` carries the newest version, the newest verdict, the open must-fix count and whether the agent is at work as correlated subqueries, each on an index by branch page. `changeStateOf` then orders them the way the contract's `ChangeState` says. It is a list's state, not the branch page's: it reads no checks and nothing of the viewer's.
- **"Mine" is the author or whoever connected the agent**, so a branch an agent writes for someone is theirs.
- **Suggestions** are other people's open branches, out of draft and not with their agent, with a version newer than the viewer's mark, that the viewer has not approved at the current head. Reasons come from rows that exist (assignee, a reviewed mark, a review of theirs, a version they pushed to the repository); there is no "review requested" in the schema, and nothing is inferred from file paths, which would be a call to the repository's object per row.
- **Activity is four reads, each newest first up to the limit**, merged: versions, reviews submitted, review runs that found something, merges. The newest twenty of all four are among the newest twenty of each.
- **`listThreads` is one statement over `git_issues`** behind the same `tiedTo`, archived repositories included: written by the viewer, assigned to them, or mentioning them. "Mentioned" is the description (someone else's) or a comment by someone else matching `mentionPattern`, the same scan `listMentions` makes. It pages by `updated_at` like the Changes list.
- **Mentions match text.** There is no table of mentions, so `listMentions` matches `@username` (`mentionPattern`, the same expression for Postgres and for the excerpt) against the comments and review comments of the viewer's repositories. That is a scan of those repositories' comments; a mentions table written when a comment is saved is what replaces it if it ever shows.

### Known gaps

- A version's commit stays readable by id (the API, raw, archive) until its ref is pruned, which is the point, and also means a secret pushed to a branch and forced away is still readable by the repository's readers for as long as the branch lives and thirty days more. There is no way to drop one version by hand yet.
- A fork's version copied late (its event was lost and a forced push has since moved the branch) has no base: the base repository can only import what the fork's branches still reach.
- The inbox counts comments and findings with a query per row of the page.
- A finding carries a version's number, not its lineage: on a branch deleted and made again, an old finding's numbers are the first lineage's.
- A review run killed mid-flight (the invocation, not the model) has what its finished reviewers used on the run and in the organisation's spend, and loses what the reviewer in flight had used.
- There is no search tool for a reviewer: the reader has none. It lists directories and reads files.
- A refusal by the model's safety classifiers fails that reviewer; the API's server-side fallback to another model is not used (not verified through AI Gateway).
- An instruction's delivery is claimed before the agent is told. A Worker that dies between the two leaves a row `delivered` that was not; T3 Code's `clientRequestId` makes a repeated send harmless, but nothing repeats it.
- Starting work with T3 Code waits on the environment inside the request: a clone that takes over a minute fails the request, and the retry finds the folder there and unregistered, which the person finishes in T3 Code (add the folder as a project).
- The model picker lists what `orchestrator_capabilities` lists without `search`: a model T3 Code leaves out of its short list can only be had by making it the project's default, which the picker then shows.
- An agent's token (`api/agent-token.ts`) is not checked against its asker again while it lives: a collaborator removed from the repository keeps recording on that one branch for up to six hours.
- An agent's token reads no branch page, version or diff through the API (`get_branch`, `get_version_diff` refuse it). A thread reads its own checkout.
- A branch-bound push token (`ref`, the app's agent sessions) is taken on the trace path, and `authorOf` then asks for a CI run by the token's `runId`, which an agent session's is not: by reading, such a token cannot record a trace. Not changed here.
- A branch's T3 Code environment is its connector's. Instructions other reviewers send are delivered with that person's sign-in, and stop being pushed when they remove the environment.

## MCP and OAuth (`src/mcp/`)

`https://git.infrawrench.com/mcp` and the authorization server its clients sign in through. `git/README.md` ("Agents and MCP") has what it is for.

### The server (`mcp/http.ts`, `server.ts`, `tools.ts`, `api.ts`, `mount.ts`)

- **The SDK, the one the app uses** (`@modelcontextprotocol/server`, the same version as `app/packages/web`). It serves both protocol eras: 2026-07-28 (the per-request `_meta` envelope, `server/discover`, the `Mcp-Method` and `Mcp-Name` header checks) through `createMcpHandler(..., { legacy: "reject", responseMode: "json" })`, and the earlier `initialize` handshake through a `WebStandardStreamableHTTPServerTransport` in JSON mode, routed by `isLegacyRequest`. Hand-rolling JSON-RPC would have been smaller and would have meant following two revisions of the specification by hand. It is 0.75 MB of the bundle unminified (0.49 SDK, 0.25 its schema library); the build picks the SDK's `workerd` shims, so the validator is the one that needs no `eval`.
- **Stateless, and every answer is complete when returned.** A fresh `McpServer` per request closes over that request's credential. JSON mode in both eras is load-bearing: the whole exchange runs inside one `withDb`, and a streamed answer would run the tool after the database client had closed. GET and DELETE are 405.
- **A tool is a request to the JSON API, made in this process** (`api.ts` `inProcessApi`): the same `GitApiHandler` instance `src/index.ts` serves `/api` with, handed a `Request` that carries the caller's `Authorization` header and nothing else of the MCP request. So authentication, `repoAccess`, a token's scope, what a job token reaches (`JOB_GROUPS`), archived repositories and the limits are the API's for a tool as for `curl`, and a tool works the day its endpoint does. `expectOk` turns a refusal into words for the agent: 503 `not_implemented` says the part is not on this server, 404 says missing or unreadable (the two stay one answer), 429 says how long to wait.
- **The request scope is re-entered by hand.** `mount.ts` captures `currentRequestScope()` and runs each API call inside it (`runInRequestScope`): `db` resolves through AsyncLocalStorage, and the SDK's scheduling between a request and a tool's callback is not relied on to carry it.
- **Tools are data** (`tools.ts` `TOOLS`): name, title, description, JSON Schema for input and output, whether it only reads, and `run`. Inputs are closed (`additionalProperties: false`) and checked by the SDK before `run`; outputs name what is promised and let the API's other fields ride along. The descriptions are the instructions an agent gets, `record_trace`'s above all: a change of behaviour changes them. `MCP_SERVER_VERSION` moves when a tool's inputs do.
- **Who a trace says wrote it**: `agent_name` when the agent gives one, else the client's own name where the protocol carries it on every request (2026-07-28), else the first product of its `User-Agent`, else `MCP client`. An earlier-era client names itself once at `initialize`, which a stateless server does not see again.
- **No prompts and no resources.** The server's `instructions` say how the tools fit together; nothing else earned a place.
- **Counted twice, on purpose**: the transport as a read against the principal (`admit` with a GET's shape), and each tool's API call as what it is.

### An agent's token (`api/agent-token.ts`, `agents.token`)

`iwj_` with the `agent` claim (client-core `git-job-token.ts`): a branch's full ref name. For an agent that works outside the app and cannot sign in through a browser.

- **An exchange, never a grant.** `POST /api/repos/:owner/:repo/branches/:branch/agent/token` takes `write` and a person (session or personal access token with `repo:write`) or an API key, and answers a token that can do less than its asker on one branch. It is the one place a token mints a credential, which `SESSION_ONLY` otherwise keeps to a browser: what it mints is narrower than what asked, expires in six hours and is stored nowhere. A job's token, a deploy key and an agent's own token are refused, so a token never renews itself. Refused for a closed page, a fork's branch and the default branch. `runId` is `agent:<user id>` of the asker, for the audit trail; nothing is decided from it.
- **Where it is a credential at all**: `/mcp` (`mount.ts`, `agentTokens`) and the API's trace, instructions and findings paths (`apiAcceptsAgentTokens`). Smart HTTP asks for `refTokens` only, and the archive, raw files and Terraform for nothing, so all of them refuse it: it clones and pushes nothing. A tool that calls another path (`get_branch`) gets the API's 401.
- **What it calls** is `AGENT_ENDPOINTS`, checked in the authentication middleware by group and endpoint: `traces.record` and `list`, `instructions.list`, `markDelivered` and `markAnswered`, `findings.list` and `report`. Not `statuses`, which a plain job token reports: a status is what a protected branch's required checks read.
- **Which branch**: `pageOr404` refuses it on any page whose head is not its branch in this repository (`ownPageOnly`), which covers every handler under `/branches/:branch`, present and future; the trace handlers, which take a branch by name, call `ownBranchOnly`. Another repository answers 404 as for any principal without access (`repoAccess`).
- **A trace it records has no author**, like a CI job's: the entry names its agent.
- **Six hours** (`GIT_JOB_TOKEN_MAX_TTL_SECONDS`) rather than a longer life: the thread asks again with the same command, so a long-lived token buys nothing and a leaked one costs more.

### Credentials on `/mcp`

- **The `Authorization` header and nothing else.** The handler builds a request that carries only that header and gives it to `authenticateRequest`, so the session cookie is never read here whatever a browser sent, and a personal token, an API key, a CI job's token and an agent's token for one branch (above) work as they do on the API. No credential is a 401 whose `WWW-Authenticate` names the resource metadata and the scopes (RFC 9728); a refused one adds `error="invalid_token"`.
- **Any origin may call it** (`oauth/protocol.ts` `CORS_HEADERS`: `*`, no credentials mode), and the same for the discovery documents, `/oauth/register`, `/oauth/token` and `/oauth/revoke`. None of them has an ambient credential for a foreign page to borrow, and a browser-based client cannot work otherwise. The specification's `Origin` check is against DNS rebinding of servers on a local network; an `Origin` that is not an origin is still a 403. `/oauth/authorize` gets none of this: it is a page.
- **Audience.** Tokens are this site's own, looked up by hash, so one presented here was issued here. `resource`, when a client sends it, must name this server (`isOurResource`: the endpoint or the site).

### The authorization server (`mcp/oauth/`)

- **Hand-written, over `git_access_tokens`.** `@cloudflare/workers-oauth-provider` was the alternative. It keeps clients, grants and tokens in a KV namespace, issues tokens of its own format, and is built to stand in front of a Worker's routes. Here that would have meant a second kind of bearer credential that `authenticateRequest` and `repoAccess` do not know, a second store beside Postgres for what a person may revoke, a KV binding to provision, and a token list that is not the one under **Settings > Access tokens**. The part of OAuth this site needs is small once the token is one it already has.
- **A grant is a personal access token** (`grants.ts`): a row of `git_access_tokens` whose id starts `mcp_`, named `<client> (MCP)`, with the scopes consented to. It authenticates everywhere a token does (the same token is the client's bearer and what its `git push` sends), is capped by `repoAccess` rule 2 like any token, and never reaches the `account` group. `account.listTokens` shows it with the others; its `expiresAt` there is when the grant lapses, not the access token's hour (`grantLapsesAt`).
- **No table was added.** What OAuth usually stores is sealed instead (`sealed.ts`: the session cookie's AES-256-GCM construction under `WORKOS_COOKIE_PASSWORD`, with the purpose sealed inside so one kind never opens as another, or as a session):
  - A registered client id (`iwc_`) carries the client's name and redirect URIs. `/oauth/register` writes nothing, so it cannot be used to fill a table. A client id cannot be revoked one at a time, which loses nothing: it is a name and addresses, and what is granted to it is a token.
  - An authorization code (`iwa_`, sixty seconds) carries the grant's row id. Exchanging it inserts that row, so the primary key makes a code single use: a second exchange finds the id taken, is refused, and revokes the row the first made.
  - A refresh token (`iwr_`) names the grant and the hash of the access token it was issued beside. Refreshing swaps the row's hash, compared on the old one (`rotateGrantedToken`), so a refresh token works once and the old access token dies with it. An older refresh token no longer matches: refused, and the grant revoked unless the row was refreshed in the last minute (two processes of one client sharing a stored token). The moment of the last refresh is `expires_at` minus an hour, which is why no column was needed.
  - A grant lapses thirty days after its access token expired without a refresh: a comparison on the same column.
- **Rotating `WORKOS_COOKIE_PASSWORD` ends every refresh token and every registered client id.** Access tokens keep working for their hour. A client then holds a client id the site no longer knows and has to be added again.
- **Clients** (`clients.ts`): a Client ID Metadata Document (an `https://` client id with a path; fetched with no redirects, five seconds, 64 kB, to a public host that is not this site, and kept fifteen minutes per isolate) or dynamic registration. Both are advertised; the specification prefers the first and deprecates the second, which is still what most clients use. Every client is public (`token_endpoint_auth_method: none`). Redirect URIs: `https`, `http` to loopback only, or an app's own scheme; never a fragment, credentials or this site. A loopback redirect matches on any port (RFC 8252).
- **`/oauth/authorize`** (`authorize.ts`):
  - The person signs in first (`/auth/sign-in?returnTo=` and back), before the client is looked at: a client id can be an address to fetch, and nothing is fetched for a visitor who cannot be counted. Signed in, the page is counted against them (`admit`).
  - Until the client and its redirect URI are known good, a problem is shown and nothing is sent anywhere. After that the client is told (`error`, `state`, `iss`), but the browser is redirected by itself only to a loopback address, or once the person pressed a button; for any other address the page shows the problem and a link. Registering costs nothing, so an automatic redirect to whatever a client registered would be an open one.
  - Consent is asked every time. A client id proves nothing about who presents it, so the click is the check. The page names the client, the scopes, the redirect URI's host, the document's address for a CIMD client, and warns when the redirect is to this computer.
  - The form carries the request sealed with the person it was shown to, for ten minutes. The POST rides on the cookie, so `authenticateRequest` takes it only from this origin. The page is its own document with its own policy (`default-src 'none'`, a nonce for its one style block, `form-action 'self'` plus the redirect's origin, which Chromium also holds a form's redirect to, `frame-ancestors 'none'`), which `serve` leaves alone.
- **PKCE with S256 is required**; `plain` and a missing challenge are refused. Every authorization response carries `iss` (RFC 9207) and the metadata says so.
- **Scopes**: `repo:read` and `repo:write`. Anything else a client asks for is ignored (`offline_access`, `openid`), `repo:write` brings `repo:read`, and a request naming neither gets both, which the page shows.
- **`/oauth/revoke`** ends a grant given either of its tokens, answers 200 whatever it was given, and leaves a token a person made by hand alone.
- **Logging.** `http/log.ts` redacts every `iw?_` value and the `code`, `refresh_token` and `code_verifier` parameters; nothing here logs a request's query or body.

### Known gaps

- A grant's `expiresAt` in the token list is its lapse date, which the UI labels as any token's expiry. The UI has no separate presentation for a connected application yet.

## Terraform (`src/terraform/`, `src/events/terraform.ts`)

`../terraform/NOTES.md` is the design and the whole flow; this is what runs in the Worker.

| File                        | Job                                                                                                    |
| --------------------------- | ------------------------------------------------------------------------------------------------------ |
| `terraform/state-store.ts`  | `WorkspaceStateStore`: the package's `StateStore` over a Durable Object's SQLite and R2.               |
| `terraform/state-serve.ts`  | What the object does with a request: the backend, restore, forced unlock. Reports the head afterwards. |
| `terraform/state-do.ts`     | `TerraformStateDO`: the shell that is Cloudflare about it.                                             |
| `terraform/client.ts`       | `stateClient(env, workspaceId)`, and `localStateClient` for tests.                                     |
| `terraform/access.ts`       | `decideStateAuth`: who may read, write and administer a state. Pure.                                   |
| `terraform/route.ts`        | `terraformState` and `terraformPlan`: the two routes, over a `TerraformDirectory`.                     |
| `terraform/directory-db.ts` | The directory over Postgres, and `recordStateHead`, the mirror.                                        |
| `terraform/scan.ts`         | `scanAt`: a ref's Terraform scan, cached in `git_terraform_scans` by tree.                             |
| `terraform/scan-views.ts`   | A scan row as the API shows it, a branch page's change, and the plan-wins rule. Pure.                  |
| `events/terraform.ts`       | Recording runs: branch page plans, merge applies, runs by hand.                                        |

- **One Durable Object per workspace** (`idFromName(workspaceId)`) holds the lock, the current version and the catalogue; the bytes are R2 objects `terraform/<workspaceId>/<serial>-<versionId>.tfstate`, written once each. `commit` uploads first and moves the head in one synchronous transaction that checks the head is still what the backend decided on, so of two writers one wins and the other's object is deleted again (`test/terraform-state.test.ts` races two).
- **The object never opens Postgres.** Every answer to a change carries the head in `x-infrawrench-terraform-head`; the front Worker mirrors it (`recordStateHead`: the `git_terraform_state_versions` row of a write, and the workspace's `current_*` and `lock_*` columns) and takes the header off. A mirror that fails is logged and not the client's problem: the object has answered, and the next change mirrors again. The handlers ask the object, not the row, before they delete a workspace.
- **Access** is `decideStateAuth` (`access.ts` has the table), and the answers are the route's: 401 with a Basic challenge for no valid credential, whatever the path names; 403 for a credential that may not, a missing repository and a missing workspace alike; never 404 or 204, which Terraform reads as "no state yet". People need `admin` on the repository: `write` is every member of an organisation, and a state holds every secret its workspace manages. A personal access token works for an administrator and needs `repo:write` (the directory asks `repoAccess` about the token and about the person behind it, `stateHolder`); it never administers, so deleting the state and unlocking without the lock's id are an API key's with `git:admin`, or the UI's. The routes read `Authorization` only: the session cookie is taken off before authentication, as on smart HTTP.
- **A run's job token** (`iwj_`, minted by server-core when the run is sent) carries its workspace's id and works for that workspace alone, for the run whose `ci_run_id` is its `run` claim, while that run is `queued`, `running` or `planned`. A plan's is `read`: it reads the state, takes the lock and posts its plan. An apply's is `write`: it writes the state too. Neither administers. A job token that names no workspace, or another one, is refused: without the claim it is not a credential here at all (401), with another workspace's it is a 403. The app's own token (purpose `terraform-link`) is bound to a workspace the same way; it reads a state and a plan's pricing inputs, and nothing else.
- **A plan** is posted by its job, summarised (`summarizePlan`), stored through server-core's `recordTerraformPlan` and dropped: it is never stored or logged. What pricing needs (`planPricingInputs`) waits at `terraform/<workspaceId>/plans/<runId>.json` and is deleted by the `GET` that reads it.
- **Runs.** `queuePullRequestPlans` plans the workspaces a branch page touches (`touchedRoots`: the comparison's changed paths against discovery at the head; every workspace when the storage cannot say), records a fork's as `skipped` and nothing for a personal namespace. `queueMergeApplies` records an apply as `queued` or `awaiting_approval` (`initialApplyStatus`). `recordRun` then starts, announces or notes the run through server-core, and a failure there leaves a queued row the app's pass starts.
- **The API** (`handlers/automation.ts`): `approveRun` is gated in the handler (`mayApprove`: a signed-in person with `admin` on the repository, or `ci:approve` in the organisation; never a personal access token); `createRun` starts a plan at once and an apply as approved only for someone who may approve; `discardRun` discards a plan or cancels a live run and its CI run; `forceUnlock`, `restoreStateVersion` and `downloadStateVersion` go to the object, and all three take `admin`; a CI run's output (`ci.getRun`, `ci.runLog`) is withheld from a caller without `write` when the run is a workspace's (`terraformOutputWithheld`), since Terraform prints values that are not marked sensitive; `listAccounts` is the picker; a workspace's and a resource's `monthlyCost` come from `managedResourceCosts`, through the caller's cost visibility, for a session with `costs:read`.
- **Tests.** `test/terraform-state.test.ts` runs the real `terraform` against the routes on Node stand-ins (apply, lock contention, restore, the 401 and 403 answers, the plan route) and the store's races. `test/e2e/terraform.test.ts` (opt-in, `GIT_WORKER_E2E=1`) does the same in workerd with the real `TerraformStateDO` and real job tokens. `src/__tests__/db/terraform.test.ts` (`test:db`) covers runs against Postgres: the CI run and its pipeline (no secret in it), a fork skipped, the approval gate, a plan's summary on the run, the commit and the timeline, and what a workspace manages on both sides with its cost.
- **Left to do.** A removed workspace's objects are not swept (`StateClient.destroy` exists and nothing calls it; the contract promises thirty days). Drift is not read from the app. `pluginName` on an account is its plugin id: the Worker has no plugin manifests to name it from.

## After the security review

`git/SECURITY-REVIEW.md` has the findings. The rules that came out of it, by area:

### Access

- **A branch page's or a comparison's head is the base, or a repository in its fork network** (`api/repos.ts` `headRepository`) that the caller can read, and a private head only goes into a private base of the same namespace (`mayProposeTo`). The consumer stops following a fork that no longer passes, and `updateBranch` does not copy a private base into a fork more people can read.
- **A personal token without `repo:write` changes nothing through the API** (`api/context.ts` `mayWriteThroughApi`), and no token claims or renames a username.
- **A job token reaches the `statuses` group only** (`api/middleware.ts`).
- **Only a branch page from the base repository itself queues Terraform plans** (`plansPullRequest`).
- **A workspace's accounts are shown with `accounts:read` and lent with `ci-access:write`** in the owning organisation; a resource's match is shown with `resources:read`; a lock's id and holder and state labels at repository `write`.
- **A transfer drops the workspaces' account links and managed resources** (`moveWorkspacesToOrganization`), and CI runs are shown only under the organisation that made them.
- The assignee list is for callers with `triage` and members of the owning organisation. Commit authors are matched only to people with a forge username.

### What can be read by id

- **A commit is read by id only when a ref reaches it**: the API (`queries/session.ts` `resolveCommitId`, memoised per ref state; `createBranch` is the exception, so a writer can restore a deleted branch), the raw and archive routes and `readPath` (`Repository.isReachable`, `refs/pull/*` included, which CI needs), and `exportPack`, which sends another repository only what the source's own branches and tags reach.

### Pushes

- **A push writes `refs/heads/*` and `refs/tags/*` and nothing else** (`policy.ts` `namespaceRefusal`), with or without a policy. A ref that would be a file and a directory at once is refused. The forge's own path refuses deleting HEAD's branch too.
- **A pushed pack passes core's `ObjectFsck`** and may inflate and rebuild 8 GiB at most (`maxInflatedBytes`). Packs the server makes (repack, a fork's copy, an import) are not held to either.
- Stored `ref-delta` chains are followed 4 096 deep at most.

### HTTP

- **Smart HTTP ignores the session cookie.** Raw and archive take it (the UI's images and download links).
- **Raw files** (`transport/http/raw-headers.ts`): raster images inline with their type; SVG and PDF with their type as a download; UTF-8 text as `text/plain`; everything else `application/octet-stream` as a download. Always `Content-Security-Policy: default-src 'none'; sandbox`, `nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `private, no-store`, and a file name that cannot end a header. These headers are the whole defence while raw files share the site's origin; a separate origin for them is the stronger answer and is not built.
- A request body in an encoding other than gzip is a 415, and a fetch's body is 32 MiB at most once inflated.
- **Archives** leave out names that could land outside the unpack directory, refuse a directory over 1 MiB and stop at 500 000 entries.
- **Every `/api` answer is `private, no-store`** with `Cross-Origin-Resource-Policy: same-origin`; pages add `Cross-Origin-Opener-Policy: same-origin` and `base-uri 'none'`.
- **Admission** (`http/admission.ts`, `http/rate-limit.ts`): a caller without a credential is counted by address (an IPv6 /64) against budgets for cheap reads, heavy reads and writes, and 60 refused credentials in ten minutes refuse that address's credentialed requests for the rest of the window. A caller who authenticated is counted by who they are (`Admission.admit`, `subjectOfPrincipal`: a person by id whichever credential they used, an API key, a deploy key, a CI run) against the signed-in budgets, four times the anonymous ones: by the API's `Authentication` middleware and by the Git routes (smart HTTP, raw, archive), each right after it resolves the principal and before it looks anything up. Heavy reads are a diff, a blame, a comparison, a filtered history, the file table's last commits, an archive, a raw file, a clone or fetch and a search (`classify`). Counts live in the six `RL_*` Rate Limiting bindings (`ratelimits` in `wrangler.jsonc`, per Cloudflare location, approximate by design), else the data centre's cache, which is what local development and the tests use; `http/__tests__/bindings.test.ts` holds the bindings' limits to `DEFAULT_RATE_BUDGETS`. Git over SSH is not counted here.

### SSH

- **The key is looked up again before every command**, so a removed key stops working on a connection that is already open (a command that is running finishes).
- Failed authentication is counted per IPv6 /64; an IPv4 address written inside IPv6 counts as that address.
- The client's version string and an error's message are quoted, escaped and cut at 80 characters in the log line.
- The command parser trims ASCII blanks only and refuses a path that starts with `-`.

### The reader

- New `ReaderLimits`: `treeWalkEntries` (200 000), `lastCommitsEntries` (1 000 000), `diffCountLines` (4M), `diffPageBytes` (4M characters), `diffPageCompared` (2M lines), `shownMessageBytes` (64 KiB), `listedMessageBytes` (4 KiB). The file table walks only the names it lists. A git-ops `limit` refusal is `too_large` (422). A trial merge that was refused is remembered like one that succeeded.

### Logging

- **A fetch that sent a pack logs one line** from the object when it ends (`repo-do.ts`, `onEnd`): the repository's id and numbers, nothing of the request.
- **Nothing passes an error object to `console`.** `http/log.ts` `describeError` writes the class, the message without a statement's parameters or a schema error's value, a few frames and the causes, with anything shaped like a credential cut to its kind and control characters removed.

## Push mirrors (`src/mirror/`, `src/jobs/`)

Settings > Mirrors keeps another Git host equal to a repository here. `git/MIGRATION.md` is how this monorepo uses it with GitHub as the mirror.

| File                      | Job                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------- |
| `mirror/address.ts`       | Where a mirror may push: public `https`, no credential, query or fragment in it, never this site. |
| `mirror/refs.ts`          | Which refs are carried (branches and tags) and the exclude patterns. Pure; the object reads it.   |
| `mirror/plan.ts`          | The target's refs against ours, as pushes in order. Runs in the repository's object.              |
| `mirror/sync.ts`          | One run: advertisement, plan, a pack a push, the report. No database, no clock, no log.           |
| `mirror/store.ts`         | `git_push_mirrors`: the rows, the sealed credential, generations, the lease, the retry schedule.  |
| `mirror/job.ts`           | What the jobs queue runs: claim, open the credential, `syncMirror`, record.                       |
| `jobs/consumer.ts`        | The `infrawrench-git-jobs` consumer, shared with issue imports.                                   |
| `jobs/sweep.ts`           | Every two minutes: what is owed a run and carried by no message. Hourly: every mirror is checked. |
| `api/handlers/mirrors.ts` | The settings API. The protocol is `@infrawrench/git-protocol` `send-pack.ts`.                     |

- **It mirrors a state, not an event.** A run asks the target for its refs (`GET info/refs?service=git-receive-pack`), asks the repository's object for a plan against them, and pushes the difference. The push event only says a run is owed. So runs can be repeated, merged and lost without harm: whichever finishes after the last push leaves the target right. A push whose event never reached the queue (the object's send is not retried) is caught by the hourly pass, which marks every mirror as owed a run; a run that finds nothing to do is one request.
- **Ordering.** Three things, each enough for the common case and together for the rest. (1) `pendingGeneration` goes up with every push and `syncedGeneration` is the pending value a finished run started from, so a push that lands during a run leaves the mirror owed another. (2) One run at a time holds the lease (`claimMirror` is one `UPDATE` that only succeeds when nobody holds it), reads the refs after taking it and renews it before every push it makes, stopping when it is no longer the holder; a message that finds the mirror held does nothing, and the holder answers `again` when it ends with a run still owed. (3) Every command names the value the target advertised, so a ref somebody else moved in between is refused by the target, not overwritten. `src/__tests__/db/mirror.test.ts` holds a run just before its push, lands a newer push and its message, and checks the target ends at the newer commit.
- **Objects are never rewritten.** The pack is this repository's stored entries (`mirrorPack`, the path a fetch uses), so every id is the same on both sides; `test/mirror.test.ts` compares `rev-list --objects --all` of both. The pack stands on its own (`thinBases: null`): nothing is known of how the target stores a base.
- **Planning runs in the object** (`RepoDO.mirrorPlan`, `mirrorPack`), where the commit graph is: whether an update is a fast-forward and how many commits a ref brings are walks, and a walk in the Worker is a call an object. The credential never goes there: the Worker makes both requests and pipes the object's pack stream into the second.
- **Size.** One push when there is little to send. A branch bringing more than `stepCommits` (2 000) commits goes in parts along its first-parent line, oldest first, each its own push to that branch, so the target is always at a real commit of the branch and a run that stops is carried on by the next. A pack is streamed from the object through the Worker into the request body (chunked), counted on the way and cut off at `maxPackBytes` (1 GiB; GitHub refuses a push over 2 GiB), after which the run starts again with parts a quarter the size, down to 25 commits. A run stops starting pushes after ten minutes (`partial`) and is sent again at once. Not measured in production: a Worker's memory while it pipes a large pack (it holds no more than the stream's buffers in Node), and whether a fifteen-minute consumer can finish a part of a history with very large blobs.
- **Tags three a push** (`maxTagsPerPush`): GitHub creates no event, and so starts no workflow, for tags that arrive more than three at once. Branches go up to 500 a push.
- **Force.** On (the default), the target's branches and tags are made equal: updated whatever their history, and deleted when they are not here. Off, branches are only created and fast-forwarded and nothing is deleted; what differs is listed with the reason. Deletions go first, in a push with no pack, so a branch `a` that became `a/b` can be made.
- **Exclude patterns** leave a ref alone on both sides (not pushed, not deleted), which is what makes a target with refs of its own usable: `dependabot/**`, or `refs/tags/**` while release workflows on the target still create their tags there. `*` within a segment, `**` across; a pattern starting with `refs/` is matched against the whole name, any other against the short name of branches and tags alike. Only `refs/heads/*` and `refs/tags/*` are ever carried: never `refs/pull/*` or a version's ref.
- **The address** is checked when saved and again before every run: `https` only, no user or password (they are fields of their own), no query or fragment, a host `blockedHost` (`images/proxy.ts`) lets through, and not this site. `redirect: "manual"` on both requests, and a redirect is an error that says to enter the new address, so the host that was checked is the host that is reached. `allowLocal` exists for the tests' Git host on 127.0.0.1 and nothing in the Worker sets it.
- **The credential** is sealed with server-core's `encrypt` under `ENCRYPTION_MASTER_KEY`, bound to its row (`gitMirror:<id>:credential`), sent as HTTP Basic with the mirror's user name (`x-access-token` by default, which GitHub takes for a personal access token and an installation token alike). No endpoint returns it, and changing the address needs it entered again, so a stored credential is only ever sent to the host it was entered for. The endpoints are `admin` and session only (`RequiresUser`): a token cannot add a mirror.
- **What is stored and logged of a failure.** `last_error` is one of the sentences written in `send-pack.ts` and `sync.ts` (a status code at most), and `last_result.refused` holds the target's reason for a ref, cut to 200 printable characters. A network error's own message can name the address, so it is replaced by "The target could not be reached". The log line is the mirror's id and the kind of failure. Tests assert the address, the credential and `Basic` appear in neither.
- **Retries.** A failed run sets `next_attempt_at` a minute out, then twice as long each time up to an hour; the sweep sends it when due. A push, **Sync now** and any change to the mirror try at once (the last two reset the count). The queue's own retry is only for the consumer failing (the database away).
- **Without the queue** (`JOBS` unbound: tests, a Worker deployed before the queue was made) the sweep runs up to two jobs itself every two minutes, so mirrors work, slowly.
- **Limits**: five mirrors a repository, fifty exclude patterns, 5 000 of the target's refs offered as haves, fifty refs listed in a result.

### Known gaps

- **Nothing is fetched from a target**, by design: a mirror is one way.
- **`http.extraHeader`-style authentication and SSH targets** are not there. Basic over HTTPS is what every large host takes for a token.
- **A GitHub App installation token** works as a credential but lasts an hour; nothing mints one. A mirror to GitHub uses a fine-grained personal access token.
- **A single commit over `maxPackBytes`** cannot be mirrored.
- **The workerd path is not run by a test**: the suites drive `Repository` on the Node stand-ins and the real `git http-backend`. `RepoDO.mirrorPack` returning a stream over RPC is the same shape as `exportPack`, which `test/e2e` does cover.

## Issue import (`src/import/`)

Settings > Import brings a GitHub repository's issues in. It runs in the forge, as an administrator's action, rather than as a client of the API: an import writes other people's issues with their original dates, which the API rightly lets no caller do, and the jobs queue gives it paging, resuming and rate-limit waits. `github.ts` is the client, `store.ts` the rows, `job.ts` one step; `api/handlers/imports.ts` starts, lists and cancels.

- **What a step does.** A message names an import (`git_issue_imports`). The step claims it, reads pages until about twenty seconds or forty requests have gone, saves `phase` and `progress.page` after every page, and answers `again: 0`. Phases: `labels`, `milestones`, `issues`, `comments` (the repository-wide list, each comment attached by the number its `issue_url` ends in), `finish`. A page read twice writes the same rows, so nothing depends on a step ending cleanly.
- **The claim is `updated_at`.** There is no lease column. A step stamps the row when it claims it and with every page it saves; a second message that finds the stamp younger than 45 seconds does nothing. A step that ends with more to do writes a stamp a minute old, so the next message claims at once, and the sweep still finds an import nobody has touched for three minutes. An import whose first message could not be sent (no queue bound) is stamped old enough for the next sweep.
- **Rate limits.** 403 or 429 with `x-ratelimit-remaining: 0` waits until `x-ratelimit-reset`; `retry-after` waits that long; a secondary limit that names no time waits a minute. The step writes `resume_at` and answers `again` with the wait, 900 seconds at most; a message that comes back early asks to be sent again and makes no request, and the sweep leaves a waiting import alone. GitHub being away (a 5xx, a timeout) is tried again a minute later for up to three days. 401, a 403 that is no rate limit, 404, 410 and a redirect fail the import with a sentence written in `job.ts`.
- **One host.** Requests go to `https://api.github.com`, a constant. The owner and the name are percent-encoded path segments, and `redirect: "manual"` makes a redirect (a renamed repository) an error, so the token is never sent anywhere a response points. `X-GitHub-Api-Version` is `2022-11-28`.
- **The token** is sealed with server-core's `encrypt` (`gitIssueImport:<id>:token`), opened by the step, and both columns are nulled when the import ends, whichever way. A `GitHubError` carries a status and one of a few fixed sentences; nothing GitHub answered is logged or stored.
- **Idempotency keys.** An issue is `(repository, 'github', GitHub's issue id)`, a comment `(repository, 'github', GitHub's comment id)`, on the two partial unique indexes. A label is its lowercased name (one that exists is left alone, colour and description included). A milestone is its title (state, due date and description follow GitHub's).
- **Running it again.** A new import after one that finished asks GitHub only for what changed since that one began (`progress.since`, the `since` parameter of both lists). What it reads is updated to match GitHub, including the state, so an issue closed here and then changed there is open again if GitHub says so; an issue that did not change there is not read and keeps what was done to it here. A deleted issue is not brought back unless it changes at GitHub.
- **Numbering.** Issues and branch pages share `git_repositories.next_number`. Before the first page of issues the step asks GitHub for its newest issue or pull request and raises `next_number` past that number; this happens first, not after the phase, so that a thread opened here while the import runs, and an imported issue whose number is taken, are both numbered past everything GitHub has. An imported issue then takes its GitHub number when no thread here has it, and the next number otherwise, with the GitHub number always kept in `import_number`. The choice is made in a transaction that locks the repository's row, the row `allocateNumber` updates, so a thread opened at the same instant is numbered before or after and never the same. GitHub's pull requests are gaps that stay empty: `#N` in old text must not come to mean something else. An issue already imported keeps its number. After the last page, and again at `finish`, `next_number` is raised to one past the highest number in use.
- **Authors.** One `GET /users/{login}` per distinct login per import, remembered in `progress.authors` (a bot's and a deleted account's are never asked). A login is an account here when (a) the address on its public GitHub profile is an account's `users.email`, or a verified, active commit email that counts in this repository (its organisation's, for someone still a member; the owner's own in a person's namespace), or (b) it is, case-insensitively, the username of someone who already reaches the repository: its owner, a member of the owning organisation, or a collaborator. (b) has that condition so nobody gets a stranger's issues by registering the stranger's GitHub name. Otherwise `author_user_id` is null and the views show `import_author` ("mona on GitHub"). Assignees go by the same rule and unmatched ones are dropped. `closed_by_user_id` is left null.
- **What is kept.** The body as written (nothing is added to it), `created_at`, `updated_at`, `closed_at`, the lock, and the state: `not_planned` and `duplicate` are `not_planned`, every other closed issue is `completed`. A comment whose `updated_at` is after its `created_at` is marked edited.
- **What does not happen.** The rows are written directly: no timeline event, no mention or cross-reference, no notification, no CI, no review. Counters are not incremented either: `recountAfterImport` sets `comments_count`, each milestone's open and closed counts and the repository's open issues from the rows when an import ends (done, failed or cancelled), so a second run cannot drift.
- **Not imported.** Pull requests and their comments (the issue list returns them with a `pull_request` key; they are skipped and counted nowhere), review comments, reactions, the events between comments, attachments (a body's image links still point at GitHub and load through the image proxy), projects, and who closed an issue.
- **Limits.** One import at a time per repository (409). A title is cut at 256 characters and a body at 262 144, the API's own limits. `progress.authors` grows by one entry per distinct login.
- **Known gaps.** A secondary rate limit always waits a minute rather than backing off further each time. The sweep runs at most two jobs itself where no queue is bound, so an import there moves forty requests every two minutes.
