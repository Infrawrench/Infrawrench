# git.infrawrench.com

A Git forge on Cloudflare: Workers for the edge, a Durable Object per repository for refs and coordination, R2 for packfiles, and the app's Postgres (through Hyperdrive) for everything a forge knows about people and repositories. It is its own site with its own UI, not a part of the app; the app links to it and it links back.

This file is the design every package builds against. Each package's own notes go in its `NOTES.md`; settled decisions move up into this file and KNOWLEDGE.md.

## Packages (`git/packages/*`)

Small packages with one job each, in the spirit of `plugin-architecture/`. The pure ones run anywhere (Web Streams, `Uint8Array`, WebCrypto) and are tested in Node against the real `git` and `ssh` binaries; only `worker` knows it is on Cloudflare.

Rules that keep it modular:

- A pure package never imports `cloudflare:*`, `node:*` (outside tests) or `worker`.
- Interfaces live with their consumer (`protocol/src/backend.ts`, `ssh/src/server.ts`); the implementer changes with them in the same commit.
- The worker is a composition root: each route, DO and queue consumer is its own module, and `src/index.ts` only wires them.
- Nothing in these packages names a provider plugin; Infrawrench knowledge comes from server-core and the app's API, as elsewhere.

## Identity, namespaces, access

- **Sign-in is WorkOS AuthKit**, the same users as the app (the `users` table), its own redirect (`https://git.infrawrench.com/auth/callback`) and its own sealed, host-only session cookie. First sign-in asks for a username.
- **Namespaces** (`git_namespaces`): a case-insensitive unique slug owned by a user or by an Infrawrench organisation. An organisation's namespace is claimed by someone with `git:admin` in it, here (Settings > Organisations) or in the app (Settings > Git), by the same rules: a signed-in browser, Git turned on for the organisation, and a paid plan for the first claim. Slugs and repository names: `[A-Za-z0-9._-]`, no leading dot or dash, not ending in `.git`, with a reserved list (routes, `api`, `auth`, `explore`, ...).
- **Profiles**: a namespace's page shows a name, a bio (plain text, 280 characters, addresses linked), a website and a location. A person edits theirs in Settings > Profile; an organisation's administrators (`git:admin`) edit theirs from its page and may upload its picture, which is kept in R2 under `avatars/<namespace id>/` and served from this origin at `/-/avatar/...` (`worker/NOTES.md` "Profiles and uploaded pictures"). A person's picture is their account's.
- **Commit checks**: wherever a commit is summarised its combined status is a button that lists each check and links to the run's page (`web/NOTES.md` "Commit checks and profiles"). A status Infrawrench CI wrote names its run (`git_commit_statuses.ci_run_id`, `CommitStatus.runId`).
- **Bot accounts**: `claude` and `cursor` are the accounts commits made with those tools are shown under, by the address the tool writes (`noreply@anthropic.com`, `cursoragent@cursor.com`). They are a fixed list in client-core (`git-bots.ts`), not rows: nobody signs in as one or takes its name, and each has a page with its picture and a Bot badge.
- **Commit emails**: a member adds extra addresses in an organisation (Settings > Organisations), and commits with one are shown as theirs in that organisation's repositories only, from the moment it is added. Verifying one with a code mailed to it is optional: it marks the address and, in an organisation, makes it that member's alone. A person does the same for the repositories of their own namespace (Settings > Profile), and those count there only. When a code is asked for the app's poller sends it; the Worker holds no mail key.
- **Organisations are Infrawrench organisations.** Membership and roles come from the app (WorkOS memberships, the role/permission system). New permissions in the catalog: `git:read`, `git:write`, `git:admin`. Per-repository collaborators add access for individual users: `read`, `triage`, `write`, `admin`.
- **Visibility**: `public` (anyone, signed in or not, can read and clone) or `private` (only people with access). Forks of a private repository stay private and inside the same owner's reach, and a fork within the same owner starts with its parent's collaborators, as on GitHub.
- **Credentials for git**: HTTPS takes Basic auth with a personal access token (`iwg_…`, hashed, scoped `repo:read`/`repo:write`, optional expiry) or an Infrawrench API key (`iwk_…`, the organisation's repositories, its own role). SSH takes the user's git SSH keys (`git_user_keys`, separate from the organisation's server keys) and deploy keys per repository. CI jobs get a short-lived, repository-scoped job token. None of these is ever logged.

Access resolution is one function, `repoAccess(principal, repo) -> none | read | triage | write | admin`, used by HTTP, SSH and the API alike.

## Storage

- **R2 bucket `infrawrench-git`**: `repos/<repoId>/packs/pack-<id>.pack` and `.idx`. Repositories are keyed by id, never by name, so renames and transfers move nothing. A pack's id is time-ordered and random, not its checksum: the key has to exist before the first byte is uploaded.
- **`RepoDO`, one per repository** (`idFromName(repoId)`), SQLite: `refs`, `HEAD` and the pack catalogue. There is no row per object: an object is found through each pack's `.idx`, loaded from R2 and held in memory, which costs no billed row writes per pushed object (the worker's notes have the numbers). Every ref change goes through one synchronous transaction that compares each ref with the value the caller saw, so a push, a merge from the UI and a branch deletion cannot race, and nothing needs a lock.
- **Pushes stream.** `ingestPack` writes the incoming pack to R2 as it arrives (multipart) while indexing it, resolving deltas with bounded memory (bases read back by range), checks that every object's references resolve, and leaves the pack unpublished; `updateRefs` publishes it in the same transaction as the refs that reach it. A Worker request body is capped by the zone's plan (100 MB on Free/Pro), so very large pushes go over SSH, which has no such cap.
- **Fetches reuse stored bytes.** A full clone is the stored pack (or every entry of every pack, copied); anything else walks history and copies the chosen entries, rewriting only delta headers.
- **Repacking** runs from the DO's alarm once a repository has many small packs: a run of adjacent packs is merged into one, verified like a push, and the old files are deleted a day later.
- **Forks copy** the parent's packs within R2, so the two repositories share nothing afterwards.
- **The API reads inside the object.** Everything the JSON API asks of Git (a file table with its last commits, a diff, blame, a merge) is one call from the Worker to the repository's `RepoDO`, which runs `ops` next to its packs and keeps the commit graph in memory while it is awake; a walk in the Worker would be a call per object. The answers a front page needs (the file table's last commits, the commit count) are written down per commit, so a woken object does not walk history again. A merge from the UI writes its objects and then moves the branch by the same compare-and-swap a push uses, with the same event.
- **A branch proposed from a fork lives in the base repository.** Its head's objects are copied from the fork's object into the base's (one object asking the other for a pack) and a hidden ref (`refs/pull/<n>/head`, never shown to a client) points at them, so comparing, merging and CI all read one repository.
- **Postgres** (server-core `db/git-schema.ts`, migrations through `drizzle-kit generate`): namespaces, repositories, collaborators, keys and tokens, issues, branch pages (in `git_pull_requests`), reviews and comments, labels, milestones, stars, protected branches, commit statuses, Terraform workspaces and runs.

## Transports

- **Smart HTTP**: `GET /<owner>/<repo>.git/info/refs?service=…`, `POST /<owner>/<repo>.git/git-upload-pack|git-receive-pack`, v2 via `Git-Protocol`. The front Worker resolves the principal, the access and (for a push) the protected-branch rules, then hands the body stream to the repository's DO over one internal `fetch`; the DO runs `protocol` against its backend and streams the answer back. The DO never opens Postgres.
- **SSH**: `git@git.infrawrench.com:<owner>/<repo>.git`. The host is the Worker's `SSH_HOST` variable, the one place it is named: clone URLs are built from it and the Spectrum application is created under it, so it can become a host of its own (`ssh.git.infrawrench.com`) by changing that value. A Spectrum application on port 22 forwards TCP to the Worker's `connect(socket)` handler (inbound TCP, public beta; `startTls` is not available on inbound sockets, which SSH does not need). The Worker runs the `ssh` server; `exec` resolves the repository and access the same way HTTP does and opens the same internal `fetch` to the DO with both bodies streaming at once (`statelessRpc: false`).
- **Push mirrors**: a repository can keep another Git host equal to itself (Settings > Mirrors). After a push the consumer marks the repository's mirrors as owed a run and a job on the `infrawrench-git-jobs` queue pushes the difference to the target over smart HTTP, with this repository's own objects, so commit ids are the same on both sides. One run at a time per mirror, each from the refs as they are when it starts, so a later push is never overwritten by an earlier one's slow run. `packages/worker/NOTES.md` ("Push mirrors") has the design; `MIGRATION.md` is how this monorepo itself moves here with GitHub as its mirror.
- **After a push** the DO sends an event (`{ repoId, actor, updates, at }`) to the `infrawrench-git-events` queue. The consumer updates the repository row, opens a branch's page at its first push and updates the pages of the branches that moved, closes issues a commit fixes, and starts CI and Terraform plans. A push that brings a branch's changes into its page's base, however they got there (a squash or merge made elsewhere, a cherry-pick, a fast-forward), marks the page merged and deletes the branch; deleting a branch merges or closes its page (`packages/worker/NOTES.md`, "Merged without the merge button").

## The forge

Code (tree, file with highlighting, raw, blame, history, archive download), branches, tags, compare, commits with diffs, issues (labels, milestones, assignees, comments, import from GitHub), branch pages (one for every branch: versions, diff, inline review comments, approvals, merge commit / squash / rebase, conflict check, protected branches with required approvals and required checks), stars, forks, explore and search, user and organisation pages, repository settings (rename, transfer, visibility, collaborators, deploy keys, protected branches, push mirrors, issue import, delete), personal settings (SSH keys, tokens, username). Every page has link preview tags and an image (`/-/og/...`) drawn as a signed-out visitor sees it (`packages/worker/NOTES.md` "Link previews").

## Agent work review

Review is what the forge is for, and a branch is the unit of it: a versioned record of work that people and agents read along the way, not only at the end.

- **Versions.** Every push to a branch other than the default branch records a version (v1, v2, ...), forced pushes and rebases included. Each keeps its commit, so an older version can be read and compared after the branch has moved on. The commits are kept until thirty days after the branch is merged or deleted; the versions themselves, with their numbers, traces, findings and review comments, are kept for good. A version whose commits are gone stays in the strip, and its diff says so (the newest version of a merged branch still shows the whole change, read from the merge or squash commit).
- **Every branch has a page.** Each branch of a repository but its default one gets a branch page, as a draft, the first time it is pushed, at `/<owner>/<repo>/branches/<branch>` (the branch's own slashes kept; Commits and Checks are `?tab=`). Merging, protected branches, statuses, reviews and review threads are the page's, and the repository's **Branches** tab lists the pages, open, merged and closed. A fork's branches get no page on push: **Propose to <parent>** on the fork's branch opens one in the parent, named `<fork owner>/<fork name>:<branch>` and marked as from a fork, and it never gets secrets, a Terraform plan or a trusted CI run. A page's conversation shares the issues' number sequence (`#12` in a comment still links to it), but no page and no URL shows the number. There is one UI for everyone.
- **Diffs between versions** compare each version against its own base, so a rebase alone shows nothing: the whole change, one step, or everything since the version a person last marked as reviewed. A review comment is written on a version and carries forward while its lines stand; when they change, it says which version answered it.
- **Traces.** An agent records the ask, its steps, decisions, evidence and doubts through the API or the MCP server; entries wait on the branch and belong to the version its next push makes. Secrets are masked before an entry is stored.
- **Findings.** Review agents, switched on per repository, leave line-anchored findings (`must_fix`, `should_fix`, `note`) with evidence. An open must-fix finding holds the merge until it is fixed, dismissed, or overridden by an administrator, on the record.
- **The record is on the default branch too.** The commit a branch was merged as (the merge commit, the squash, or the last rebased commit) has a Review section: the ask its trace recorded, how many versions it went through, and every finding with how it was settled (fixed in which version, dismissed by whom and why, open at the merge, or merged past by an administrator and why). A blamed file marks the lines a merged branch's findings were about, and a file lists the findings merged branches left on its path. Every one links to the finding on its branch page. Findings are listed on a branch page whenever there are any, whether or not the repository's own review agents are on.
- **Review agents are the forge's own.** On each new version of an open branch they read what changed (and the repository around it, the author's trace, the checks that ran, the Terraform plan) and record findings. A general reviewer, and ones a repository adds: security, tests, Terraform, intent (does the change do what the branch's description asked). Evidence first: a finding says how the reviewer knows, and one that cannot is shown folded, as a question. A reviewer never approves or merges; it has no way to. A dismissal is remembered across versions, a finding the next version resolves is marked fixed in it, and a must-fix finding on an agent's branch goes back to that agent as an instruction. Runs are billed to the organisation that owns the repository, from its AI spend; a person's own namespace has none. A reviewer of your own reports through the API under its own name.
- **Instructions.** A reviewer sends a comment, a finding or a note to the agent that wrote the branch; the version that answers it says so. What the agent is told is written out when it is sent. The forge tells an agent it can reach itself (a T3 Code thread); every other agent asks for its instructions and marks them delivered and answered.
- **Any agent** takes part through the MCP server (below) or the API. A branch page names the agent behind it: an Infrawrench agent session (the default), a T3 Code thread in one of the person's environments (the forge is an OAuth client of that environment), or anything else that speaks MCP or the API.
- **Starting work** from an ask makes the branch and opens its page as a draft, with the ask as its description, then starts the agent where it can: it launches a T3 Code thread on a worktree for the branch, or links to the app, which starts an agent session that clones the repository with a job token good for that one branch. The app links to the forge and the forge links back; neither embeds the other.
- **T3 Code.** A person connects an environment by its public `https` address (the one T3 Connect gives) under Settings > T3 Code. The forge is an OAuth client of the environment's MCP server: it registers itself, signs in with PKCE, keeps the token sealed, and calls only public `https` addresses, with no redirects followed. The thread pushes with the Git credentials on its own machine; nothing of the forge's is sent to it. Its first message teaches the agent every marker (trace kinds, instructions, findings, a CI job's notes) and how to get a token of its own for the branch: it exchanges the machine's Git credential for one that writes that branch's markers and nothing else, for six hours.

`packages/worker/NOTES.md` ("Versions and review") has how versions are recorded and kept, and which parts are built.

## Agents and MCP

`https://git.infrawrench.com/mcp` is a Model Context Protocol server (Streamable HTTP, stateless, the 2026-07-28 revision and the earlier `initialize` handshake). An agent's client is given that address and nothing else: `claude mcp add --transport http infrawrench-git https://git.infrawrench.com/mcp`.

- **The tools are the review loop**: `whoami`, `list_my_branches`, `get_branch`, `get_version_diff`, `record_trace`, `list_instructions`, `mark_instruction_delivered`, `mark_instruction_answered`, `list_findings`, `report_finding`, `start_work`. Each is a wrapper that calls the JSON API in the same process with the caller's credential, so what a tool may do is what the API lets that credential do, decided in the one place it always is (`repoAccess`). A tool whose endpoint is not built answers that in words.
- **A client signs in with OAuth 2.1**, and the forge is its own authorization server: the two discovery documents under `/.well-known/`, a client id that is either the address of a Client ID Metadata Document or made by `/oauth/register`, PKCE (S256 only), `/oauth/authorize` (a consent page on the site's own sign-in), `/oauth/token` and `/oauth/revoke`. What a client is granted is a personal access token like any other (a row of `git_access_tokens`, `iwg_`, `repo:read` and `repo:write`), valid for an hour and renewed with a refresh token that works once. It is listed under **Settings > Access tokens** as `<client> (MCP)` and revoked there.
- **Headless agents bring a token**: a personal access token, an organisation's API key, or a CI job's token, as `Authorization: Bearer`. A job's token records traces on the branch its run is of and does nothing else.
- **Nothing new is stored.** A registered client id, an authorization code and a refresh token are sealed values that carry what they stand for, and a grant is the token's row. There is no table of clients, codes or sessions.

`packages/worker/NOTES.md` ("MCP and OAuth") has the decisions. The user documentation is `features/git-agents-and-mcp.md` on the website.

## Infrawrench CI

Repositories here run Infrawrench CI the same way GitHub ones do: `.infrawrench/ci/*.yml`, on push and on a branch page's updates (a pipeline's `pull-request` event), through `server-core/src/ci/`. A run's source is either a GitHub installation or a git.infrawrench.com repository; the runner fetches the commit over smart HTTP with a job token. Results show as commit statuses and checks in the repository UI (a CI tab per repository, a status on every commit and branch page) and in the app's CI tab, which links to the commit here. Billing is CI's existing outbox.

A run is an organisation's: the one that owns the namespace. A person's own namespace has none, so its repositories run CI, and review agents, in the organisation its owner connected it to, chosen with the username and changed under Settings > Profile. The connection lasts only while they are a member there. Such a repository keeps its own secrets and variables, is lent only what an administrator of the organisation lends it by name, and is otherwise untouched: it is still the person's, and the organisation's members get nothing in it (`packages/worker/NOTES.md`, `NOTES-ci.md`).

## Terraform

A repository with Terraform roots gets an Infrastructure tab.

- **Detected configurations**: every root of the default branch, read from its files in one walk of the repository's Durable Object and cached by tree (`git_terraform_scans`): backend, providers and versions, modules, resource counts, and an estimate of its monthly cost from configuration with list prices, priced by the app's `git-terraform` pass. What could not be priced is listed beside the total. A branch page shows the configuration cost change of the roots it touches that no plan has priced.

- **Workspaces**: a root directory plus a name, mapped to Infrawrench connected accounts whose credentials a run gets as environment variables (never written to the repository).
- **State**: the HTTP backend at `https://git.infrawrench.com/<owner>/<repo>/terraform/<workspace>/state` (with `lock`/`unlock`). A Durable Object per workspace (`TerraformStateDO`) serialises the lock and the serial and lineage checks; every version's bytes are kept in R2 (`terraform/<workspaceId>/<serial>-<id>.tfstate`) and listed in the UI. Reading and writing take `admin` on the repository (every member of an organisation has `write`, and a state holds every secret its workspace manages) or the live run's job token; deleting and force-unlocking take `admin` and are never a personal access token's; and a refusal is 401 or 403, never 404 (Terraform reads a 404 as "no state" and plans to create everything). The backend takes tokens only, never the session cookie.
- **Plan on branch, apply on merge** (or on approval), run on Infrawrench CI as ordinary CI runs of the repository with a pipeline generated per run (never committed), a job token as the run secret `IW_GIT_JOB_TOKEN`, and the workspace's linked accounts lent as connections. That token names the run's workspace and reaches its state and the run's plan and nothing of the repository: no clone, no push, no API. A plan's reads the state and takes the lock, an apply's writes it too. A branch plans the workspaces it touches. A branch proposed from a fork is never planned (its run is `skipped`, with the reason, and the dispatcher asks again before it hands a run its credentials). An apply plans again at the merge commit, posts that plan and applies that plan file; it waits for an admin of the repository or `ci:approve` in the organisation unless the workspace applies on merge without approval. The branch's page shows the plan summary (`Infrawrench Terraform / <workspace>` on the commit, an entry in the timeline) and the monthly cost change, priced from the plan.
- **Personal namespaces** get the state backend only: no linked accounts, no runs.
- **Back to the app**: after each apply the gateway's `git-terraform` pass matches the state to the organisation's Infrawrench resources, so the tab shows what each workspace manages and what it costs (through the caller's cost visibility), and the app's resource pages say which repository and path manage a resource (`managedBy` on `GET /iac/resource`). Drift from the app's IaC reconciliation is not wired yet.
- `packages/terraform/NOTES.md` has the flow, and `packages/worker/NOTES.md` ("Terraform") what runs where.

## Tie-ins with the app

The app does not embed the forge. It links to it: a Git entry in the sidebar opens the organisation's namespace on git.infrawrench.com; resource pages name the repository that manages them; CI runs from repositories here link to their commits; Settings has a Git section (namespace, default visibility, usage). The forge links back to resource pages, costs and CI runs in the app.

Public repositories are free. Private repositories and storage follow the organisation's plan (`planAccess`); storage is sampled and metered through the same outbox pattern CI uses.

## Style

The app's look: `@infrawrench/ui`'s tokens and components, dense layouts, no blurbs. A page has a name and its controls; explanation goes in the docs. Every page sits beside one sidebar: for someone signed in, the workspace switcher, Home, Your work (Changes, Reviews, Mentions), the selected workspace's repositories (the sidebar follows the workspace picked, and the repository being read) and the account menu at the foot; for a signed-out reader, the site's name, Explore, the public repository being read and Sign in. A repository has no header: the top bar names it and holds its sections, and the Code tab is the file table with the README below.

## Local development

One command runs the whole forge on this machine and touches no account anywhere:

```sh
pnpm install
node git/dev.mjs --migrate
```

| Where                   | What                                                                                                                                                                                      |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `http://localhost:5174` | The UI under Vite, with hot reload. It proxies `/api`, `/auth`, `/mcp`, `/oauth`, `/.well-known` and the Git paths (`.git`, `raw`, `archive`, the Terraform state backend) to the Worker. |
| `http://localhost:8787` | The Worker under `wrangler dev`: R2, the Durable Objects and the queue are local, in `git/packages/worker/.wrangler/state`.                                                               |
| `localhost:8788`        | Git over SSH: the Worker's `connect` port. Clone URLs here are `ssh://git@localhost:8788/<owner>/<repo>.git`.                                                                             |
| `http://localhost:4100` | The WorkOS emulator, the one the app's dev stack uses, with its seeded user.                                                                                                              |

- **The database** is the one thing it does not start. It uses `DATABASE_URL`, or without one the app's dev stack's Postgres on port 5433 (`docker compose -f docker-compose.dev.yml up -d postgres`). The URL needs a password: wrangler refuses a Hyperdrive connection string without one. `--migrate` applies the app's migrations first (`pnpm --filter @infrawrench/web db:migrate`), which is where the forge's tables come from; leave it off once the database is current. Production is PostgreSQL 18; the migrations and the database suites were also run on 14.
- **Signing in**: **Sign in** goes to the emulator's login page. The seeded user is `dev@infrawrench.local` / `devpassword1!` (`infra/docker/workos-emulate/seed.yaml`). The first sign-in asks for a username, as in production, once the user belongs to an organisation with Git turned on (the temporary flag, KNOWLEDGE.md "Git feature flag"): put `dev@infrawrench.local` in `INFRAWRENCH_PLATFORM_ADMIN_EMAILS` in the app's `.env`, open `http://localhost:3000/admin` and turn on **Git** for its organisation. The script starts the emulator (`@workos/emulate`, through `npx`) unless one already answers on port 4100, so it shares the app's when the dev stack is up, and the same user is then signed in to both. An organisation's namespace needs that organisation's rows, which the app makes: sign in to the local app once (`http://localhost:3000`) to have one.
- **Secrets** are made on the first run and kept in `git/packages/worker/.dev.vars` (gitignored): an SSH host key from `ssh-keygen`, a cookie password, a job token key, the emulator's API key, and the dev stack's `ENCRYPTION_MASTER_KEY` so an `iwk_` key made in the local app verifies here. Delete the file to start over.
- **Git over HTTPS** is `git clone http://localhost:5174/<owner>/<repo>.git` with a personal access token as the password. **Over SSH**, add a key in the UI's settings and use the `ssh://` URL the clone box shows.
- **The UI alone**, with no Worker and no database: `pnpm --filter @infrawrench/git-web dev:mock` (its notes say what the mock covers). **The Worker alone**, serving the last `vite build`: `node git/dev.mjs --no-ui`. `--no-emulator` leaves WorkOS to whatever `WORKOS_API_HOSTNAME` in `.dev.vars` names.
- CI for repositories here needs the app's CI proxy and is off locally; a push still records its run.

## Tests, CI and deploys

- **Each package's tests** are `pnpm --filter @infrawrench/git-<name> test`. They drive the real programs and skip the suites whose program is missing: `git` (core, ops, protocol, ssh, worker; a current one, since ops compares itself with `git merge-file --diff-algorithm`, which is 2.44's, and with how a current git scores renames), `ssh` and `ssh-keygen` from OpenSSH 9.9 or later (ssh, and the worker's workerd suites, which also want `GIT_WORKER_E2E=1`), `unzip` (ops), `terraform` (terraform). The worker's database suites are `test:db`, against a migrated scratch Postgres. Use a current Node 24: 24.21 and 24.22 pass, and on 24.11 seven of the SSH server's tests hang.
- **Infrawrench CI** runs them in `.infrawrench/ci/git.yml`, on machines (`platform: linux`), because an isolate has neither Git over SSH, Terraform nor workerd. That file says what each kind of job has. There a skipped test fails the job (`.infrawrench/ci/no-skips.mjs`), so a suite that could not find its program cannot pass by not running; `.infrawrench/ci/git-tools.sh` builds the git and the OpenSSH client the suites need (Ubuntu 24.04's are too old for them) and fetches Terraform, each pinned by sum. Typechecks, Prettier and the source hashes are `.infrawrench/ci/test.yml`'s, with every other package's.
- **The Worker's bundle** is checked by a test (`worker/src/__tests__/import-graph.test.ts`): no plugin code, nothing that cannot run in a Worker, and the size it was measured at. `worker/README.md` has the numbers.
- **Deploys** are `.github/workflows/git-deploy.yml`: on a push to `main` that touches `git/**` or what the Worker and the UI are built from, it builds the UI, waits for the commit's migrations to be in the database (the app's deploy applies them), and deploys the Worker with the app's secrets it shares. `worker/README.md` lists every binding, variable and secret; `infra/README.md` ("git.infrawrench.com") is how the bucket, the queues, the host key and the Spectrum application are made.
