Plugins should have all their logic encapsulated within them. The base should be as generic as possible, and then each plugin should handle everything. We don't want the electron code to have platform specific stuff. Update KNOWLEDGE.md as the project grows.

When you make changes to content that isn't specific to either web or desktop, make sure to implement on the other. Prefer sharing code where it makes sense to do so.

NEVER use a emdash unless needed.

A workspace package the **main process** imports must also be added to the `exclude` list of `externalizeDepsPlugin` in `app/packages/desktop/electron.vite.config.ts`, which is the list of packages electron-vite _bundles_ rather than leaves as a runtime require. `electron-builder`'s `files` drops `node_modules/@infrawrench/**` from the asar, so an externalized workspace package throws `Cannot find module` the instant the packaged app starts; a lit dock icon and no window, with nothing visible in dev because dev resolves through the real `node_modules`. Adding the dependency to `package.json` is only half the change.

The desktop app doubles as the `infrawrench` CLI (`app/packages/desktop/electron/cli/`, entered via `--cli` in `electron/index.ts`). Keep `electron/cloud-tokens.ts` and `electron/db.ts` free of GUI side effects; the CLI depends on that. The CLI takes zero new runtime dependencies (hand-rolled ANSI output/charts, `node:util` parseArgs). When you add a user-facing data surface (new listing, metrics, costs-style feature), consider a CLI subcommand with `--json` + text output.

The mobile app (`app/packages/mobile`, Expo + expo-router) is a cloud companion that talks Bearer to the existing web API; it adds no server surface of its own. Platform-neutral client logic (fetch, tokens, SSE, chat contract, WS frames, push helpers) lives in `@infrawrench/client-core`, not in the mobile package; `@infrawrench/ui` re-exports the chat types from there, so shared contract changes go in client-core. Mobile can't use DOM libraries; give it a small native counterpart instead (e.g. `ChatMarkdown`). When you change a cloud feature the mobile app surfaces (chat, dashboards, resources, notifications), mirror the change there like you would between web and desktop; deliberate omissions (read-only billing, no editors) are listed in KNOWLEDGE.md. `assets/generated/terminal.html` is gitignored build output; `scripts/build-terminal-html.mjs` generates it, wired into `dev`/`android`/`ios`/`typecheck` and the `eas-build-post-install` hook; keep new generated assets on that pattern. Verify with `pnpm --filter @infrawrench/mobile typecheck`.

When you make code for providers remember that the user shouldn't have to know the API. If it needs a resource or a slug of some kind, add a picker. Also remember this replaces the cloud dash by in large and is not a replacement to it. If you add something, think about how the user can edit it if possible. Look online to verify API's, assume your memory is wrong. Make sure to include all possible metrics/side tools where possible. When you want a logo SVG, please also look online. You aren't good at freestyling logos.

## Workspace tabs

Org-level pages opened from the sidebar are **workspace-tab kinds, never plain routes**; a page outside the tab system leaves a stale active tab and a stale window title. The only exceptions are Moment and `/admin`, which get their titles from `plainRouteDocumentTitle` instead.

Adding a tab kind touches the whole chain, in one change:

- `ui/src/store/ui.store.ts`; the `WorkspaceTabTarget` union plus all three switches (`getWorkspaceTabId`, `getWorkspaceTabFallbackTitle`, `workspaceTabTargetsEqual`). For a single-instance tab with remembered state (Settings, Deploy), give it a fixed id but compare the state field in `workspaceTabTargetsEqual`; that is what makes the route sync record it and reactivation restore it.
- `ui/src/workspace-tabs.ts`; a target factory, exported from `ui/src/index.ts`.
- Both platforms' `lib/workspace-tabs.ts`; `getWorkspaceNavigateArgs` and `syncWorkspaceRouteFromPath` (desktop uses `?param=` search, web uses path segments). A target that carries state in the query needs the route's `validateSearch` extended too; it is a **whitelist**, so an unlisted key is dropped from the URL on navigation and the tab silently resolves to something else. Numeric values go in `search` as numbers, not strings: the router JSON-encodes each value, so `"4"` becomes `%224%22` and reads back out of a raw query string with its quotes on.
- Both viewports' `renderPanel`, plus a no-op route stub per platform (tab content renders in the viewport, which keeps every open tab mounted).
- Desktop `__root.tsx` `validateWorkspaceTab` and the web `validate-tabs` kind list **and** the OpenAPI `TabTarget` enum; a kind missing there gets silently dropped on reload. The enum change means an `API_VERSION` minor bump.

Tests enumerate kinds in `{web,desktop}/src/lib/__tests__/workspace-tabs.test.ts`; the full conversion recipe with rationale is in KNOWLEDGE.md.

## Settings

The 14 settings sections are shared components in `ui/src/settings/`, rendered by web's thin `/org/:orgId/settings/*` route wrappers and by the desktop cloud-mode Settings tab (`DesktopSettingsPanel`). They get everything platform-specific; API transport, permissions, `openExternal`, cross-surface navigation; from `SettingsHostProvider` (`ui/src/settings/host.tsx`); never import `@/lib/api` or router primitives inside a section.

- **New section**: add it to `SETTINGS_SECTIONS` + `SettingsSectionBody`, a web route wrapper, and a docs page. Both platforms' navs derive from the registry.
- **New endpoint used by a section**: the desktop reaches the cloud through the single `cloud_settings_request` IPC channel, whose handler (`electron/cloud-data/settings.ts`) enforces a method+path allowlist. Add the new path there in the same change, or the section works on web and silently fails on desktop.
- Structured errors the sections branch on (seat limit, plan gate) live in `client-core/src/api-errors.ts` and must be thrown by both transports (web `apiFetch`, desktop `settings-client.ts`).

## UI translations (gt-react)

The web and desktop UIs are internationalized with gt-react (General Translation); English is the source language and untranslated text just renders in English, never breaks. The pipeline detail lives in KNOWLEDGE.md ("UI translations"); what binds changes made elsewhere:

- **New user-facing strings** in `ui/src`, `web/src`, or `desktop/src` should be marked: `const gt = useGT()` + `gt("Plain string")` / `gt("With {value}", { value })` for strings and attributes, `<T>` (with dynamic children in `<Var>`) for JSX, and `import { t } from "gt-react"` for module-scope event handlers that run after boot. `gt` is a hook product; include it in effect dep arrays.
- **`translations:audit` is a CI gate** (the Translations job in `test.yml`): every JSX text node, user-facing attribute (placeholder / title / aria-label / alt / label), and toast string must be either marked for translation or excused with an `i18n-ignore: <reason>` comment on the same line or the line above (`// i18n-ignore: …` between JSX attributes, `{/* i18n-ignore: … */}` in JSX children). The reason is mandatory, and a marker that no longer suppresses anything fails the gate too, so excuses cannot rot. Excuse only deliberately-English text: product names (Slack, 1Password), syntax examples (`s3:GetObject…`, `KEY=value`, SQL), technical identifiers (IANA timezones, region codes), example emails, hostnames and paths. Anything a translator could sensibly translate gets marked instead, plus catalog entries in the same change when feasible. Run `pnpm --filter @infrawrench/web translations:audit` before pushing; it exits non-zero on any violation. The same CI job also runs `translations:status`, which fails only on gt extraction errors (a broken `<T>` site), never on catalog lag.
- **Never pass a variable to `gt()`, `t()`, or `msg()`** in extracted sources; the gt CLI hard-errors on non-literal arguments to the names it recognizes. Anything data-driven (plugin display names, resource type labels, values from the API) goes through `useDataString()` from `@infrawrench/ui`, which does the same lookup under a name the CLI ignores.
- **Changing plugin metadata** (manifest displayName/description, credential field labels, resource type names, field/output labels or descriptions) means regenerating the extraction manifest in the same change: `pnpm --filter @infrawrench/web generate:plugin-strings`, commit `ui/src/i18n/plugin-strings.gen.ts`. It is generated from `BUNDLED_PLUGINS` and never imported at runtime; strings containing `{}` or `<>` are deliberately skipped (they read as ICU syntax).
- **The two apps mirror.** `gt.config.json`, `src/_gt/` catalogs, and `loadTranslations.ts` exist in both `web` and `desktop`; a locale or config change goes to both. Adding a locale touches both configs, empty `{}` stubs in both `_gt` dirs, and `website/src/content/docs/features/interface-language.md`.
- **Boot order is load-bearing**: each app's entry is `src/index.ts` (not `main.tsx`), which must finish `initializeGTSPA()` before importing `./main`. Desktop additionally installs `installCookieStoreShim()` as its very first statement.
- **The locale cookie is the mechanism, and the desktop shim is what makes it work.** gt-react resolves the locale from `[cookie, ...navigator.languages, _getLocale()]` in that order, so only the cookie outranks the OS language; `_getLocale` is a fallback, not an override. The packaged renderer runs on `file://`, where Chromium discards cookie writes, which silently pinned it to the OS language and made the picker a no-op; `desktop/src/lib/cookie-store-shim.ts` gives that origin a localStorage-backed cookie jar (feature-detected, so dev over http is untouched). `localStorage["infrawrench-locale"]` via `getStoredLocale`/`setStoredLocale` from `@infrawrench/ui` is a _secondary_ record passed as the boot-time `locale` candidate; it does not by itself beat the OS language. Anything touching locale persistence must keep both in step, and must not assume passing `locale` to `initializeGTSPA` sticks; it only seeds the cookie.
- **The catalogs are maintained locally, not through General Translation's API.** `src/_gt/*.json` are plain `{contentHash: translation}` maps (prettierignored), and the CLI's extraction hash is the same one gt-react derives at render time, so translations can be authored offline. There is deliberately **no `translate` script**: `gt translate` has no local incremental mode; it re-extracts every marked string, sends all ~3,300, and bills for them, because its dedupe is server-side under hashes these catalogs were never uploaded with. (`gt upload` cannot register them either: `aggregateFiles` returns nothing when `gt` is the only configured format.) Don't reintroduce one, and don't invoke `npx gt translate` by hand, unless the user explicitly asks. Builds never depend on any of this; a lagging catalog only means English text.
- **After changing UI strings or plugin metadata, check what drifted**: `pnpm --filter @infrawrench/web translations:status` prints per-app, per-locale missing/orphaned counts for both apps offline. Add `--emit-batches <dir>` to write the untranslated sources as `{i, s}` batches ready to hand to translators (the workflow that filled these catalogs is in KNOWLEDGE.md). Orphaned entries; translations whose source changed or vanished; are inert at runtime; `gt generate` prunes them, but note it also backfills missing keys with English source text, which hides what is still untranslated.
- Mobile is deliberately untranslated (gt-react-native is experimental and breaks Expo Go), so the usual web↔desktop↔mobile mirroring rule does not extend there yet.

## Desktop changelog (git-cliff)

`include_paths` in `cliff.toml` limits the changelog to commits touching the desktop app or a workspace package it transitively depends on. When you add or remove a workspace dependency of `@infrawrench/desktop` (or of anything in its closure), recompute the closure and update the glob list in the same change. Currently that closure is `app/packages/{desktop,client-core,ui,workflow-runtime}` plus all of `plugin-architecture/`; a new desktop dep on e.g. `@infrawrench/telemetry` would need its path added, and a config key typo fails silently (it's `include_paths`, plural; the CLI flag is singular), so verify with `git-cliff --unreleased` against a commit that should be excluded.

## Terraform provider

`terraform-provider-infrawrench/` at the repo root manages **Infrawrench's own configuration** as Terraform resources: cost allocation and reporting, monitoring, lifecycle governance, connected accounts and access control, and alert delivery (47 resources, 6 data sources). Its README carries the full design rationale; what follows is what binds changes made elsewhere in the repo.

Three unrelated features have "Terraform" in the name; **eject to Terraform** (`Plugin.terraformExport`, writes HCL describing _the user's cloud resources_), **org config as code** (`infrawrench config export/plan/apply`, whole-org JSON document), and **this provider** (per-object CRUD against the org-scoped routes). The provider deliberately does not wrap config as code: that document addresses entities by a name-derived `key` with no server id, so import is impossible and a rename becomes destroy-and-recreate. It also carries only a handful of the object types the provider manages.

- **It is outside every JS toolchain, on purpose.** Not in `pnpm-workspace.yaml`, not in `turbo.json`, not in `cliff.toml`'s `include_paths` (a standalone Go module is outside the desktop changelog's dependency closure). Build and test it on its own: `cd terraform-provider-infrawrench && gofmt -l . && go build ./... && go vet ./... && go test ./...`, Go 1.25+. `.github/workflows/terraform-provider.yml` runs exactly that and nothing else touches the module; `test.yml` is the pnpm workspace's CI and never reaches it. Its path filter covers the provider folder **and `app/packages/web/openapi.json`**, because the wire drift test reads the spec and a regeneration can break the module without touching a file in it.
- **Every URL and JSON body lives in `internal/iw/`**; `wire.go` (cost allocation and reporting) and `wire_platform.go` (everything else) for the structs, `endpoints.go` and `endpoints_platform.go` for typed per-object methods. Nothing under `internal/provider/` assembles a path or a body; the split across files is by domain and purely for readability, the package boundary is the invariant. These are hand-written rather than generated from the spec because the SDK generator collapses `discriminator` unions to `any` and drops `readOnly`/`default`, which are exactly the signals that decide whether an attribute is `Computed`.
- **A change to any route the provider covers is a change to the provider, in the same commit**; the same mirroring rule that holds between web, desktop and mobile. That is now most of the org-scoped configuration surface, not just cost: probes, metric alerts, status pages, schedules, freezes, custom graphs, log queries, accounts, bastions, roles, API keys, SSH keys, deploy triggers, workflow schedules, alert routing, Slack/Teams/Jira/Linear, the digest, network flow collection, and every `*/settings` singleton. `internal/iw/wire_spec_test.go` reads `app/packages/web/openapi.json` and fails when a schema property is neither decoded by a Go struct nor listed in that check's `ignored` list with a written reason. It runs one way only (extra Go fields are expected, since the checked-in spec lags the routes) and skips when the spec is absent, which keeps the module extractable to its own repository.
- **`schemasKnownAbsent` is empty as of the 1.9.0 spec regeneration**, which brought scenario models and billing rules into the document. Keep the list and `TestKnownAbsentSchemasAreStillAbsent`: the next object added ahead of a spec refresh goes there, and the test then says out loud when the refresh catches up.
- **Every resource must implement `ImportState` and `Configure`**; `provider_test.go` enforces both across the registry, because someone adopting the provider already has budgets and a resource without import would have to be deleted and recreated to come under management. Objects with no single-GET route (cost centres, allocation rules, report folders, probes, status pages, schedules, freezes, log queries, roles, SSH keys, bastions, API keys, snippets, accounts, deploy triggers, Slack channels, Teams webhooks, digest recipients, exchange rates, cost annotations, report notifications) are read by listing and filtering, and their `endpoints.go` wrapper synthesises the 404 itself so an out-of-band delete still surfaces as "needs recreating" rather than silent success. Bastions and API keys go further: DELETE only _revokes_, and the listing keeps returning revoked rows, so their wrappers treat a non-null `revokedAt` as a 404 or `terraform destroy` would silently no-op.
- **Adding a resource or data source** touches, in one change: `wire*.go` + `endpoints*.go`, the `internal/provider/resource_*.go` (or `datasource_*.go`) file, the registry in `provider.go`, `wantResources`/`wantDataSources` in `provider_test.go`, a `specChecks` entry when the spec describes the schema, the README's resource table, `app/packages/website/src/content/docs/features/terraform-provider.md`, an `examples/resources/infrawrench_<type>/import.sh`, and a regenerated `docs/`. `documentation_test.go` checks the two prose tables against the registry in both directions, and CI regenerates `docs/` and fails on a diff, so a forgotten row fails the build rather than shipping.
- **A documented bound must be an enforced bound.** Any attribute whose `MarkdownDescription` states a range or a length carries a matching validator from `internal/provider/validators.go` (`between`, `betweenFloat`, `elementsBetween`, `sizeBetween`, `sizeAtMost`, `elementsLengthBetween`, `stringvalidator.LengthBetween`). `TestDocumentedRangesAreValidated` walks the served schema and fails on any that does not; a stated bound that is not checked reads as a promise the provider will not keep, and the failure lands mid-apply as an HTTP 400 after other resources in the graph already exist. The probe timings are the case that argues it hardest: the server _clamps_ rather than rejecting, so an unvalidated value applies successfully and then diffs forever.
- **`docs/` is what the Registry publishes**, generated from the schemas by `go tool tfplugindocs generate --provider-name infrawrench` (pinned as a Go tool dependency; needs `terraform` on PATH) and **committed**. Nearly all of it comes from each schema's `MarkdownDescription`, which is why those are written as prose rather than labels. `examples/` supplies what a schema cannot: the provider index example, per-resource `resource.tf`, and an `import.sh` for every resource. `terraform-provider-infrawrench/docs/` is in `.prettierignore`; Prettier and the generator would otherwise rewrite each other forever.
- **Adding a resource does not bump `API_VERSION`.** The provider is a client; it changes no HTTP surface. Changing a route it calls does.
- **Auth is Bearer**, from `INFRAWRENCH_API_KEY` / `INFRAWRENCH_ORG_ID` / `INFRAWRENCH_BASE_URL`, and both an `iwk_` API key and a WorkOS access token work; `apiKeyOrgMiddleware` widened the org tree. Two resources stay closed to keys by `API_KEY_DENY_RULES` (`web/src/auth/api-key-route-policy.ts`): `infrawrench_api_key` entirely, `infrawrench_role` for writes. The provider recognises that 403 and names the affected resources (`apiKeyDeniedHint` in `internal/iw/errors.go`), and separately explains a 401 as a key problem rather than a categorical rejection (`apiKeyUnauthorizedHint`). **If you add a deny rule covering a route the provider calls, update those hints and both resources' schema descriptions.**
- **Releases mirror to a satellite repository**, `Infrawrench/terraform-provider-infrawrench`, exactly as the Go/Swift/PHP SDKs do; the Terraform Registry requires a dedicated repo named `terraform-provider-{NAME}` and cannot read a monorepo subdirectory. The monorepo is the direction of truth and the satellite's tree is replaced wholesale, workflows included, so **nothing there is hand-maintained**. Cutting a release is one edit: change `terraform-provider-infrawrench/VERSION` and merge. Before mirroring, the workflow dry-runs GoReleaser and asserts the artifacts are ingestible; the manifest is checksummed, the archives are named `terraform-provider-infrawrench_*`, and `docs/index.md` exists. Each of those assertions is a burnt version number: `v0.1.0` published the manifest without a checksum, `v0.1.1` published with no docs. A released tag is never re-cut, so the fix for either is always another version. `.github/workflows/publish-terraform-provider.yml` gates on the tag `terraform-provider-v<version>`, re-verifies, mirrors, and pushes `vX.Y.Z`; the satellite's own `release.yml` (which lives in `terraform-provider-infrawrench/.github/workflows/` and is inert here) runs GoReleaser. The provider's version is **its own**, not `API_VERSION`; it is a client, so a spec bump obliges no release.
- **The provider is MIT licensed**, not the repository's BUSL-1.1, because it is a client library people vendor into their own infrastructure repositories. `terraform-provider-infrawrench/LICENSE` governs everything under that directory.
- Acceptance tests (`TF_ACC=1 go test ./...`) create and destroy real objects against a live org; they need credentials on top of `TF_ACC` and should only ever point at a scratch organization.

## Linux app server (`linux-appserver/`)

`linux-appserver/` at the repo root is the remote half of Linux application support: `iwappd`, a headless Wayland compositor uploaded to a customer's host over SSH that streams one app window per workspace tab. KNOWLEDGE.md carries the design rationale; what binds changes made elsewhere:

- **It is outside every JS toolchain, on purpose**; not in `pnpm-workspace.yaml`, not in `turbo.json`. Build and test it on its own: `cd linux-appserver && cargo fmt --all -- --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace`, Rust 1.85+ (edition 2024, toolchain pinned in `rust-toolchain.toml`). `.github/workflows/linux-appserver.yml` runs exactly that plus the static musl builds; `test.yml` is the pnpm workspace's CI and never reaches it.
- **The shipped binary is built inside Alpine**, not with a musl cross-toolchain: the compositor links `libxkbcommon` and only Alpine packages a musl build of it (`libxkbcommon-static`). The recipe is in the README, and CI runs it per architecture on its own native runner.
- **It _is_ in `cliff.toml`'s `include_paths`**, unlike the Terraform provider, because the desktop app ships this binary; a change here is a user-visible desktop change.
- **The protocol has two ends.** `crates/iw-proto` is the source of truth for the frame layout and the control messages, and its serde field names are the field names in `@infrawrench/appstream-core` (`plugin-architecture/packages/appstream-core`), the client half. A change to either side is a change to both, in one commit: `crates/iw-codec/tests/golden.rs` writes the fixtures that package's tests decode, so a format change fails on one side or the other until both move. Regenerate with `UPDATE_GOLDEN=1 cargo test -p iw-codec --test golden` and commit the fixtures.
- **The client half is two workspace packages**: `@infrawrench/appstream-core` (the wire; its serde field names come from `iw-proto`) and `@infrawrench/appstream-host` (staging and running the binary over an SSH connection the caller supplies). Both apps consume both; the launcher is a resource view and each window is a `linux-app` tab. A change to the protocol is a change to `iw-proto`, `appstream-core` and the golden fixtures in one commit.
- **No new runtime dependencies without a reason you would defend in review.** Everything in this workspace runs on someone else's machine; the list is `serde`, `thiserror`, `zstd` and `jpeg-encoder` (the lossy tier; zero transitive dependencies, and the decoder is the browser's own).

## Server environment variables

Every server-side variable read through `process.env` (web, poller, github-watcher) must be added to **both** places in the same change:

- `app/packages/web/.env.example` - local development.
- the `app_env` map in `infra/terraform/terraform.tfvars.example` - production.

There is no per-variable Terraform to write. `app_env` is a `map(string)` (`infra/terraform/variables.tf`) written wholesale into the `infrawrench-env` k8s secret that all three deployments `envFrom` (`infra/terraform/kubernetes.tf`), so a key added to the map is a key in the pods. The flip side is that nothing fails at plan time: a variable missing from the tfvars map is simply `undefined` in production, and the feature silently no-ops.

`terraform.tfvars` itself is gitignored; the example file is the only checked-in record of what the deployment expects, so treat it as documentation. Above each key say whether it is required or optional, what the value looks like or where to create it, and what degrades without it. Group related keys under one comment the way Slack, ClickHouse, and the GitHub App already are.
